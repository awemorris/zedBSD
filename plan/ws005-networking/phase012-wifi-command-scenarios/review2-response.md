日付: 2026-09-06
対象レビュー: `/home/awe/claude/zedBSD/plan/net-wifi-report-2.md`
対象コード: `/home/awe/zedBSD` の `a3f1ea3` からの未コミット差分。

モデルの優劣ではなく、現行コードの制御フローと契約で判断した。
ユーザーは外部レビューを受けた追加修正を指示した。受け入れ前の
修正段階として扱い、30シナリオや実機テストは実行していない。

| 指摘 | 判断と対応 |
| --- | --- |
| A: 1024バイトを超える resolver が接続・後片付けを阻害 | 妥当。`snapshot_resolver()` に「存在するが大きすぎて所有しない」状態を追加。IPv4/経路のスナップショットを失敗させず、完全なバイト比較ができないファイルを削除しない。DHCP前が巨大でも、DHCP後が小さな生成済みファイルなら差分とインタフェース別マーカーを確認して所有できる。削除直前の再確認でも巨大化は外部変更として扱う。 |
| A: 5秒ごとに永久再試行する | 再試行間隔への指摘は妥当。実際のOSエラーは5、10、20、40、60秒へバックオフし、その後60秒で再試行。自動接続側がこの期限を消してしまわないよう修正。外部変更で所有を失った場合は再試行しない。 |
| B: Wi-Fi探索中の有線コマンドがEBUSY | 妥当。`SHOW` は子プロセスを起動しない専用観測経路で応答。認可済みの有線変更は背景Wi-Fiを中断してから、通常要求と共通の `dispatch_request()` に渡す。認可・confirmed所有・期限を再確認し、再帰的な変更実行を避ける。 |
| C: 通常時と処理中のlist形式が異なる | 妥当。新規取得とキャッシュで共通の `append_wifi_snapshot()` を使用。`snapshot-age-ms` と `scan-snapshot` を明示し、未観測・キャッシュ退避も明示する。出力容量超過は完結した行までを残し、予約領域に `wifi output-truncated=1` と最終状態を出す。 |
| D: enableの成功が接続成功ではなくなった | 契約変更との指摘は妥当で、非同期化自体は維持。`net` のヘルプに背景接続とlistによる状態確認を明記。成功は有効化の受付であり、接続成功は後続の観測で確認する。 |
| E: 静的キャッシュとネストしたスタックが大きい | 妥当。各radioの完全なchild構造体を16個保持する方式を廃止し、レコードを必要な長さだけ動的確保。全キャッシュ合計32,748バイトを上限とし古い観測を退避する。観測応答の作業バッファを動的確保し、変換時の32KBの中間スタック配列も廃止した。 |
| F: 後片付けエラー時にpolicyをリセットしない | 不具合との判断には同意しない。正常化できなかった所有情報を残すのは意図した契約。失敗時もリセットすると、再利用された呼出元が未完了のL2/L3を見失う。コメントを成功時だけpolicyを消す契約に修正した。 |

## 採用しない提案・レビュー記述の補正

- Aの「失敗が続いたら最終的に所有を捨てる」は採用しない。I/Oエラーは
  外部の置換を証明しない。所有放棄は、値の不一致・消失・巨大化などを
  実際に確認した資源だけに限定する。回数だけではL2退去やL3削除の成功に
  置き換えない。
- Fの「起動時正常化を無期限にする」は採用しない。応答しない子プロセスで
  起動が永久停止しないよう30秒の正常化予算を保持する。正常化失敗は
  `wifi-normalize` の起動失敗として報告し、成功を偽らない。
- Dの「enableが1秒未満に返る」は保証しない。associationは背景処理だが、
  radioの準備や既存接続の退去は有限の処理時間を必要とする。
- §4の「失敗後はenableまたはdisconnectで自動検索を再開」は不正確。
  `disconnect` は自動検索を抑制した状態を維持する。再開は `enable`、
  または保存済みSSIDへの明示的な `connect` で行う。
- 冒頭の「RF処理がrequest callbackから決して動かない」は広すぎる。
  イベント処理と実行中の観測コールバックから再帰的なRF処理を排除した。
  通常の要求ハンドラは、明示connectやradio準備の子処理を引き続き所有する。
- Eの「端末レコード除去後は必ず大幅に小さい」は容量保証として使わない。
  BSS削減は必要長の確保と合計予算で保証し、長い実データを想定している。

## 付随指摘への対応

途中までの入力に対する5秒のフレーム待ちと5秒のEOF待ちが、実行中Wi-Fiを
停止させる指摘も妥当。`receive_wait_request()` は到着済みバイトだけを
`MSG_DONTWAIT` で取得する。入力枠は4個、各枠は受付から絶対5秒、最大長も
固定。完全なフレームとEOFを得るまでは政策の要求として受け付けない。
背景処理が終わっても入力枠を捨てず、外側のループで受信を継続する。
返信の逆圧も有限にする。通常の待機中受付は従来の有限read経路を保持する。

延期する有線要求にはWi-Fiの後片付け待ちが追加されるため、クライアントの
受信予算にも15秒を加え、ヘッダからペイロードまでの絶対期限を使う。
confirmed DISARMの250ms契約は保持する。背景Wi-Fi中には有効なconfirmed
トランザクションは存在せず、非アクティブなCHECK/DISARMは子処理なしで
応答する。延期要求は残りの背景処理期限を最大10秒の後片付け枠へ縮める。
明示的な前景Wi-Fi処理との変更競合は引き続きEBUSYとなる。

使用されなくなった `allow_recovery` 引数を削除し、待機中のopcode認可も
通常受付と同じNULL検査を行う。
