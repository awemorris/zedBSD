## QEMU の解析

起動しない・固まる・例外は、log を読まずに QEMU のデバッグ機能で解析する（AGENTS.md §9）:

- **gdbstub**: `-S -gdb tcp::<port>` で止めて起動し、host の `gdb` で `target remote :<port>`、`bt`・`info registers`・`x/i $pc`・`stepi`。`vmunix` は strip されていない。
  行番号・局所変数が要る時は調査用の build だけ DWARF 付きにする。
- **map**: link で作る `$(BUILD)/vmunix.map` で address から関数を引く。
- **monitor/QMP**: `info status`・`info registers`・`info mem`・`info tlb`・`x/`・`xp/`・`pmemsave`。
- **trace**: `-d int,cpu_reset,guest_errors -D <file>`（例外と reset だけ）。
- pc98 は QEMU の PC-98 fork（`~/qemu-pc98/build/qemu-system-i386`、`-M pc9821,pegc=off,coregraph=on`）で起動し、`pmemsave 0xa0000 0x2000` で
  取り出した text VRAM を `boot-parameter-image-tool decode-pc98-vram` で読む。
- guest の memory: amd64 は 8 GiB（`plan/tools/guest/guest.py` の既定と `boot-test.sh` の `uefi-usb`）。arm64 の QEMU raspi4b は board が 2 GiB しか
  受け付けないので 2 GiB。i386 は変えない。

## 注意

注意（2026-10-09 P1 の所見）: BUG-274 の直しで `ps -o args` が command line の全体を出すようになった。guest の試験で `ps -A -o pid,args | grep <語>` で選んで kill する形は、その語が試験自身を走らせる shell の行にも出ると自分を kill する（ws172 の passkey の FAIL の原因）。新しく書く試験は `ps -A -o pid,comm` で選ぶ。既存の約 380 箇所は一斉に直さず、FAIL した時に追従する（試験の整理の基準を当てる）。

- WS105 継続 fixture: `plan/tools/keiland-linux/dbus-wire.c` / `dbus-wire.py`（独立 wire / fd 境界、ordinary + ASan/UBSan）、`seat-fd.c`（guest の DRM master / caller fd 所有権）。[手順](tools/keiland-linux/README.md#logind-の-fd-と-d-bus-wire-の独立-fixture)。

## RDNA 機の時間の枠（2026-10-29 ユーザー「Q1を通して、あらかじめ時間枠を定義し、さらにQ1を通じて排他できたことを確認しつつ、譲り合って使えば、同時に進められるかなと思います。」、枠はユーザーの回答「案どおり、45 分 (推し)」）

- 対象: RDNA 機（10.0.10.3、Debian と zedBSD、SwitchBot の plug 1 AC276E42B252）。使う担当: P2（WS291）、P1（WS235 の RTL8127）、P3（WS221 p010）。
- 枠は 45 分。Q1 が順を決めて担当に知らせる。優先はネットワーク（WS235・WS221 p010）、ユーザー「あるいは、排他がちょっと難しいようであれば、ネットワーク改善を優先してもいいです。」。
- 使い始め: 担当は Q1 に「使い始め」を送り、centris で `flock -n /tmp/zedbsd-rdna.lock` を取り（中に担当名・始め・終わりの予定の時刻を書く）、Q1 が排他を確かめた返事を待ってから機械を触る。
- 終わり: 機械を決めた状態（Debian か zedBSD か、入っている kernel を phase.md に）にして lock を返し、Q1 に報告。延長は Q1 を通して相手と譲り合う。電源の入れ直しは lock を持つ担当だけ。
- 機械の構成の変更（2026-10-29 05:4x ユーザー「では、RDNA機をシャットダウンします。再起動後、RTL8127と、RTX 2070が接続されています。RX 5600 XTはPCIスロットの高さの関係で、RTL8127と排他だからです。」）: 10.0.10.3 は今 RTL8127（PCIe 10GbE）と RTX 2070（NVIDIA）。RX 5600 XT（RDNA）は外した（RTL8127 と同時に挿せない）。RDNA の実機の計測は、RX 5600 XT を挿し直すまでできない。
- 2026-10-29 ユーザー「移設完了、起動済みです。」: 10.0.10.3 の RTL8127 は 10GbE の switch へ（前は 2.5G の switch）。
- 2026-10-29 08:3x ユーザー「あ、Switchbotがつながってないです。いまからつなげます。」: 移設の後、10.0.10.3 の SwitchBot の plug 1（AC276E42B252）が機械につながっていなかった（08:24 の P2 の cycle は届いていない）。
- 2026-10-29 08:4x ユーザー「HDMIケーブルがRTX 2070に認識されていなくて、GOPがでてなかったっぽいので、DPケーブルで起動しました。」: HDMI で GOP が出ない時、NVMe の zedBSD は 2 回とも network に出なかった（起動しなかったのか未確かめ）。DP の cable に替えた後の 08:49 の起動では 08:51 に 10.0.30.5 に出た。10.0.10.3 の画面は DP でつなぐ。追記（P2 の調べ）: 「出なかった」の判定は、新しい worktree の `plan/tmp/guest/id_ed25519` が 0664 で ssh が鍵を拒み、uname の確かめが失敗した物だった見込みが高い（chmod 600 で直った）。zedBSD は 2 回とも起動していた可能性があり、GOP が無い時に起動しないという Bug の候補は根拠が弱い（未確かめのまま）。
