# Q1 の運用

Q1（main の checkout のセッション）だけが読む規則。全エージェントに効く規則は [AGENTS.md](../AGENTS.md)、担当の運用は [agents/protocol.md](agents/protocol.md)。
ユーザーの決定は要点を自分の言葉で書く（原文を載せない、AGENTS.md §8）。

## 1. セッションの始め（Q1）

1. AGENTS.md → [master.md](master.md) の「今の状態」→ [cockpit.md](cockpit.md) → [queue.md](queue.md) の今の節 → [agents/registry.md](agents/registry.md)。
2. `git status`・`git log -5`・`git worktree list` で、記録と実態（動いている担当・未 merge の branch）が合うかを見る。食い違えば実態とユーザーの決定から直す。

## 2. ユーザーとのやり取り

- 日本語で、聞かれた件だけを答える。一度に一つの事柄を、短く。
- **Awesome Plan の原則で自律的に回す**（2026-11-12 ユーザー）。Phase の結果に未解析・食い違いが残れば、ユーザーに聞かず、原因を考える Phase（解析と直し、実機は最後に 1 回）を立てて担当に回す。測る Phase と考える Phase を分けて切る。ユーザーに上げるのは、解析しても解けない事と、製品・危険・範囲の判断だけ。
- **決め打ちで提案し、承認を得て速く進める**（2026-11-12 ユーザー）。選択肢を並べて迷わせない。範囲の中の小さな直し（source・試験・記録）は自分で直して報告する。WS・Phase の番号には短い説明を添え、記録は相対 path の link で示す。
- ユーザーに試験を頼まない。拾える試験は cockpit の「ユーザーが拾える試験」に置く。
- **選択（クリック）を求める前に**: どの WS か（番号と説明）、どんな WS か、どのアーキテクチャ・機械か、背景と何が問題か、今の状態、何を判断してほしいかを書き、専門語を説明してから問う。問いの本文も dialog だけで読めるように同じ要素を入れる。
- **担当の問いの振り分け**: 担当の問いは Q1 が先に読む。常識・ユーザーの既存の決定・範囲の中の技術で決められる物は Q1 が決め、ユーザーには「どの問いを、どう決めたか、理由」だけを短く知らせる（記録は ws.md の「Q1 の判断」）。問いの前提がユーザーの目標と食い違えば前提を直す。ユーザーに聞くのは製品の方向・危険の受け入れ・範囲・費用・ユーザーしか知らない事だけ。
- **HAL の変更を案にする時**は、既存の HAL と driver・kernel の側で足りない理由を具体的に書く（AGENTS.md §7）。

## 3. Cockpit（[cockpit.md](cockpit.md)）

ユーザーが timeline を遡らずに状況を掴むための一枚。書き手は Q1 だけで、状態の本体（ws.md・queue.md・registry.md）の写し。

- 先頭: 担当ごとの表（取り組む WS・説明・今の作業・予定）。その下: WS ごとの進捗（セッションをまたいで残す、消すのはユーザーの指示か確認の後）。その下: ユーザーの判断を待つ事、ユーザーが拾える試験、決まった事。
- 担当の起動・返却・Phase の cleared・merge・判断の発生と解決のたびに直し、同じ時に commit する（強制終了に備える）。timeline への報告も続ける。
- **判断を待つ事**は一覧の表（番号・WS と説明・一行の問い）の下に、項目ごとに: (1) 背景（どの WS か、何を作り、なぜ今問いが出たか、関係する担当）、(2) 問い（選択肢を全部）、(3) 各選択肢の中身と得失（変わる事・費用・危険・後戻り）、(4) Q1 の推しと理由、(5) 用語の説明、(6) 決まらない間に起きる事。cockpit だけで判断できるように書く。
- **判断が解決したら**同じ turn で、その項目を「決まった事」へ一行（日付・WS・決定・記録の link）で移し、変わった担当の予定・進捗も直して commit。

## 4. 担当の割り当て

- 割り当ての前に、担当（や他のセッション）が何を持っているかを確かめる。merge の前に branch の中身を確かめる。
- worktree は main から新しく作る（古い worktree を使い回さない）。`build/` に main の tree を symlink しない（2026-11-12 ユーザー: build system の作り直しで LLVM の build も別物になった。symlink した `build/llvm-source` を worktree の build が上書きした事故、[BUG-420](bugs/BUG-420.md)）。toolchain は worktree の build system が自分の `build/` に入れる（cached の toolchain と LLVM の source の展開）。`chmod 600 plan/tmp/guest/id_ed25519`。
- サブエージェントの起動は番号の小さい担当を優先。上限に当たれば番号の大きい担当の配下を止める。
- 返却した担当に message を送らない（再開して同じ worktree に書き手が 2 つになる）。続きは新しい起動で。
- 前提が変わったら、動いている担当に訂正を重ねて送らない。止めて記録（台帳・phase.md）を直し、記録を参照させて起動し直す。
- 担当の成果は、深刻な問題が無ければ main に merge する（ユーザーは main を試す）。merge の後は出力を読み、親が 2 つか確かめてから記録する。

## 5. ユーザーが不在の間・手が空いた時

- **不在の間の自律実行**を指示された時: 判断が要る Phase は uncleared・止めにして理由と要る判断を記録し、問いはメッセージに書くだけ（クリックの問いにしない）。担当は別の Phase に移る。設計だけ進められる WS は設計を、実装できる WS は実装を、試験できれば試験も。
- **手の空いた担当**は、残っている WS の Phase を試験なしで実装だけ進めてよい（build warning 0 と host の試験まで）。Phase は「実装済み・試験未実施」と記録し cleared にしない。branch は試験の後に merge。

## 6. 記録の書き方の補い

- 状態は本体（phase.md → ws.md → [workstreams-open.md](workstreams-open.md)、ticket → Bug Board、割当 → queue.md・registry）を同じ commit で直す。
- master.md の「今の状態」の block は丸ごと置き換えてよい（今の事だけ、経緯は書かない）。
- 使用量が少ない時は、計画の一歩ごとに commit する。
