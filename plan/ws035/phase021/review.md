# ws035-p021 敵対的レビュー: audioフレームワークと `/dev/dsp` の設計

対象は [audio-design.md](../audio-design.md) の初版。
**7件を指摘し、6件を設計へ反映、1件を制限として記録した。**

## R1: 再生の空きを `position()` だけで数えると、1周ぶん多く見える（重大）

初版の §4.4 は、`position()` が返すリング内 offset を前回と比べて巻き戻りを検出し、
64 bit の総量へ足し込むとした。**割り込みが 1 周ぶん遅れるとこれが破綻する。**

`fragment_bytes × fragment_count` = 32 KiB のリングで、48 kHz・S16・2ch なら 1 周は約 170 ms である。
アプリが 200 ms 止まると、hardware は 1 周以上進んでいるのに offset は小さい値へ戻っているだけで、
巻き戻りは 1 回しか見えない。総量は 1 周ぶん少なく計算され、**空きが実際より小さく見える**。
書く側は待たされ続け、音は無音のまま流れる。

より悪いのは録音側で、同じずれは**空きが実際より大きく見える**方向にも起こりうる。
`position()` を 2 回読む間に 1 周ちょうど進むと巻き戻りが検出できず、
「まだ読んでいないデータ」として**上書き済みの領域を読む**。

**対応**: 総量の前進を `position()` の差分だけで決めない。
**割り込みの回数を一次の情報にする**。`drv_audio_interrupt()` は fragment ごとに来るので、
呼ばれた回数 × `fragment_bytes` が hardware の進んだ量の下限になる。
`position()` はその中での端数を埋めるためだけに使い、
**総量が割り込み由来の下限を下回らないようにする**。
割り込みが落ちた（取りこぼした）場合に備え、`position()` の offset が
「割り込み由来の総量」から見て 1 fragment 以上先なら、その差も足す。
設計へこの規則と、どちらが権威かを明記する。

## R2: `drv_audio_interrupt()` から waitq を起こす文脈が書かれていない（重大）

`waitq_sleep()` は `struct spinlock *condition_lock` を取り、`observed` の世代と突き合わせる。
つまり**条件の更新と世代の前進は、その spinlock の下で行わねばならない**。
初版は「`drv_audio_interrupt()` が位置を更新し、waitq を起こす」としか書いておらず、
どの lock の下で位置を更新するのかも、割り込み文脈で取ってよい lock なのかも決めていない。

`read()`/`write()` は copy の間 sleep しうる（user memory へのアクセス）。
その間ずっと spinlock を持つことはできない。

**対応**: 設計に次を決める。

- 位置・計数・世代を守るのは**1つの spinlock**（`device->lock`）。
  割り込み文脈から取れるよう、この lock の下では copy も割り当ても行わない。
- `read()`/`write()` は lock を取って「どの範囲を copy してよいか」を決め、
  **lock を落としてから copy し**、また取って位置を進める。
  copy 中にその範囲を hardware が触らないことは、
  リングの空き計算が保証する（再生なら hardware はまだそこを読んでいない）。
- `drv_audio_interrupt()` は lock を取り、位置と計数を更新し、`waitq_wake_all()` を呼んで落とす。

## R3: 「lock を落としてから copy」は再生の上書きを防げるが、録音では防げない（重大）

R2 の段取りは再生では正しい。**録音では正しくない。**
録音で `read()` が「hardware が書き終えた範囲」を copy している最中に、
hardware がリングを 1 周して**その範囲を上書きしうる**。
lock を落としている間は誰も止められない。

**対応**: 録音の copy 後に**もう一度位置を確かめる**。
copy し終えてから lock を取り直し、その間に hardware が copy 対象の範囲へ入っていたら、
**その `read()` を捨てて overrun を 1 増やし、読み直させる**（copy したデータは返さない）。
壊れた音を返すより、落としたと言う方がよい。
このやり直しの規則を設計に書く。

## R4: `GET_DELAY` の定義が無い（欠落）

初版は「今書いた音がいつ鳴るか」を返すとしか書いていない。
**どこからどこまでの遅延なのかが決まっていない**と、p019 が時間へ直せない。

**対応**: `GET_DELAY` は
**「今この瞬間に `write()` したデータが鳴り始めるまでに、hardware が運ぶべき byte 数」**、
すなわち「書き込み位置 − 再生位置」と定義する。
リングに溜まっている未再生の量そのものである。
hardware の内部 FIFO や codec の遅延は含まない（kernel は知らない）。
その旨を UAPI のコメントと設計に書く。

## R5: 音量の減衰を「書き込み時」に行うと、音量を変えても既に書いた音に効かない（設計の穴）

§4.5 は、`set_volume` の無い driver では再生データを書き込むときに減衰させるとした。
リングには最大 170 ms ぶん溜まっているので、**音量を下げても 170 ms は大きいまま鳴る**。
音量つまみとしては使いものにならない。

**対応**: この場合の音量は**フレームワーク側の減衰ではなく、`SET_VOLUME` を `ENOTSUP` で断る**。
`GET_VOLUME` は「音量調整なし」を表す 100・100・muted=0 を返す。
audiod（p009）が自分のミックスの段で音量を扱えばよく、そこならまだ書いていないデータに効く。
kernel が中途半端に効く音量を持つと、audiod が二重に減衰させる。
QEMU の intel-hda には codec の音量があるので、p007 は `set_volume` を実装する。

## R6: 「最初の `write()` がリングを半分以上埋めた時点で `start()`」は、短い音を鳴らせない（設計の穴）

§5.2 の規則では、リングの半分（約 85 ms）に満たない音を書いて `close()` すると、
`start()` されないまま `DRAIN` に入る。**何も鳴らない**、あるいは drain が止まらない。

**対応**: `start()` の条件を「リングの半分が埋まった」**または**
「`DRAIN` が呼ばれた」または「`close()` された」のいずれかにする。
書かれた量が 1 fragment に満たない場合は、末尾を無音で 1 fragment ぶんまで埋めてから動かす。
hardware は fragment 単位でしか進められないためである。

## R7: 2つ目の open を `EBUSY` にすると、audiod の再起動で音が出なくなりうる（運用）

§5.3 は 1 つの開きだけを受けるとした。audiod が異常終了して再起動するとき、
前の fd がまだ閉じ切っていなければ 2 つ目は `EBUSY` になる。
fd の解放は process の後始末に依存するので、**再起動が数秒間失敗しうる**。

**対応**: 設計へ「`EBUSY` は close で必ず解ける」ことと、
**close は `stop()` が hardware の停止を確かめるまで戻らない**ことを明記する。
`struct drv_audio_ops` の `stop` の契約に「hardware がリングを触るのをやめるまで戻らない」と
既に書いてあるので、そこに依存してよい。加えて、
`DRAIN` 待ちの `close()` に**上限（既定 2 秒）**を置き、超えたら捨てて止める。
そうしないと、hardware が壊れたときに close が返らず、fd が永久に解放されない。

## 反映しなかった指摘

無し。R5 は「フレームワークの減衰をやめる」という形で設計を変えたので、制限 §8-5 を書き換えた。
