## 問題と到達点

ユーザーから、現在の PC-98 は QEMU でも動作しないと報告された。
停止位置・原因は未確認であり、リファクタリングが直接原因とはまだ断定しない。
現行のソース構成を維持して原因を特定・修正し、通常イメージからログインして
シェルを操作できる状態へ戻す。ビルド成功だけでは完了としない。

基準資料は [Claude の作業記録](../../refactor-claude-1.md) と
[現在のコーディング規約](../../coding-style.md)。区間マーカー撤去後の実ソースを
基準とし、旧マーカー抽出や古いファイル配置へ戻すことを修正方針にしない。

## 対象と境界

- PC-98 のビルド列挙、リンク、loader/handoff、HAL、割込み、console/input、
  IDE/disklabel、root mount、VM、init に至る起動経路。停止位置に応じて対象を絞る。
- 原因に直接関係する共通コードと、現行構成に追随するために必要な検証 fixture。
- 無関係な機能追加、VM の再分割、全ホストテストの一括修復、他機種 bring-up は
  本 Phase に含めない。必要な追加デグレは別 Phase として記録する。
- 既存のユーザー・Claude の変更を保持し、履歴への一括巻戻しはしない。

## 手順

1. 実行開始時の差分、設定、コンパイラ、QEMU の実体と版、イメージのハッシュを保存する。
   古い成果物と現行ソース由来の成果物を区別する。
2. 維持対象の `build/qemu-pc98/build/qemu-system-i386` を使う既存 runner を確認する。
   基準構成は `-M pc9821,pegc=off,coregraph=on -cpu 486 -smp 1 -m 64M`。
   通常の PC/AT QEMU で代用しない。必要な環境が欠けていれば不足を明記する。
3. `make -j16 ZEDBSD_CONFIG=config/ci/config-pc98.mk` で通常成果物を生成し、
   disposable image で失敗を再現する。debugcon、monitor、PC-98 VRAM の復号結果を保存し、
   loader → kernel entry → root mount → init → login の最後の到達点を確定する。
4. 必要に応じて限定的な診断出力・GDB を使い、ソース列挙漏れ、初期化順序、
   統合に伴う状態や型の変化、i386/486 固有条件などを証拠に基づき切り分ける。
   比較可能な旧成果物があれば再現条件を揃えるが、その存在を必須としない。
5. 原因に対応する修正を現行の構成・規約で行う。再発を捉える最小の検証を用意する。
6. 下記の受け入れを実行し、診断専用変更を除いた通常成果物でも再確認する。
   原因、修正、実行コマンド、結果、残件を `results.md` に記録し、M/W/P を同期する。

## 受け入れ

| R02 | overlay root 起動 | 通常イメージで `login:` に到達し、panic・reset loop がない |
| R03 | native UFS root 起動 | 現行形式の通常イメージで `login:` に到達する。旧 runner の `init: system running` だけでは合格にしない |

## 実行と証拠

Queue 選択時の時間枠案は、従来同様 90 active minutes ごとの進捗・証拠確認。
この時間を超えたこと自体を合格理由にしない。q123 は履歴として終了し、実行承認済み q124 で実施する。

再利用テストは `plan/ws025-io-memory-cache/tests/`、一時資料は同 WS の
`temp/p032-*` に置く。ビルド・テスト・QEMU は直列実行し、`make -j16` を使う。
amd64 は `qemu-system-x86_64` を使う。commit、aggregate `make check`、
`.internal/` の参照は行わない。実機は今回の完了条件ではない。

R01–R09 の実行結果と原因・修正の対応が確認できたときに completed とする。
環境制約や未解消の失敗は未完了として記録し、残りの機能 Phase へ先送りしない。
