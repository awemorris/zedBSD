Handling: 未定（kernel の TCP か virtio-net・slirp の経路。BUG-222 の USB LAN とは別の interface）

## 2026-10-14 関係の疑い（T1-597、P2 の解析）: 起動の直後に SSH の接続が命令を走らせずにすぐ閉じる

- 同じ物とは断定しない（BUG-281 は止まってから戻る、こちらは止まらずにすぐ閉じる。ssh の status は 255 と推測、LogLevel=ERROR で何も出ない）。
- T1-597（QEMU、tree 24208099f、config-amd64-users.mk）で、`guest.py wait` が通った後の約 1 分、admin-p026 と user-commands-guest の request が guest に届かず空の答えで FAILED。guest の /var/log/messages には最初の 2 行と、約 1 分後からの行だけ。証拠: T1 の worktree の build/review/t1-597/（admin-run2.txt・uc-run2.txt・out2b/messages.txt）。

## 2026-10-14 T1-600（QEMU、tree 79562b496、config-amd64-users.mk）: SSH の命令の答えが 120 秒空のまま、guest で走った形跡無し

## 2026-10-31 P2（q1761-i01）: source の読みと、再現に要る物

- 再現はしていない。guest の SSH は openssh の package を要るが、この Queue は host の / の空きの制約で package の build が要る image を作らない（Q1 の指示）。
  serial の console だけの guest では SSH の session の止まりを観測できない。bug-analyzer も同じ理由で再現できないので起動していない。
- 止まりの長さが TCP の timer の段と合う（推測、未確認）:
  - 再送の timer（`src/kern/net/tcp.c`、初期 1 s、倍々、上限 `TCP_RETRANSMIT_TIMEOUT_MAX` 60 s）: 1+2+4+8+16+32 = 63 s、続けて 64 s 相当で約 127 s。
    T1-515 の約 60 s・T1-513 の約 120 s と合う。止まって戻る（切れない）のも、何本かの segment が続けて落ちて再送の間隔が伸びた形に合う。
  - persist の timer（5〜60 s）と、読んだ後の window の update（`tcp_send_ack_news`、送れなかった時は後で再び送る）も候補。
  - guest の NIC は QEMU の `usb-net`（CDC-ECM、`plan/tools/guest/guest.py`）。frame が落ちるならこの driver か slirp の側。
- 次の再現の採取の案（SSH の image が作れる時に）:
  1. 止まりの前後で guest の `net.tcpstats`（`retransmit_segments`・`segment_send_failures`・`send_refused`・`receive_refused`・`window_updates_out`・`zero_windows_*`）と
     `ifconfig ue0` の数を取る（serial の console から。SSH が止まっていても取れる）。
  2. QEMU の `-object filter-dump,netdev=net0,file=…` で slirp と guest の間の frame を取り、止まりの間に再送の間隔が伸びているか、どちらの向きが落ちているかを見る。
  3. 再送の段なら、落ちる側（CDC-ECM の受信の bulk の再装填、送信の完了、packet の pool）を調べる。
- （同日、Q1 が SSH の image を許可したので、下で再現を試みた。）

## 2026-10-31 P2（q1761-i01）: 今の main の QEMU で再現しない、BUG-369 が原因の見込み

image: main 4fd802a15 の tree（BUG-308 の直しの ufs.c を含む）、`plan/ws221/tests/config-amd64-tcp.mk`（SSH の guest、sysctl・tcp-perf）、BUILD は /tmp。QEMU は KVM、NIC は usb-net（guest.py の既定）。

- `plan/tools/ssh-rtt/qemu-ssh-rtt.sh`（新しい SSH の接続で `true` を 1 回ずつ、filter-dump の pcap、net.tcpstats の前後）:
  - `ROUNDS=100 LIMIT=5`: **100 回とも 0.29 s 以下、PASS**（23 回の接続で pcap に再送 1 つ、止まりに繋がらない）。
  - `ROUNDS=40 LIMIT=5 WRITE_IOPS=20`（guest の disk の書きを 20 IOPS に絞る、遅い disk の再現）: **40 回とも PASS**。
- 長い転送（一時の script、64 MiB の put・get と 20 回の `ifconfig`・`ls` を 1 組に 30 組、各段の時間、20 s 超を遅れとする、filter-dump、net.tcpstats）:
  - put の中央値 12.8 s・最大 35.9 s、get の中央値 13.0 s・最大 27.1 s、命令の中央値 0.29 s・最大 0.33 s。60〜120 s の止まりは無し。
  - 20 s 超は最初の 5 組だけ（put 1 回・get 3 回、get の 2 回は host の側の受け取りの失敗）。この時間に host の /tmp（tmpfs）が満杯になり（Q1 の観測）他の担当の QEMU も重なっていた。6 組目以降は全部 16 s 以下。
  - pcap は最初の 158 s 分だけ残った（tmpfs の満杯で書けなくなった見込み）。その範囲の frame の最長の間隔は 3.9 s。
  - net.tcpstats の後: `packet_alloc_failures=0`、session の `retransmit_segments=0`・`segment_send_failures=0`。
- 見立て: T1-597・T1-600 の形（SSH の命令が guest で走らず、guest の /var/log/messages の行が約 1 分抜ける）は、BUG-369（syslogd が 2 秒ごとの fsync の間に 1 本の loop で止まり、
  syslog() を呼ぶ sshd もそこで止まる。2026-10-30 に直り main e1c714fb5、この tree に入っている）と同じ形。T1-513・T1-515 の時期の image（10-10）の syslogd が同じ形だったかは未確認。
  当時の UFS の fsync は BUG-307 の直し（10-14）の前で遅かった。
- 状態の案: **closed**（今の main で再現しない。BUG-369 の直しで説明が付く見込み、確定ではない）。再び起きたら、上の道具の net.tcpstats と pcap を添えて reopen。
