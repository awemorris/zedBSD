# BUG-400: storage-test の「short」の cookie（Max-Age）が、期限の前に送られない事がある

- 状態: fixed（2026-11-02 P5 q1918-i01、試験の側の不具合。libbrowser は変えていない。確かめは下の「確かめ」）
- 発見: 2026-11-02 06:58 Q1。main で `plan/ws334/tests/storage-test.sh` が時々 2 件 FAIL する（storage-test.c:250 `short=5` が header に無い、:258 record が 5 個で 6 個でない）。再実行すると PASS。
- 経緯: 最初は host の負荷で 2 秒の Max-Age が切れると見て、Q1 が Max-Age を 8 秒・待ちを 8.3 秒に広げた（af39faf94）。それでも同じ 2 件が落ちた（host の load average は 16 / 64 core で重くない）。時間切れでなく、Max-Age の期限の計算（時計の種類・単位・丸め）か、record の書き出しの順の不具合の見込み。
- 扱い: P5（q1918）。原因を突き止め、libbrowser の側の不具合なら直す。試験の側なら試験を直す。

## 原因（2026-11-02 P5）

- cookie の期限の計算は正しい。`cookie_now` は `wb_os_wall_ns`（CLOCK_REALTIME）の ms、Max-Age は秒 × 1000 を足し、`expires <= now` で切れる。単位・丸め・比べ方に誤りは無い。2 件の FAIL は、「short」が本当に（壁の時計で）切れた結果だった。
- 試験は「short」を set.html の頁の前に置いていた。頁の script の `localStorage.setItem` は、その origin の localStorage を読む（`wb_storage_queue_read`）。queue は順に進むので、読みは先に積まれた cookie の record の書き込み（max・expires・both・short・replaced・script の 6 個と replaced の削除）が終わるまで待つ。files の backend は record ごとに fsync する（`wb_os_file_replace`）。
- disk が遅いと（他の build・image の作成・`sync` が同じ disk に書いている時）、この待ちが Max-Age を越え、header を作る時（cookie_pairs）に「short」は切れていて、jar から外れ、record も消える。それで :250 と :258 の 2 件が一緒に落ちる。host の CPU の負荷とは関係が無く、Max-Age を 8 秒にしても disk の待ちが 8 秒を越えれば同じに落ちる。
- 証拠:
  - main の FAIL の run（build/tmp/ws334-storage.run.byiNp0）の server.log では set.html から get.html まで 19 秒（PASS の run は 9 秒 = 8.3 秒の sleep と少し）。set.html の応答の後に約 10 秒が増えていた。
  - 頁の各段の時刻を取る試験の写し（build/tmp/p5-bug400/src/storage-test-t.c）: 静かな disk では頁は 0.09 秒、12 回とも PASS。fsync を 1 回 1.5 秒遅らせる LD_PRELOAD の shim を付けると、頁の load が 9.0 秒（6 回の fsync × 1.5 秒）かかり、同じ 2 件が FAIL した（再現）。

## 修正（2026-11-02 P5）

- `plan/ws334/tests/storage-test.c` の test_cookies: 「short」の cookie を頁の後、header の確かめの直前に置いた。その間に storage を待つ物は無い（cookie の書き込みは queue に積むだけ、header は jar を読むだけ）。Max-Age を 2 秒、待ちを 2.3 秒に戻した（disk の速さに依らないので広げる理由が無くなった）。record の数の comment に頁の cookie を足した。
- libbrowser は変えていない。queue の順の待ち（頁の localStorage の読みが先の書き込みの後になる）は設計どおりで、壊れてはいない。

## 確かめ（2026-11-02 P5、host、worktree agent/p5-ws334d）

- 再現（直す前の試験、各段の時刻を取る写し、fsync を 1 回 1.5 秒遅らせる shim）: 2 回とも :250 と :258 の同じ 2 件が FAIL（build/tmp/p5-bug400/slow1・slow-old2）。shim 無しでは 12 回とも PASS（loop2）。
- 直した試験（同じ shim）: 3 回とも 222 checks の全てが PASS（slow2・slow3 の 1 回目・slow4）。slow3 の 2 回目は test.log が空のまま終わった。始めから約 4 分で止まっており、P5 の loop の 300 秒の上限に cache の部分（fsync が多い）で届いて止められた見込み（終了の code は取っていない。check の FAIL の行は無い。上限を 1200 秒にした slow4 は PASS）。
- `PORT=18471 sh plan/ws334/tests/storage-test.sh plain` を 30 回続けて流し、30 回とも PASS（222 checks、build/tmp/p5-bug400/script30.txt）。その中の host-build plain（plan/ws074/tests/host-build.sh）は warning 0。
- libbrowser を変えていないので、WS074 の stage1 と cross-build.sh は流していない（未実施。storage-test.c はどちらにも入らない）。
