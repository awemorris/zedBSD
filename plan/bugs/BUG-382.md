# BUG-382: 5330 の NVMe の p7 を discard して起動した直後に、mkfs が "no registration" で失敗する（約 2 分後なら通る）

- 状態: closed（2026-11-01 06:53 Q1 の判定、main ecad7fc74。ユーザーから、P2 をラップアップし BUG-382 の直しを main に入れる、という趣旨の指示を受けた。5330 で 5 回の起動と 268 回の繰り返しで失敗 0（直す前は 110 回中 83 回失敗）。QEMU の amd64 の起動の確かめは未実施）
- 発見: 2026-11-01 P1（WS299 の 5330 の計測、q1788、main 82c6ef325 の image）。`plan/ws299/tests` の p7fswrite の段で、p7 の discard と起動の直後に
  2 回 `mkfs failed: no registration`。起動の約 2 分後に手で流すと通り、script の 3 回目（q1788-Z4）も通った。
- 疑い（未確かめ）: discard の後、NVMe の名前空間・区画の登録（partition の probe か device の登録）が起動の後しばらく終わっていない、または discard の完了を待たずに次へ進む。
- 影響: 5330 で起動の直後に新しい区画に file system を作れない事がある（間欠）。

## 原因（2026-11-01 P2、q1811-i01）

- "no registration" は `plan/ws299/tests/bench-zedbsd.sh` が出す行で、mkfs の最初の（断る）実行が `registration=` を出さなかった、
  つまり open・BLKGETINFO・BLKRESERVE のどれかが失敗したという意味。P1 の 2 回の失敗の log は残っておらず errno は不明
  （bench-zedbsd.sh は P1 の直しの後は mkfs の出力も出す）。
- 区画の登録の遅れは否定: dmesg で nvme0n1 の 7 区画は root の mount の前に同期で登録されている。discard は Debian の
  `blkdiscard`（同期）で、その後に reboot が挟まるので、zedBSD の側で discard の完了を待つ物は無い。
- 再現した仕組み: BLKRESERVE（`src/kern/devfs.c` block_reserve → `disk_admin_begin` → `disk_admin_idle`）は、区画の予約でも
  物理の disk（nvme0n1）全体の `d_inflight`（転送中の要求）と `d_cache_users`（cache の利用者）が 0 でなければ EBUSY を返していた。
  root（p5）・swap（p6）の I/O・file の読み・page-in・先読みの job・sync の flush がその瞬間に一つでもあれば、p7 の mkfs が
  「Device or resource busy」で断られる。起動の直後は I/O が多く、2 分後は静かなので通る、という観察と合う。
  P1 の失敗の瞬間に何が p5 で動いていたかは確かめていない（log が無い）。

## 再現（5330、`plan/bugs/BUG-382/repro-5330.sh`・`mkfs-probe.sh`）

1 cycle = Debian で p7 を discard → BootNext で zedBSD → SSH が答えたらすぐ（電源の入れ直しから約 16 秒）mkfs（bench と同じ、
断る実行 → FORMAT）→ 断る mkfs を 1 秒ごとに LOOP 秒。LOAD=1 は同時に /root（p5）へ 8 MiB の dd と sync を繰り返す。

| kernel | 条件 | cycle | 最初の mkfs | 断る mkfs の失敗 |
| --- | --- | --- | --- | --- |
| 元（p4 にあった物） | 負荷なし、LOOP=120 | 3 | 3/3 通る | 0/342 |
| main 32b00f9bf（82c6ef325 と kernel の source は同じ） | `nvme-bench-5330.sh zedbsd … p7fswrite ×3`（P1 と同じ手順: fstrim、60 秒の休み、30 秒の settle、scp） | 3 | 3/3 通る | （loop なし） |
| 元（p4 にあった物） | LOAD=1、LOOP=60 | 2 | 2/2 通る | **83/110**（全て EBUSY） |
| 直した kernel（build/k1、sha256 b781b6b63ae6f4ce…） | LOAD=1、LOOP=60 | 5 | 5/5 通る | **0/268** |
| 直した kernel | LOAD=1、LOOP=20、NEG=1 | 1 | 1/1 通る | 0/14。p7 を別の process が開いている時・nvme0n1 全体を開いている時は今も EBUSY（正しい拒否） |

P1 の条件（image を書いた直後の最初の起動を含む）の完全な再現はしていない: P1 の手順の p7fswrite ×3 は直す前の kernel でも通った。

## 直し（2026-11-01 P2）

区画の予約で、重なる範囲の物だけを見る（`docs/reference/block-administration.md` の「重ならない兄弟の I/O は使える」に合わせる）。

- `src/kern/disk.c`: 物理の disk ごとに転送中の要求の list（`d_inflight_head`、registry lock の下で admission の時に繋ぎ、完了・
  dispatch の失敗で外す）。`disk_admin_idle` は対象の区画の物理の範囲に重なる転送（flush を除く）がある時だけ EBUSY。
- cache の admission を、入ってきた disk ごとにも数える（`d_cache_entries`、入ってきた区画も pin）。`disk_admin_idle` は対象・
  物理の disk・重なる alias の admission だけを見る。admission の token は入ってきた disk になり（`disk_cache_acquire`・
  `disk_direct_begin`）、物理の disk は `disk_cache_leaf(token)` で引く。
- `src/kern/writeback.c`・`readahead.c`: `writeback_domain_acquire` が token と物理の disk の両方を返し、worker・job は物理の
  disk を識別に、token を解放に使う。`src/kern/devfs.c` は変数の名前だけ。
- 物理の disk 全体の予約（diskpart の BLKRESERVE）と区画の reload の検査は変えていない（全体が重なるので今まで通り全部を見る）。
- HAL の API・mkfs は変えていない。
