# BUG-308: UFS の journal で、held の content が seal の後に home へ書かれるので、commit の間だけ再利用した block が消した file の中身を見せる窓がある

- 状態: **resolved の案**（2026-10-31 q1761 P2、案 A、QEMU）。以前: reproduced / tracking（2026-10-14 Q1: BUG-307 の T1-615 の試験 D の 1 回目の写しで窓を観測、下の「証拠」）。以前: unknown / tracking（2026-10-14 Q1 登録、BUG-307 の review-1 の「既存の問題」、今回の回帰ではない）
- 内容: `ufs.c` の j3 の seal の後（`j3_finish_commit`）に held の content を home へ書くので、再利用した block が commit の短い間だけ、消した file の中身を見せうる（推測、review-1）。fsync が戻った後には起きない。
- 次: ベータ3 で調べる。再現の試験は BUG-307 の T1 の試験 D（消した file の block の再使用の直後の fsync）が近い。
- 関連: BUG-307、BUG-163。

## 証拠（2026-10-14、bug-analyzer、QEMU）

- T2 の worktree の `build/t2-307/snap-D.img`（fsync の途中で止めて写した volume）: `rm /jour/old && cp /tmp/new /jour/new && sync /jour/new` の commit（seq 2）が seal 済みで metadata の home は書けているが、held の content の home の書き出しが途中。`/jour/new` は block 36 の後半〜1023 が old の中身（replay の後も同じ、`UFS OK`）。この瞬間に crash すると、new が消した file の中身を見せる。fsync が戻った後の状態ではない。
- 解析の script: 同じ dir の `an/extract.py`・`an/journal.py`。

## 2026-10-31 P2（q1761-i01）: 原因の確認（source）と直しの案、判断待ち

### 原因（source の読みで確定、`src/drivers/fs/ufs.c`）

- `j3_write`: content（file の中身）の書き込みは普段 journal の外の遅延書き込み。ただし、走っている transaction か閉じた transaction が free にした block
  （`j3_content_freed`、`freed`・`closed_freed` の集合）に落ちる content は **held**（cache に pin するだけで slot に写さない、`j3_range_add(..., hold=1)`）。
  free が durable になる前に新しい中身が home に出て、crash で元の持ち主に block が戻った時に新しい中身を見せるのを防ぐため。
- `j3_finish_commit`: `j3_commit_seal`（descriptor と commit record を durable に）の **後** に、held の range を `ufs_buf_writeback_range` で home へ書く。
  replay は held の range を知らない（slot に中身が無い）。
- よって seal が durable になってから held の home が書き終わるまでの間に crash すると、replay の後の volume は「新しい file の inode が再利用の block を指す」
  metadata と、その block の **前の持ち主（消した file）の中身** を持つ。T1-615 の D の写し（ticket の「証拠」）がこの状態。
  allocator の `zero_new_block` が新しい block に書く 0 も同じ held の content なので、0 にした後に書く前の段でも同じ窓がある。
- 逆向きの窓は既に塞がれている（held にするのはそのため）。free の集合が半分を超えて held にできない時（`j3_freed_add` の注記）は、逆向きの窓が残る（既知、今回は触らない）。

### 直しの案

| # | 内容 | 良い点 | 費用・危険 |
| --- | --- | --- | --- |
| A | held の content を slot に写して log する（metadata と同じ扱い。replay が home に書く）。`j3_room` で payload を数え、1 回の書き込みが payload より大きい時だけ今の held に戻す | `j3_write`・`j3_room`・`j3_range_add`・`j3_finish_commit` の中で閉じる。窓が無くなる | 消した直後の block への書き込み（上書きの保存、`rm` と `cp`、build の出力の作り直し）の中身が journal を 2 度通る。payload が埋まると `j3_write` が mount の lock を持ったまま commit する（BUG-135 で減らした待ち）回数が増える |
| B | allocator が durable でない free の block（`freed`・`closed_freed`）を選ばない（ext4 と同じ）。空きがそれしか無い時は commit してから選び直す | held が普段は起きなくなり、journal の量も増えない | allocator が複数（`allocate_block_compat`、run の allocator `allocation_run_*`、xattr、journal の image）あり全部に要る。満杯に近い volume で commit の待ちが入る。変更が広い |
| C | 今のまま（fsync の後には起きない窓として受け入れ、文書にする） | 変更なし | 消した file の中身が別の file に見える窓（情報の漏れ）が残る |

- P2 の推奨は A（範囲が狭く、窓が確実に消える。費用は消した直後の block への書き込みだけ）。性能の費用（journal の量と mount の lock の下の commit）を受け入れるかは判断が要る。
- 確認の方法: A・B とも電源断の試験（`plan/tools/ufs/crash-test.sh`、T1-615 の D）と性能の比較（消してから書く繰り返し）が要る。
  どちらも SSH の guest image（openssh の package）を使う。この Queue は host の / の空きの制約で package の image を作れないので、実装と試験は次の Queue で。

- 状態: tracking（原因は確定。直しの方式の判断と、SSH の image を作れる環境が要る）。

## 2026-10-31 P2（q1761-i01）: 案 A で直した（Q1 の判断）、QEMU で窓が消えたことを確認

- 判断: 同日 Q1 が案 A（held の content を slot に log）を技術の判断として選んだ。
- 直し（`src/drivers/fs/ufs.c` の `j3_write` だけ、commit d40d9bbb0）: durable でない free の block（`freed`・`closed_freed`）に落ちる content は、
  metadata と同じく pin して slot に写す（log）。replay が home に書くので、seal の後に crash しても新しい中身が戻る。
  1 回の書き込みが slot の payload より大きい時だけ従来の held（写さずに pin、seal の後に cache が home へ）に戻す。
  file の書き込みは allocation の run（16 block まで）ごとなので、普通の volume では held に戻らない。
- build: amd64・rpi4 の vmunix、warning 0（rpi4 は `arm64 vmunix check: PASS`）。`plan/tools/style-check.py` は変えた行で違反 0。
- 試験（QEMU、KVM、SSH の guest、`plan/ws221/tests/config-amd64-tcp.mk`、BUILD は /tmp。修正前 = main 4fd802a15 の ufs.c、修正後 = d40d9bbb0。一時の script）:
  - 窓の試験（BUG-307 の試験 D を seal に合わせた形）: 512 MiB の新しい volume（v3 journal、16 MiB）に 8 MiB の `/jour/old` を書いて sync。
    gdb で `j3_finish_commit` の seal の直後（commit record の `bio_flush` の後の命令）に hardware breakpoint を置き、止まるたびに volume の file を写す。
    その間に `rm /jour/old && cp /tmp/new /jour/new && sync /jour/new`。写しを別の起動で 2 台目に付けて mount（replay）し、`/jour/new` を host で 8 KiB ごとに new・old と比べた。
  - 修正前: **2 回とも窓を再現**。ある写しで `/jour/new`（8 MiB）の 1024 block 全部が消した `/jour/old` の中身（他の写しは new のとおり）。
  - 修正後: **3 回とも消した file の block は 0**（seal の直後の写しは new のとおりか、まだ途中で書かれた所だけ）。最後の volume は 3 回とも `UFS OK`。
- 速さ（消してから書く形、10 回の中央値、`time` の分解能 10 ms、guest の disk は host の page cache の上）と、作業の volume への書き込みの量（QMP の blockstats）:

  | 形 | 修正前 | 修正後 |
  | --- | --- | --- |
  | 8 MiB: `rm old && cp new && sync new` | 0.060 s、10 回で 163 MiB | 0.095 s、10 回で 236 MiB（約 7 MiB/回が journal を 2 度通る） |
  | 8 MiB: 新しい block に同じ書き込み（比べ） | 0.030 s、164 MiB | 0.030 s、164 MiB |
  | 32 MiB: `rm old && cp new && sync new` | 0.170 s、647 MiB | 0.170 s、652 MiB |
  | 32 MiB: 新しい block（比べ） | 0.100 s | 0.125 s |

  8 MiB の形では消した直後の block への書き込みが約 1.6 倍の時間・書き込みの量は約 1.45 倍。32 MiB の形ではほとんど log されなかった
  （free の集合が上限の半分を超え、それ以上の block は「free でない」扱いになる（`j3_freed_add` の既知の注記、逆向きの窓）か、allocator が別の block を選んだ見込み、未確認）。
- 残り・制限:
  - 32 MiB の形のように free の集合に入らない block は、今までどおり普通の遅延の書き込み（commit の前に cache が書く）。この Bug の向きの窓は無いが、逆向き（crash で元の持ち主に戻った block に新しい中身）は既知のまま。
  - `j3_write` が room の不足で途中の commit（`j3_commit_now`）をする時、同じ allocation の run の metadata が先の commit に入り content が次の commit に入る組み合わせがありうるかは、この直しでは調べていない（直す前から metadata にもある形）。design-reviewer の review を勧める。
  - 電源断の繰り返し（`plan/tools/ufs/crash-test.sh` など既存の試験）は流していない。BUG-312 の電源断 10 回（今の main、修正前の ufs.c）は別に PASS。
  - 実機は未実施。
- 状態の案: **resolved**（観測した窓は QEMU で消えた。上の review と電源断の試験は残り）。
