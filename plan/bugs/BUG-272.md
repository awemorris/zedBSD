# BUG-272: 起動時の Ctrl+Shift（C3）を loader が間欠に検出しない（12 回に 1 回）

- 状態: reproduced（QEMU、T1-214 の 1 回目） / tracking・**blocked（UAT 待ち）**（2026-10-08 P2 q914: QEMU の頻度の測り直しを T1 に、判定は 5330 の UAT）
- 起こした: 2026-10-08 P2（q910 の後、Q1 の判定「ws174-p003 は C3 の間欠を Bug に起こしてから cleared」）
- 期待: 起動時に Ctrl と Shift を押したままにすると、loader が両方を読んで C3 の動き（kmsg と login の両方を console）になる。
- 観察: T1-214（`plan/ws174/tests/run-boot-keys-qemu.sh … --ctrl-alone`、QEMU の USB の keyboard）の 1 回目で C3 だけ FAIL（Ctrl+Shift を検出せず）。変更なしの再試行では全 cell PASS。C0・C1・C2・C4 と R0 は 2 回とも PASS。12 cell のうち 1 回の不検出。
- 証拠: t1 の worktree `build/ws174-keys/t1-214/`（1 回目）、`build/ws174-keys/t1-214-retry/`（再試行）。
- 見立て（未確かめ）: 2 つの修飾 key の押下が loader の読む時より遅れて届いた（QEMU の key の送り方、または loader が 1 回しか読まない）。実機（UEFI の 5330）でも起こるかは未確認。
- 由来: [ws174-p003](../ws174/phase003/phase.md)（2026-10-08 Q1 が cleared）。
- 次の再調査の条件: 5330 の UAT で Ctrl+Shift が効かない時、または QEMU の回帰で再び出た時。直すなら loader の修飾 key の読みを一定の時間くり返す形。

## 調べ（2026-10-08 P2、q914、読みだけ）

- loader（`bootloader/uefi/boot-keys.c`）は待たない。key は 2 点だけで見る:
  - S0: `A64 UEFI ENTRY` の直後。
  - S1: config の parse の直後。
  各点で、ReadKeyStrokeEx で queue を最大 32 件読み、空なら EFI_NOT_READY と一緒に返る「今押されている修飾 key」を足す。設計どおり（ws174 の design 第 3 版、S2 は Q1 の決定で外した）。
- QEMU の試験（`run-boot-keys-qemu.py`）は修飾 key を押したままにし、0.1 s ごとに押し直して Space を叩く。押し直すのは、firmware の USB の reset の後に emulate の keyboard が押下を忘れるため（試験の注記）。
- 見立て（未確かめ）: S0 と S1 は短い間に続く。その間が OVMF の USB keyboard の再接続と次の押し直し（≤ 0.1 s）の間に入ると、queue も今の状態も空で、検出しない。C3 は修飾 key が 2 つで、押し直しの 1 回の event が大きい。実機（5330 の内蔵 keyboard は PS/2、人は押し続ける）では起きにくい形。
- 直し方の候補（判断が要る、実装していない）:
  - (a) loader の S1 で、修飾 key の状態を短い間（例 150 ms）くり返し読む。「待たない」設計と S2 を外した Q1 の決定に当たる。
  - (b) 試験の側で、修飾 key を一度押したら押し直さない形を比べる。
- 次:
  - T1: `run-boot-keys-qemu.sh IMAGE OUT --cells C3` を 5 回流し、不検出の頻度を測る（判定は記録だけ）。
  - 5330 の UAT: 電源を入れる前から Ctrl+Shift を押し続け、3 回とも kernel の text と console の login になるか見る。UAT で出なければ close の案（Q1・ユーザー）。
