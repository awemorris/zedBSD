# BUG-157: 鍵を間違えたとき「Could not join (Network is down)」と出る（5330 の AX211）

Reproduction: reproduced（S1（2026-10-03、Latitude 5330、素の USB 起動、ユーザー、[結果](../ws133/s1-results.md)））
Disposition: resolved（2026-10-08 夜 ユーザーの決定で close、Q1 の中継）
Discovery: 安定版 S1 の実機試験（[WS133](../ws133/ws.md)）

QEMU の RTL8822BU では EACCES（did not accept the key）だった（ws005-p020）。AX211 の経路で鍵の拒否が ENETDOWN として返っている見込み。読みで原因を探し、確認は実機（AX211 の passthrough は host が止まったので使わない）。

## 読みでの原因の候補（2026-10-03、q638、P1。実装していない）

鍵の拒否の分類は共通の `src/kern/net/wifi/wlan.c` の `wlan_station_report_frame` にある: message 2 を送った後（`WLAN_WPA2_STATE_MESSAGE_2_TX`・
`MESSAGE_3`）に AP の deauthentication・disassociation を受けると `EACCES`、それ以外は `ECONNRESET`。RTL8822BU（QEMU）はこの経路で EACCES になった。
AX211 の受信の経路（`ax211_pci_connection_rx_dispatch`）も管理 frame を同じ関数へ渡すので、5330 で ENETDOWN になるのは別の所で終わっている見込み。

1. **（第一候補）2 回目の試行が AX211 の recovery 中に断られる。** `userland/base/wifi/main.c` の connect は `ETIMEDOUT`・`ECONNRESET` などを
   「新しい scan で再試行できる」扱いにする（`retryable_connect_error`）。鍵が違う時に AP が deauth を送らず message 1 の再送の後に黙る、または
   deauth が driver に届かない（firmware が落とす）と、WPA2 engine は ETIMEDOUT（`wlan-wpa2.c` の fail(ETIMEDOUT)）で終わり、再試行になる。その間に
   AX211 が TX の timeout などで recovery に入っていると、`intel-ax211.c` の ioctl の入口（約 7120 行）が `recovery_pending`・`recovery_running`・
   `!runtime_active` の時に connect・status を **ENETDOWN** で断る。この ENETDOWN が networkd → Settings・system bar に「Network is down」として出る。
2. wifi の tool の待ちが station の状態 `WLAN_STATE_DOWN`（recovery の session stop・carrier down の後）を見て ENETDOWN を返す（`main.c` の
   約 1422 行）。1 と同じく、元の失敗（鍵の拒否・timeout）が後の recovery の状態で上書きされる形。
3. networkd の `acquire_managed_l3` の ENETDOWN（L2 が成功とされた後に address が無い）。L2 は鍵が違えば成功しないので可能性は低い。

直し方の方向（案）: 再試行の前に最初の失敗の理由（EACCES・ETIMEDOUT の 4-way の段階）を覚え、再試行が ENETDOWN・recovery で断られた時は最初の
理由を返す。4-way の message 1 の再送を受けた・message 3 が来ないまま timeout した、を「鍵が違う見込み」（EACCES）に分類する。
実機で見ること（S2）: kernel log の `intel-ax211: connect ioctl rejected result=50`・`recovery latched error=`、networkd の join の出力
（wifi の tool の進み: FOUR_WAY の後の終わり方）。

## 対応（2026-10-03、q641、P1）

handling: [ws005-p028](../ws005/phase028/phase.md)。共通の WLAN core の `station_retire_controlled` が close・quiesce で terminal_error を 0・state DOWN に
していたため、接続が EACCES で失敗した後に AX211 が close・quiesce に入ると、wifi の tool は DOWN・理由なしを ENETDOWN として返していた（host 試験で再現）。
close・quiesce の retire で、既に失敗した接続の理由を保つようにした。kernel の build は warning 0、`host-wlan-retire.sh` PASS（修正前は FAIL）。

上の第一候補（再試行が recovery 中の ioctl の入口で ENETDOWN になる）は、wifi の tool が networkd の machine mode では再試行しないので、そのままでは
当たらない。代わりに同じ形（後の状態が最初の理由を上書き）の共通の箇所を直した。ioctl の入口の ENETDOWN（前の操作の recovery の最中に join が来た場合）は
直していない。

### S2（実機、5330 の AX211）での確かめ方

1. 保存していない WPA2 の AP に、Settings の Wi-Fi で間違えた鍵（8 文字以上）を入れて Join する。期待: 「X did not accept the key. Check the key and
   try again.」（EACCES）。system bar の menu から同じ操作をして「Could not join (Permission denied)」系の EACCES の文言になること。
2. 「Network is down」が出た時は、SSH（有線の USB LAN）で kernel log を読む:
   - `intel-ax211: connect ioctl rejected result=50 runtime=… recovery=…` があれば、ioctl の入口の ENETDOWN（残る候補）。直前の
     `recovery latched error=` の行と合わせて、何が recovery を起こしたかを見る。
   - `intel-ax211: stopping connection generation=` の後に rejected が無ければ、wifi の tool の待ちが DOWN を見た形（この修正の対象）。修正後も出るなら
     別の経路。
3. networkd の join の出力（`net wifi join` を SSH で直接実行し、wifi の tool の進み `WIFI1 connect state=` の行）で FOUR_WAY の後の終わり方を見る。
4. 正しい鍵で join し直して接続できること（理由を保つ変更が次の接続を妨げないこと。open と connect で terminal_error は消える）。

2026-10-04 user: P1・P2・P9 への割り当て（「P1、P2はBUG-143, 053, 052, 162, 103, 129, 033, 157, 139を修正します。直す順序は任せます。」「BUG-135はFable 5.1 HighのサブエージェントP9に修正を依頼しましょう。テストは依頼しないで除外しましょう。」）→ ws005-p031（P1）。

## 対応（2026-10-04、q651、P1）

handling: [ws005-p031](../ws005/phase031/phase.md)。残りの経路を読みで探して直した（実機無し）: (1) networkd の `run_managed_connect` が join の失敗の後始末
（`wifi disconnect`）の error で join の理由を置き換えていた（AX211 は recovery の間の disconnect を ENETDOWN で断るので、鍵の拒否が「Network is down」に
なる）→ join の理由を返す。(2) AX211 の recovery の間の disconnect を EBUSY（再試行できる）に。(3) 共通 core の link loss が、既に FAILED の接続の最初の
理由を recovery の error で上書きしていた → 最初の理由を保つ（host 試験 case 4 で修正前に再現）。kernel（AX211 有効）と networkd の build は warning 0、
`host-wlan-retire.sh` PASS。確認は S2 の実機（手順は上、加えて networkd の `join failed: Permission denied; its cleanup is retried` の log）。
