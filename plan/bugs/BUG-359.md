# BUG-359: 遅い USB の mass storage で xHCI の command（Stop Endpoint）が時間切れになると、zedBSD は device を失い回復しない（root の stick なら init が動かない）

- 状態: closed（2026-10-31 Q1 の判定。2026-10-31 P4 q1753-i01、bb2b25ff3、QEMU で旧と新を比べて確かめた。main に未 merge）
- 発見: 2026-10-30 P4（q1665-i10、WS307 p011 の 6 回目 `p011.yygfuq4e`、QEMU、live の USB stick が sdc）。
- 観測（gdbstub で `klog_buffer` を読んだ、console log ではない）: xHCI の「command 15 timed out」、cancel の失敗、BOT の転送が error 17/42、root を書き込みで mount できない（clean flag の書き込みが error 42）、`/sbin/init` の exec が EIO、全 CPU が sched_idle で SSH が上がらない。
- 見立て（未確定）: host の fdatasync が中央値 1 s・最大 1.8 s（load 12〜15）の時、stick の SYNCHRONIZE CACHE が QEMU の USB を止め、guest の xHCI の command が時間切れになる。p011 の 1 回目（`p011.64jmegwb`）の SSH 無し、WS309 の P1 の 2 回の SSH 無し（p014u・p014v、host の負荷の高い時）も同じ原因の候補（未確かめ）。
- 期待: 遅い device でも command の時間切れを回復できる（endpoint の reset・device の reset と BOT の reset recovery で続ける）、少なくとも transfer の待ちが長い device を失わない。実機の遅い stick でも起こりうる。
- 回避: WS307 の試験は試験の disk と stick を `cache=unsafe` にした（installer_walk の Run.start、共有の guest.py は変えていない）。
- 未確認: 実機、xHCI の command の時間の上限の値と USB の mass storage の reset の道。
- 観測の追加（2026-10-30 P6、q1711-i01、WS307 p004 の run1 `build/ws307-test/p004.9Et1i3`（p6-ws307 の worktree）、image `build/ws307-p004/installer-image.img`（main 5aca73738 の tree）、QEMU std VGA、live の stick は sda で guest.py の既定の cache）: 同じ症状。gdbstub で `klog_buffer` を読み、stick の flush（sync-cache）で xHCI の cancel failed（42・5）、clean flag の書き込み error 42 で root が read-only、続く BOT の read が error 17、`/sbin/init` の exec が EIO（5）、全 CPU が sched_idle、900 秒 SSH 無し。stick を `-set drive.boot.cache=unsafe` にして試験を続けた。

## 原因と直し（2026-10-31 P4 q1753-i01、bb2b25ff3）

- 原因: `src/drivers/pci/pci-xhci.c` の `command_ex` は doorbell を鳴らした後の loop で、event ring を読む前に時刻を見て 5 秒を過ぎていれば break していた。QEMU の xHCI は command を doorbell の書き込みの中で走らせ、Stop Endpoint はその中で device の残りの要求（遅い書き込み・flush）の取り消しを待つ（QEMU の usb-storage の cancel は block の要求の完了を同期で待つ）。doorbell が 5 秒以上かかって戻ると、完了の event が ring（か IRQ の受け渡し）に既にあっても一度も読まずに「command 15 timed out」とし、`command_failed` が立って以後の command が全部 EIO（endpoint の reset・clear halt もできず、BOT の reset recovery が失敗し device を失う）。
- 直し: 時間が過ぎた後も ring が空になるまで読み、完了があれば成功とする（空なら今までどおり時間切れ）。実機で本当に完了しない command の扱い（CRCR の Command Abort での回復）は変えていない。
- 確かめ（QEMU、amd64、guest.py、`-drive ...,throttling.bps-write=64` の 64 MiB の USB stick を xHCI の port 5 に、`dd if=/dev/zero of=/dev/sda bs=16384 count=1`。4 KiB の書き込みが 1 つ約 64 秒で BOT の 30 秒を越え、URB の cancel で Stop Endpoint が出る。QEMU の trace の usb_xhci_ep_stop・usb_msd_cmd_cancel で Stop Endpoint を数え、guest の状態は SSH の dmesg と dd で見た）:
  - 直す前の xHCI（同じ tree で pci-xhci.c だけ bb2b25ff3^ に戻した image）: 最初の Stop Endpoint で `xhci: command 15 timed out`、`cancel failed (42 …)`・`(5 …)`、`BOT CSW error=42`・`error=17` が続き、`/dev/sda` の読みが `Device or resource busy`（ticket の症状と同じ）。
  - 直した image: Stop Endpoint 12 回で `command … timed out` 0 件、`cancel failed` 0 件。cancel の後に BOT が続き（書き込みは遅すぎて ETIMEDOUT になる）、静まった後に `dd if=/dev/sda of=/dev/null bs=512 count=8 skip=1000` が成功。
- 残り: 直した側でも cancel の後に `BOT CBW error=44`（CBW の stall）が時々出る（reset recovery で続く）。実機の遅い stick は未実施。
