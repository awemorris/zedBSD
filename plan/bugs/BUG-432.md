# BUG-432: 静的に link した program の stdout が、file への出力の時に exit で flush されない

- 状態: fixed（2026-11-14 P2、q2075-i01。QEMU x86_64 の guest で確かめた。arm64・riscv64 は sysroot の smoke link まで）
- 発見: 2026-11-13 P1（WS353 p002 の QEMU の試験の program、手で static に link）。WS299（5330 の NVMe）でも「return の時の stdout の flush」が見つかっていた（master の「Q1 が決める事」の Bug 化の候補）。
- 観測（P1、未調査）: stdout を file に向けた時、`exit`（か main の return）で中身が書かれない。
- 扱い: libc の exit の流れ（atexit・stdio の flush）を調べて直す。動的に link した program で起きるかも確かめる。

## 原因（2026-11-14 P2）

- static の program の start（`src/libc/crt/crt0-<arch>.S` の `crt0.o`。`libc.a` は system call の stub を持たず `crt0.o` が持つので、tree の試験の static の link は `crt0.o` を使う）の `_start` が、main から戻った後に `exit` でなく `_exit` を呼んでいた（x86_64 の `call _exit`、aarch64 の `bl _exit`、riscv64・armv7・i386・m68k・sparcv9 も同じ）。`_exit` は system call だけで、atexit の handler も stdio の flush も走らない。
- `exit()`（`src/libc/posix.c` の `exit`: handler → `__rtld_process_fini` → `fflush(NULL)` → `_exit`）は正しく、static でも `posix.o` の強い `exit` が link される（`stdio.c` の弱い `exit` は使われない。`llvm-nm`・`llvm-objdump` で確かめた）。
- dynamic の start（`crt1-<arch>.S`）は main の後に `exit` を呼ぶので起きない。
- stdout は terminal の時は行 buffer、それ以外は全 buffer（`__libc_init`）。なので file・pipe では全部が、terminal では最後の改行の後が失われ、どちらでも atexit の handler が走らなかった。P1 の観測の「exit」は main の return の事だった（static の `exit()` は修正前も PASS）。

## 修正

- `src/libc/crt/crt0-{x86_64,aarch64,riscv64,armv7,i386,m68k,sparcv9}.S`: main の後を `exit` に（C 7.22.4.4・5.1.2.2.3、POSIX の exit: handler を走らせ、開いている stream を flush する）。commit e818c322ef（agent/p2-bug432）。

## 確かめ（2026-11-14 P2）

- 再現の道具 `plan/bugs/BUG-432/`: `flush.c`（行と行の途中を書き、atexit の handler でさらに書き、`exit(3)` か main の `return 4`）、`ptyrun.c`（pty の上で走らせて出力を file に）、`build.sh`（static: crt0.o + libc.a、dynamic: crt1.o + libc.so、driver: clang の既定の link）、`guest-run.sh`（guest の中で 3 通り × exit・return × file・pipe・tty の 18 件と、tree の `plan/ws073/tests/p038/tls-check.c` の static を file へ）、`config-x86_64-flush.mk`、`qemu-flush.sh`（sysroot・userland・disk を作って QEMU で起動し、serial（`plan/tools/guest/serial.py`）で流して guest の結果の file を読む）。`sh plan/bugs/BUG-432/qemu-flush.sh OUT`、最後の行 `qemu-flush: PASS`。
- 修正前（main 4b5b95d98e、image 096059683d1c3a29）: 15 PASS 3 FAIL。FAIL は static の return の file（0 byte）・pipe（0 byte）・tty（19 byte、改行までの行だけ）。static の exit、dynamic と driver の exit・return は file・pipe・tty とも PASS。
- 修正後（image 3079afb8b33d7d94）: 19 PASS 0 FAIL（static の return も 31 byte の全部と status 4、tls-check-static も file に `TLS-CHECK:PASS`）。x86_64 の sysroot と試験の program の build の warning 0。
- arm64（`config/config.rpi4.mk`）・riscv64（`config/config.vf2.mk`）: `make sysroot` が warning 0 で通り、smoke（crt0.o + libc.a）の未定義の symbol は 0、`_start` が `exit` を呼ぶ事を `llvm-objdump` で確かめた。armv7・i386 は clang で assemble できる事まで。m68k・sparcv9 は今の toolchain に target が無く未確認（今の mk に build の規則も無い）。

## 残り・別件

- 未実施: arm64・riscv64 の guest での実行（QEMU・実機）、i386・pc9821 の image の build。
- 別件（範囲の外）: clang の driver の `-static`（crt1.o + libc.a）は `libc.a` に `__syscall6` などが無く link できない（`build.sh` の `flush-static-driver`、未定義 3 個）。直すには mk の `libc.a` に system call の stub を入れる事になる（Makefile・mk の変更はユーザーの確認が要る）。
- 回避が要らなくなった試験: `plan/ws333/tests/hw5330/static-tool.sh`・`thermal-static.sh`、`plan/bugs/BUG-424/netsleep/build.sh` の `fflush(NULL)` の wrapper（他の WS・Bug の物なので触っていない）。
