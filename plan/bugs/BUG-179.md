## 原因と修正（2026-10-05 P1 generation17 / q700-i01。build まで、QEMU・実機は未実施）

- 時間の内訳（source を読んで）: 2 回目の press の後、3 回目の press（triple click で窓を後ろへ、ws079-p013）を待つ `DOUBLE_CLICK_MS` = 400 ms の待ち（`shell.c` の `dock_when_due`）→ dock の animation `DOCK_MS` = 220 ms（ease-out）→ client が最大の大きさで描き直す。合わせて約 0.62 秒＋client の描画で、報告の約 0.8 秒と合う。event loop の poll は最大 10 ms なので遅れの元ではない。
- 修正（`userland/desktop/wayland/shell.c`・`zwl.h`・`objects.c`）: 2 回目の press で**すぐ dock** する（configure も同時に送る）。`DOCK_MS` を 120 ms にした（launch の animation は `LAUNCH_MS` = 220 ms のまま）。triple click は残し、2 回目の press から 400 ms 以内・8 px 以内の 3 回目の press で dock を戻して（`undock via=triple-click`）窓を後ろへ回す（`click_docked_third`）。待ちの log `GLASS dock waiting`・`GLASS double-click waited_ms` は無くなった。
- 計測の log: client が新しい大きさで描いた時に `ZWL GLASS resized surface=S docked=1 width=W height=H after_ms=N`（dock からの ms）。
- 試験: `plan/ws079/tests/zdesktop-p013.sh` を新しい挙動に直した（triple click は dock の後に undock via=triple-click と lower。double click の直後の画面に docked の色）。build（CI の amd64 の config、`build/q700/img/bin/wayland`）warning 0。style-check・OS の境界の checker PASS。
- 残り: QEMU（T1、p013 と C2・C9）、実機の UAT で 0.1〜0.2 秒の体感。
- 2026-10-05 ユーザーの方針「既存BUGはいったん保留して、新規実装を進める」で、ここで保留（差分は WIP commit 済み）。

## T1-138 の結果と調べ（2026-10-05 P1 generation17）

- T1-138: double click の 2 回目の press で dock した（bug179-docks ok）。dock の animation は 120 ms で最大の大きさに達し、その間とその後は client の古い image を送った大きさで描く（BUG-180 の `RESIZED_HOLD_MS`、最長 1 秒）。client（wltest）が dock の大きさで描いたのは 1393 ms・1304 ms 後（`bug179-drawn-within-200ms` FAIL ×2）。
- 読み: compositor は dock と同時に configure を送る（`window_configure` と `window_resized` は同じ所）。wltest は configure を受けると、次の frame で swapchain を作り直す（`follow_size` → `wltest_renderer_recreate`。Venus では image の確保が host との往復になる）。待ちの大半はこの作り直しと、新しい buffer の最初の commit（compositor の import）と見るが、まだ測っていない。
- 測るための計装を足した: compositor の `ZWL GLASS resized … acked_ms=A sent_at_ms=S`（client が configure を ack するまで、`protocol.c` の ack で記録）と、wltest の `WLTEST RESIZE … took_ms=T at_ms=B`（swapchain の作り直しの時間と始めた時刻、どちらも CLOCK_MONOTONIC）。`plan/ws099/tests/bug178-179-guest.sh` は `bug179-split.txt` に両方を残し、ack・作り直しの開始・作り直しの時間を出す。T1 に再試験を依頼（Q1 経由、wltest の新しい build を含む pen の image で）。
- 利用者の見え方: 窓の外形は 2 回目の press から 120 ms で最大になる（古い image を伸ばして描く）。中身が新しい大きさで描き直されるまでは app の再描画に依る。Keiland の app（wl_shm で描く物）と Vulkan の app（swapchain の作り直し）、QEMU の Venus と実機の i915 で違うはずなので、分けて記録する。

## T1-141 の内訳（2026-10-05、QEMU Venus KVM、wltest 16 ms）

| 区間 | 時間（configure の送りから） | 誰の |
| --- | --- | --- |
| configure の ack | 106 ms | wltest（次の event の読み） |
| swapchain の作り直しの始まり | 83 ms | wltest（frame の間の 16 ms の sleep と次の loop） |
| swapchain の作り直し | 863 ms（83〜946 ms） | **Venus**: `vkCreateSwapchainKHR`（oldSwapchain）と image の確保が host の virglrenderer との往復になる。compositor は関わらない（この間 compositor は古い image を送った大きさで描いている） |
| 作り直しの終わりから compositor が新しい大きさの画を取るまで | 約 390 ms（946〜1333 ms） | 未分解: wltest の新しい chain の最初の frame（acquire・描画・present、Venus の WSI が新しい buffer を作る）、compositor の import、acquire fence の待ち |

- 863 ms は QEMU の Venus の制約（swapchain の image の確保）と判断する。実機（i915）の swapchain の作り直しは別の速さで、UAT で見る。窓の外形は 2 回目の press から 120 ms で最大になり、それまでの app の画を伸ばして見せる（BUG-180 の hold）ので、利用者が待つのは中身の描き直しだけ。
- 残りの約 390 ms を分ける計装を足した: compositor の `ZWL GLASS resized … committed_ms=C`（client の最後の commit が来た時）と wltest の `WLTEST FRAME … at_ms=`（present の後）。試験は `bug179-split.txt` に新しい大きさの最初の FRAME も残し、「最初の present」「commit の到着」「compositor が取った時（acquire fence の後）」を出す。T1 に再試験を依頼（Q1 経由）。present から commit までが長ければ Venus の WSI、commit から取るまでが長ければ fence の待ち（Venus の描画）か compositor の import。
- 0.1〜0.2 秒の要求に対して: compositor の側で縮められる所（dock の 120 ms の animation、configure の即時の送り）は済んでいる。app の再描画の時間は app と GPU の環境に依る。

## T1-146 の内訳と結論（2026-10-05）

| 区間（configure の送りから） | 時間 | 誰の |
| --- | --- | --- |
| configure の ack | 69 ms | wltest |
| swapchain の作り直し | 826 ms（5〜831 ms） | Venus（swapchain の image の確保） |
| 新しい大きさの最初の present | 932 ms | wltest の描画と Venus |

- 試験（`plan/ws099/tests/bug178-179-guest.sh`）の判定を直した: 200 ms の判定を外し、`bug179-compositor-takes-at-once`（`after_ms - committed_ms` ≤ 20 ms）を見る。client の描き直しの時間は報告だけ。
- 実機（i915、Keiland の app と Vulkan の app）で中身の描き直しの時間を見るのは UAT（Q1 が UAT の項目に足す）。要求（0.1〜0.2 秒）に届かない時は、その app の再描画（wl_shm の app なら buffer の確保と描画）を調べる。
