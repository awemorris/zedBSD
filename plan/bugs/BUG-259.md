# BUG-259: PDF viewer の窓のリサイズのドラッグの応答が悪い

- 状態: reproduced（5330 bare metal、2026-10-08 ユーザーの UAT） / scheduled（q865、P1、2026-10-08: 修正済み・host で確認、QEMU は T1 待ち）
- 発見: 2026-10-08 ユーザーの UAT（原文）:「PDFビューアでウィンドウをリサイズでドラッグするとき、リサイズイベントごとになんらかの重い処理をしているように見えて、レスポンスが悪い。毎イベントに完全な再描画や内部リサイズ処理をしないで、200msごとに内部リサイズをするとかはどうだろう。あとは、重い処理が不要な処理であればそもそも省くとか。たぶん画面描画の矩形が変わるだけの実装で十分なのに、内部バッファを作り直してソフトウェアレンダリングをやり直している気がする。」
- 疑い（未確認）: configure ごとに内部の buffer を作り直し、PDF の page を software で描き直している。

## 次

- PDF viewer の configure・resize の経路を読み、event ごとの処理を測る。
- 直しの方向（ユーザーの案）:
  - drag の間は描画の矩形・位置だけ変える。
  - 内部の resize と描き直しは 200 ms ごと、または drag の終わりにする。
  - 要らない重い処理は省く。

## 原因（2026-10-08 P1、読んで host で測った）

- resize の event（`KL_WINDOW_RESIZE`）は main.c で 1 回の loop に 1 つにまとまり、`main_resize`（swapchain の作り直し・canvas の作り直し・`pv_app_resize`）と
  `main_frame`（`pv_draw` と present）が走る。`pv_app_resize` 自体は軽い。
- 重いのは frame: (1) 幅に合わせた倍率（fit width）が毎回変わるので、`draw_page` が見えている頁の raster を毎回 software で作り直していた
  （`pv_document_raster` → `pdf_display_list_rasterize`、event ごとに 1 頁 1 回）。(2) 頁の影と縁を、頁の矩形の全体に 1 pixel ずつ割り算付きの blend
  （`pv_canvas_blend` の `over`）で 2 回かけてから、その上を頁で覆っていた。これは resize に限らず全ての frame（scroll も）の大半を占めていた。
- host の測定（`notes.pdf`、1000x760 から 10 px ずつ 40 回幅を縮める、-O2、event ごとに resize と描画）: event 1 回 平均 14.8〜17.8 ms・最大 21〜24 ms、
  raster 40 回。動かない frame 1 回 10.8 ms。zedBSD の -Os と 5330 ではこの数倍と見込む（未測定）。

## 修正（2026-10-08 P1）

- `view.c`・`viewer.h`: `pv_app_resize` が `resizing`・`resized_at` を立て、`pv_app_tick` が大きさが `VIEW_RESIZE_SETTLE_MS`（200 ms、ユーザーの案）動かなかったら
  `resizing` を下ろし frame を求める（`PDFVIEWER RESIZE settled width= height=` の log）。その間は prefetch もしない。
- `draw.c`: resize の間、倍率が違う raster は作り直さず拡大縮小して出す（2 本指の zoom と同じ `pv_canvas_stretch`）。落ち着いたら新しい倍率で 1 回描く。
  影と縁は頁が覆わない帯と列だけに blend する（`draw_around`）。raster が頁より小さい時（最大の辺で抑えた時）は前と同じく全体にも blend して見た目を変えない。
- `canvas.c`: `pv_canvas_stretch` の列の計算を pixel ごとの割り算から余りの足し算にした（同じ結果）。
- 同じ測定で: event 1 回 平均 1.7 ms・最大 2.1 ms、raster 2 回（最初と落ち着いた時）。動かない frame 0.6 ms。落ち着いた時の frame 4.8 ms（raster 込み）。
- swapchain の作り直し（`kl_window_present_resize`）は libkeiland の共通の処理で、event ごとのまま（host では測れない。重ければ別の Bug）。

  修正の前後で 22 枚の frame（PPM）が byte で同じ。`run-host-pdfviewer-find.sh` PASS（14 件、plain・ASan）。
