# BUG-191: Settings の key のリピートの設定が実際の device の挙動に効かない（5330 の内蔵キーボード）

Disposition: scheduled（2026-10-09 T1-481 の QEMU で再現、P1 が直した、test-wait。前は resolved: 2026-10-08 夜 ユーザー「下記は実装の変更が多かったので、いったんすべてcloseします。」、Q1 の中継）

## 観測

ユーザー「Settingsのキーボードリピートは、実際にはデバイス挙動は設定できていないようである。少なくとも5330のキーボードではそう。」

## 次

- Settings の repeat の値（delay・rate）が、どこまで届いているかを経路の各段で確かめる: Settings → libkeiland の kl_settings_* → compositor の desktop.conf → compositor の key のリピートの生成（Wayland の `wl_keyboard.repeat_info` を client に送る、client 側が repeat する）か、kernel の evdev の EV_REP（PS/2 の typematic の設定）か。
- 5330 の内蔵キーボードは PS/2（i8042）。PS/2 の typematic（hardware の repeat）が kernel で出ていて、compositor・client の repeat と二重になっている、または hardware の repeat が設定と無関係に効いている疑い。USB のキーボードでも同じか確かめる。
- [BUG-172](BUG-172.md)（key のリピートが安定しない）と同じ根の可能性が高い。一緒に直す。
- 修正は P3 の Bug の順（q690 の BUG-172 と合わせる）。QEMU は T1、実機は UAT。

## 原因と直し（2026-10-05 q726、P2）

- 原因（コードの読み取りと host の試験）: PS/2 の driver（`src/drivers/platform/pcat/ps2-8042.c` の `keyboard_interrupt`）が、押し続けた key の typematic（keyboard 自身の repeat）の make code を毎回 **新しい press（value 1）** として出していた。compositor は value 2 だけを捨てるので、client は typematic の度に新しい press を受け、自分の repeat の delay を毎回やり直す。そのため見える repeat は keyboard の hardware の速さ（既定でおよそ 10 回/秒・500 ms）で、Settings の rate・delay（compositor が `wl_keyboard.repeat_info` で client に届けている。経路は読みで確認）が効かなかった。Caps Lock を押し続けると lock が切り替わり続ける副作用もあった。USB の keyboard は状態の report なので起きない（5330 の内蔵は PS/2）。
- 直し: driver が押されている key を bitmap で持ち、既に押されている key の make code は repeat（value 2、Linux の atkbd と同じ）として出す。compositor は value 2 を捨て、client が Settings の値で repeat する。kernel の console は value 2 を repeat として受ける（`console.c`）。
- 試験: `plan/ws081/tests/host-ps2-wheel.sh` に keyboard の 3 checks（押し続けた key の make が 1 2 2 0、別の key を挟んでも各 key が独立）。直しの前は FAIL 2、後は PASS。QEMU: `plan/ws081/tests/ps2-repeat-qemu.sh IMAGE`（QMP で A の down を 5 回・up、probe `ps2keys.c` が PS/2 keyboard の device を読み、press=2 repeat=4 release=2）を T1 に依頼。
- 未実施: QEMU（T1）、実機の 5330（UAT）。

## 2026-10-05 夜 ユーザーの観察（QEMU）

「QEMUではキーボードリピートの速度調整が効いていないように見える」（Windows の QEMU、usb-kbd、SDL の表示）。Q1 の見込み（未確認）: SDL の表示は host の OS の auto-repeat を key の押下の繰り返しとして guest に送るので、guest の repeat の設定より host の repeat が勝つ。guest の側で「同じ key の連続の press を repeat として捨てる」かを確かめる。5330 の内蔵（PS/2）とは経路が別。

## QEMU の SDL の観察の調べ（2026-10-06 P2、source を読んで。QEMU の試験は未実施、直しは無し）

問い（Q1）: SDL の表示が host の auto-repeat を guest に押下の繰り返しとして送り、guest の repeat の設定に勝っているか。compositor か
keyboard の経路で、guest の repeat が効いている時に host の繰り返しの press を捨てるべきか。

読んだ物と分かったこと:

- **QEMU（host の `/home/awe/qemu-pc98` の source、Windows の WINQ-EMU と同じ系統の UI）**: `ui/sdl2.c` は SDL の `ev->key.repeat`
  を hotkey の判定にしか使わず、host の auto-repeat の keydown をそのまま `qkbd_state_key_event()` へ渡す。`ui/kbd-state.c` は
  「押されている key の key-down は auto-repeat なので怪しくない」として guest に down を送る。つまり **QEMU は host の repeat を
  key-down の繰り返し（up 無し）として入力の層に送る**。
- **usb-kbd（Windows の zip の起動の行 `tools/release/kei-nightly/README.txt` は `-device usb-kbd`）**: `hw/input/hid.c` の
  `hid_keyboard_process_keycode()` は、既に押されている key の down を何もせず捨てる（報告の配列が変わらない）。`hid_init()` は
  keyboard の handler をすぐ activate するので、key は PS/2 ではなく usb-kbd へ行く。zedBSD の `src/drivers/usb/usb-hid.c` は
  報告の前後の held の bitmap の差だけを EV_KEY に出す。**よって usb-kbd の経路では host の repeat は guest に届かない**
  （Q1 の見込みはこの構成では当たらない）。
- **届く経路**: QEMU の PS/2 keyboard（同じ key の make code を繰り返す → 2026-10-05 の kernel の直しで value 2 になり compositor が
  捨てる）と virtio-keyboard（`hw/input/virtio-input-hid.c` は down を毎回 value 1 で送る）。compositor（`input.c` の
  `apply_frame()`・`apply_key()`）は value 2 だけを捨て、**既に押されている key の value 1 を新しい press として client に渡す**
  （押されている key を記録していない）。virtio-keyboard を使う構成ではここで host の repeat が漏れる。Windows の zip・UAT の構成は
  usb-kbd なので当たらない。
- **client の repeat**: libkeiland（`ui/window.c` の `window_keyboard_repeat()`・`kl_window_repeat()`）と Files・Settings の自前の
  repeat は `wl_keyboard.repeat_info` の rate と delay を使い、compositor は Settings の変更を `zwl_seat_repeat_changed()` で
  起動中の client にも送る（読みで確認）。ただし `kl_window_repeat()` は、loop が 1 間隔以上遅れると追いつかずに「今」からやり直す
  （BUG-172 の直し）。**描画の遅い構成（Windows の QEMU の Venus）では、見える repeat の速さが app の loop の速さで頭打ちになり、
  Settings の rate（5〜60/秒）を上げても変わらないように見える**可能性がある（未確認）。delay（150〜1000 ms）の違いは見えるはず。

判断: compositor で「押されている key の value 1 を repeat として捨てる」直しは小さい（入力の device ごとの held の bitmap）が、
ユーザーの構成（usb-kbd）の症状を直さない（そこには漏れが無い）。押されたままの記録が残る（SYN_DROPPED で release を失う）と
次の 1 回の press を捨てる副作用もあるので、**今は入れない**。virtio-keyboard を使う構成が出たら入れる。

次（Q1 の判断、試験の担当へ）:
1. usb-kbd で漏れが無いことの QEMU の確かめ: QMP で A の down を 5 回（100 ms 間隔）・up 1 回、guest の usb の keyboard の input device を
   読む probe（`plan/ws081/tests/ps2keys.c` に device の名前の option を足す）で press=1 repeat=0 release=1。
2. 設定が効くかの QEMU の確かめ: Terminal（または `cat > /tmp/r.txt` の shell）に focus、Settings の値（`keyboard.repeat.rate` 5 と 50、
   delay 400）で QMP の A の down を 3 秒押し続けて up、入った文字の数を数える（5/秒でおよそ 14、50/秒で 100 以上、頭打ちならその値を
   記録）。Windows の QEMU（Venus）では同じ手順をユーザーに。

## 2026-10-09 T1-481（再現）

- bugs.key-repeat-rate: Settings の rate 40 で 3 秒に 33 文字、5 で 15 文字。設定が app の repeat に効かない → 一括の close から戻す（P1）。

## 2026-10-09 QEMU で再現（T1-481）と直し（P1）

- T1-481（AAT `bugs.key-repeat-rate`、QEMU）: delay 400 ms、Terminal で a を 3 秒押し続けると、rate 5 で 15 文字（期待どおり、約 14）、rate 40 で 33 文字（期待は約 105）。rate を上げても 1 秒に約 12 文字で頭打ちになった。
- 原因: libkeiland の `kl_window_repeat()`（`userland/desktop/libkeiland/ui/window.c`）は、loop が起きるたびに repeat を 1 つだけ出していた。loop が 1 間隔以上遅れると、追いつかずに「今」からやり直していた（BUG-172 の直しの形）。QEMU の Terminal の loop は描き直しで 1 秒に約 12 回しか回らない。そのため見える速さは loop の速さで頭打ちになり、Settings の rate が効かなかった（2026-10-06 の P2 の見込みのとおり）。compositor が設定を client に届ける経路は効いていた（`KWL PREFERENCES key=keyboard.repeat.rate applied value=40`）。
- 直し: `kl_window_repeat()` は、前の repeat から今までに来た分を全部出す。各 repeat は前の repeat の 1 間隔の後に来る（`WINDOW_REPEAT_CATCH_UP` 250 ms まで）。loop が 250 ms より長く止まった時は、1 つ出して今からやり直す（まとめて大量に打たない）。rate が 1000 を超える時は間隔を 1 ms にした（間隔 0 は loop が終わらない）。
- 確認: `make … build/p1-ws177/bin/terminal`（libkeiland.so を含む）は warning 0。host の試験は無い（window.c は Wayland の client の file）。QEMU は T1 の `bugs.key-repeat-rate` の再試験で（未実施）。実機は UAT。
