## q786-i01（P1、2026-10-06）: TCP の受信 window と NCM の受信

Status: test-wait（T1 依頼中）

直し（9d76337b）:
- `include/kern/net/packet-buf.h`: stack の packet の pool を amd64・arm64 で 32 → 256（32-bit の board は 32 のまま）。amd64 の vmunix は約 500 KB
  大きくなる（`.net_bss` が PROGBITS のため。kernel の大きさは 12.9 MiB で上限 16 MiB の内）。
- `src/kern/net/tcp.c`: TCP の socket の受信 queue の packet の上限 `TCP_RECEIVE_PACKETS`（pool が 256 以上なら 44、他は従来の 8）。SYN の MSS option と
  window の計算の segment の単位を `TCP_RECEIVE_MSS` = 1460 に（送る segment は従来どおり TCP_MSS = 1024）。広告する window は最大
  min(64 KB の byte の上限, 44 × 1460) ≈ 62 KB（以前は 8 KB）。window scale は入れない（LAN では 64 KB で足りる見込み）。

  NTB ごと捨てていた）に。

## 2026-10-08 夜 P1: 受信の側の損失への強さと NCM の受信の折り返し

Status: 実装・build。QEMU の試験は T1、NCM（実機の RTL8156）の部分は **blocked（UAT 待ち）**（2026-10-08 ユーザー「AATで判別できずUATが必要なところはブロッキングに」）。

読みで見つけた事:
- **TCP の受信は gap の後の segment を捨て、何も返さなかった**（`tcp_segment_input` の「ahead of receive_next is left unanswered」）。重複の ACK が無いので
  送る側（他の PC の Linux・Windows）は fast retransmit できず、1 つの損失ごとに再送の timer（Linux の最小 200 ms、指数の backoff）を待ち、gap の
  後の window 全体を送り直す。USB の LAN で frame が 1 つ落ちるたびに数百 ms 止まる。window を 62 KB にした後も遅いままの説明になりうる。
- **NCM の受信の transfer は、受けた block の frame を全部 stack に渡し終えるまで戻さなかった**（`ncm_take_rx_rearm` は `rx_queue_count == 0` を
  待つ）。poll の budget（16）で渡しきれない分は次の poll（network worker が前の block の TCP の処理を budget 分して yield した後）に回り、その間
  device は transfer を持たない。速い link では device の buffer が溢れて frame が落ち、上の損失になる。
- ECM（QEMU の usb-net）は frame ごとに同じ poll で transfer を戻している（QEMU の 5〜7 MB/s は 1 frame ごとの往復の速さ）。

直し:
- `src/kern/net/tcp.c`・`include/kern/net/tcp-socket.h`: gap の後の segment を 1 接続 16 個まで（32-bit の board は 4）順に並べて持ち
  （`tcp_reorder_keep`、advertise した window の内だけ、満杯なら遠い物を捨てて近い物を）、gap が埋まると続く物を受信の queue に移す
  （`tcp_reorder_drain`、既に受けた部分は切る）。gap の後の segment ごとに直ちに ACK（重複の ACK、RFC 5681 4.2）。close で解放。
- 同: 何も retire しない ACK（重複の ACK、窓の閉じた相手の答え）は再送の timer を延ばさない（RFC 6298 5.3、延ばすと重複の ACK が来る間
  再送が先送りになる）。相手が答えている印として試みの数だけ 0 に戻す（窓の閉じた相手に接続を諦めない、以前と同じ）。
- `src/drivers/usb/usb-cdc-ncm-net.c`: 受信の block を処理した poll で queue の全部を stack に渡し（入力の queue は 256 まで取る）、同じ poll で
  受信の transfer を戻す。

確認: `make … build/p1-uat/vmunix` warning 0、`plan/ws004/tests/run-usb-cdc-ncm-wire-test.sh` PASS、style-check（新しい関数は指摘 0）。
QEMU（T1）: 新 `plan/ws033/tests/tcp-loss-speed.sh IMAGE`（tap と netns の HTTP、netem で guest へ向かう packet の 0・0.5・2 % を落とし、32 MiB を
3 回ずつ、cksum と MB/s。2 % の中央値が 0 % の 1/4 以上で PASS）を新しい image と直す前の image で。`tcp-receive-speed.sh` も。

### UAT の手順（5330 と ue0、何が律速かを分ける）

1. `dmesg | grep -i -e ncm -e ecm` でどちらの driver が付いたか、Settings の Ethernet の Link speed。
2. 網だけ: 他の PC で `python3 -m http.server 8000`（256 MB の file）、5330 で `time fetch -o /dev/null http://PC:8000/f.bin`。
3. scp の行き先: `scp PC:f.bin /tmp/` と `scp PC:f.bin /root/`（root の disk、USB stick なら遅い）。
4. disk の書き込み: `dd if=/dev/zero of=/root/z bs=1m count=256`（の後 `rm /root/z`）。

## 2026-10-10 P1: ifconfig に link の速度、通知の読みを頑丈に（ユーザー「ifconfigやSettingsでLink Speedも表示するのがいいです。まずはそこからです。」）

Status: 実装・build・host 試験。QEMU は T1（usb-net は速度の通知を出さないので `unknown` の表示まで）、値は次の UAT（5330 の RTL8156）。

確かめ（今の main、source）: 速度の口は既にある。kernel の `struct net_device.link_mbps` ← CDC ECM・NCM の driver の ConnectionSpeedChange の通知、
`SIOCGIFSTATS` の `if_data.ifi_link_mbps`（`include/uapi/netif.h`、HAL の API ではない）→ Keiland の zedBSD の backend → compositor の `link_speed` の event →
Settings の Ethernet の card の「Link speed」（不明は `Unknown`）。足りなかった所:
- ifconfig が速度を出していなかった。
- driver の通知の読みが「1 回の transfer に 1 つの通知、NetworkConnection はちょうど 8 byte、ConnectionSpeedChange はちょうど 16 byte」を前提にしていた。
  interrupt の endpoint の packet が 8 byte の device では 16 byte の transfer に NetworkConnection と速度の通知の頭が入り（長さ 16 で NetworkConnection を捨てる）、
  速度の残りの 8 byte は次の通知まで transfer に残る（transfer は短い packet か buffer の満杯でしか終わらない）。どちらの通知も落ちる。
  RTL8156 の endpoint の大きさは未確認（16 byte なら今の code でも取れる見込み）。

直し:
- `src/drivers/usb/usb-cdc-notification.c`・`include/drivers/usb/usb-cdc-notification.h`（新）: ECM と NCM が共有する通知の reader。transfer の byte を
  つないで、whole な通知を順に渡す（8 byte の packet に分かれた速度、NetworkConnection の後ろに続く速度、通知でない byte と長すぎる通知は捨てる）。
  interrupt の transfer の長さは endpoint の packet が 16 byte 未満なら 1 packet、他は 16。
- `src/drivers/usb/usb-cdc-ecm.c`・`usb-cdc-ncm-net.c`: 通知の処理を reader に置き換え（open で空に、失敗の transfer で空に）。速度が変わったら

- `platform/amd64/vmunix.mk`・`platform/pcat/vmunix.mk`: NCM か ECM が y の時に新しい file を入れる。
