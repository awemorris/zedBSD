# BUG-222: ue0 の SCP が約 950 KB/s（約 10 Mbps）。link の速度を Settings に出し、RTL8822BU（実は USB の LAN の device）が 10 Mbps の mode になっていないか確かめる

Reproduction: reproduced（ユーザー、実機 5330、2026-10-06 UAT）
Disposition: tracking
Discovery: 2026-10-06 ユーザーの UAT のコメント
Handling: WS033（USB LAN）・WS089（Settings の Network）

## 観測（ユーザー）

「SCPで他のPCからファイルを送ったところ、ue0の接続で、950KB/s (kilo byte per sec)しか出なかったです。10Mbps程度の計算ですね。リンクアップ速度をSettingsに表示するとともに、10Mbpsになっていないか（複数あるRTL8822BUのモードのうち10Mbpsのものになっていないか）を確かめてほしいです。」

## 次（未確認の見込み）

ue0 の driver（CDC NCM/ECM、RTL8156 など）の link の速度の読み取りと表示。10 Mbps に落ちているなら原因（auto-negotiation・mode の選択）。速度の律速が link でなく driver の転送（USB の bulk の数・NCM の集約・TCP の窓）の可能性も測る。注: RTL8822BU は WiFi の chip、ue0 は USB の有線 LAN（ユーザーに確かめる）。

## 2026-10-06 ユーザーの見込み

「USB LANはNCM, ECMが両方あるときの選択の問題かもしれないので、記録しておいてください。」→ USB の LAN の device が CDC NCM と CDC ECM の両方の configuration・interface を出す時、zedBSD が遅い方（ECM、または NCM の集約の無い使い方）を選んでいる見込み。確かめ: どちらの driver（usb-cdc-ncm・usb-cdc-ecm）が付いたか、configuration の選択の規則、NCM の NTB の大きさ。直し: NCM があれば NCM を選ぶ。link の速度の表示（Settings）も合わせて。

## q780-i01（P1、2026-10-06）: 調べと直し

Status: test-wait（T1 依頼中。速度の値は実機でだけ出る）

調べ（source）:
- **NCM と ECM の選択は既に NCM が優先**: `src/drivers/usb/usb.c` `device_preferred_configuration` は configuration ごとに driver の match の点の最大を
  比べ、`ncm_match` = 100、`ecm_match` = 80。UAT の config（config-amd64-beta1 → ci）は NCM・ECM とも y。どちらが付いたかは実機の kernel.log で見る。
- **律速の見込みは kernel の TCP の受信 window**（link の速度ではない）: `src/kern/net/tcp.c` `tcp_receive_window` は「残りの byte」と「残りの packet の数
  × TCP_MSS（1024）」の小さい方で、socket の `receive_packet_limit` = `SOCKET_RECEIVE_MESSAGES_MAX` = 8 なので、広告する window は最大 8 KB。
  950 KB/s は RTT 約 8.6 ms で出る。加えて NCM の driver は受信の bulk の URB が 1 本（8 KB の NTB）、送信も 1 frame ずつ。UAT の image の root は
  USB stick なので、scp の書き込み先の速さも効きうる。→ Q1 が新しい Queue **q786**（window の上限・MSS・window scale と NCM の受信の URB の本数）にした。

直し（ab0699b6、link の速度を Settings に出す）:
- kernel: `struct net_device` に `link_mbps`（`include/kern/net/net-device.h`）。CDC NCM・ECM の driver が SPEED_CHANGE の通知の速い方の向きを Mb/s で
  入れ、NETWORK_CONNECTION の切断で 0 に（`usb-cdc-ncm-net.c`・`usb-cdc-ecm.c`）。`SIOCGIFSTATS` が `if_data` の未使用の `ifi_reserved` を改名した
  `ifi_link_mbps` で返す（`include/uapi/netif.h`、struct の大きさと配置は不変）。
- desktop: `kl_backend_network_link.link_mbps`（zedBSD の backend が読む、Linux・FreeBSD は 0 = 不明）→ compositor の `kl_system_network_v1` の新しい
  event `link_speed`（manager version 11 → 12、version 12 以上の client にだけ、速度が分かる時だけ送る）→ libkeiland（`kl_network_link.link_mbps`、
  KL_VERSION 39）→ Settings の Ethernet の card の「Link speed」（`1 Gb/s`・`2.5 Gb/s`・`100 Mb/s`、不明は `Unknown`）。

確認: build（vmunix・networkd・settings・wayland）warning 0、Keiland の Linux の host build（`keiland-linux.mk`）exit 0。host の試験
`plan/ws131/tests/host-system.sh` PASS、その写し（scratch で fake の link に 2500 Mb/s を足した版）で libkeiland まで 2500 が届くことを確認。host の描画で
「Link speed 1 Gb/s」を確認。QEMU の usb-net は速度の通知を出さない見込みなので QEMU では `Unknown` の表示まで。実機の値（10・100・1000・2500）は次の UAT。

## q786-i01（P1、2026-10-06）: TCP の受信 window と NCM の受信

Status: test-wait（T1 依頼中）

直し（9d76337b）:
- `include/kern/net/packet-buf.h`: stack の packet の pool を amd64・arm64 で 32 → 256（32-bit の board は 32 のまま）。amd64 の vmunix は約 500 KB
  大きくなる（`.net_bss` が PROGBITS のため。kernel の大きさは 12.9 MiB で上限 16 MiB の内）。
- `src/kern/net/tcp.c`: TCP の socket の受信 queue の packet の上限 `TCP_RECEIVE_PACKETS`（pool が 256 以上なら 44、他は従来の 8）。SYN の MSS option と
  window の計算の segment の単位を `TCP_RECEIVE_MSS` = 1460 に（送る segment は従来どおり TCP_MSS = 1024）。広告する window は最大
  min(64 KB の byte の上限, 44 × 1460) ≈ 62 KB（以前は 8 KB）。window scale は入れない（LAN では 64 KB で足りる見込み）。
- `src/drivers/usb/usb-cdc-ncm-net.c`: pool が 256 以上の時、受信の NTB を 16 KB（以前 8 KB）、1 つの NTB から受ける frame を 32（以前 8。超えると
  NTB ごと捨てていた）に。

確認: amd64・rpi4 の vmunix の build warning 0。pcat・pc98 は `sandbox_*` の未定義で link できない（この変更と無関係の既存の壊れの見込み、base では
未確認）。`plan/ws004/tests/run-usb-cdc-ncm-wire-test.sh` PASS。QEMU: `plan/ws033/tests/tcp-receive-speed.sh`（host の HTTP から 32 MiB を 3 回、
cksum と MB/s）を T1 に依頼。実機の scp は次の UAT。

残り（未着手）: NCM の受信の URB を 2 本以上にする（今は 1 本で、NTB を処理し終えてから次を出す）。ECM（QEMU の usb-net）は 1 frame ごとの URB 1 本。
送る側の segment（1024）を相手の MSS と device の MTU に合わせる。測った結果で次を決める。
