# BUG-367: loopback の TCP で accept 側を先に close すると、connect 側の close(2) が戻らない

- 状態: open（2026-10-30 Q1 が登録、P3 が解析と修正）
- 発見: 2026-10-30 P2（WS327 p016 の QEMU、doc の image）。SSH の出力で確かめた（console は読んでいない）。
- 再現: `plan/ws327/phase016/tcp-close-repro.c`（P2 の branch agent/p2-ws327）の引数 `0 1`・`0 0`（order nonblocking）で "close client" の後に止まる。client を先に close すれば server・listener の close は戻る。blocking・非 blocking とも。
- 影響: 08-network の例が終わりで止まる（FINISHED が来ず、窓を閉じても join が戻らず process が残る）。Mailer など、相手が先に閉じた接続の close で止まる恐れ。
- 疑い（未確かめ）: 2026-10-30 の TCP の変更（WS315 p006: 受けの buffer の自動調整と予算の返し、送りの ring 768・送りの buffer 1152 KB）の後に出たかを先に確かめる。P2 の image は main b901b1968（受けの自動調整を含み、送りの ring の変更 bc991f3ca は含まない）。
- 直す方針: 再現を QEMU で取り、close の待ちの条件（FIN の送り・linger・送りの queue の掃き出し・相手の RST の扱い）を調べて直す。例（08-network.c）の close の順は変えない（不具合を隠さない）。

## 解析（2026-10-30 P3 q1706-i01）

- 再現（QEMU、SSH で判定）: `plan/tools/tcp-close/qemu-close.sh build/bug367/head/hdd-image.img build/bug367/qemu-head`（image は main b776fd468 の
  `plan/ws221/tests/config-amd64-tcp.mk`、repro は P2 の f5f7dbe4c の物を `plan/tools/tcp-close/tcp-close-repro.c` に写した）:
  `0 1` 10.4 s・`0 0` 10.3 s（どちらも最後に "done"）、`1 1` 0.2 s・`1 0` 0.3 s。止まり続けるのではなく、client の close が 10 s 待ってから戻る。
  （08-network の例で close が戻らないと見えたのは、この 10 s の待ちと考えられる。例の側は確かめていない。）
- 原因: accept した側の close は FIN を送り、その ack を待って（`tcp_close_drain(TCP_DRAIN_ALL)`）endpoint を解放する（FIN_WAIT_2・TIME_WAIT を
  保たない）。後から client が close すると、client（CLOSE_WAIT → LAST_ACK）の FIN は 4-tuple で合う接続が無く、`tcp_lookup` が同じ port の
  listener に渡す。`tcp_input` の LISTEN の分岐は SYN 以外を黙って捨てていた（RFC 793 の LISTEN は ACK 付きの segment に RST を返す）。
  client は FIN の ack も RST も得ず、close の drain が上限 `TCP_CLOSE_DRAIN_MS`（10 s）まで待つ。listener も閉じていれば合う物が無く
  `tcp_send_reset` が RST を返すので待たない（client を先に close する順は、server の FIN が client の ephemeral port の解放後に届き RST）。
- 今日の TCP の変更（WS315 p006）とは無関係: 同じ待ちは root の 846464d1e から有る（`TCP_DRAIN_ALL` と LISTEN の分岐）。
  tcp-model の close の場面を c90327de3（p006 の前）の src に当てても close-b-first は 10000 ms で FAIL（`build/bug367/c903`）。
- 所見（直していない）: 閉じた接続を TIME_WAIT（2MSL）・孤児の FIN_WAIT_2 として残さず、最後の参照で endpoint を解放する。TIME_WAIT への
  遷移（`tcp_input` の FIN の受け）は有るが 2MSL の timer は無く、TIME_WAIT を省く理由は source にも docs にも書かれていない。
  影響: 解放の後に届く相手の segment は RST で答えられ（この直しで listener が有る port も同じ）、相手の close は ECONNRESET で終わる
  （close(2) の戻り値は 0）。RFC 793・1122 の 2MSL による古い segment の保護（同じ 4-tuple の次の接続へ）は無い。
- 直し: `src/kern/net/tcp.c` の LISTEN の分岐で、ACK 付き・RST 無しの segment に `tcp_send_reset` を返す。HAL は変えない。
- 模型: `plan/ws220/tests/tcp-model` に `--close-first a|b`（転送の後に close(2) の順で閉じる、listener は開けたまま、2 番目の close の待ちが
  1 s を超えれば FAIL）と run.sh の場面 close-b-first・close-a-first。直しの前: close-b-first の 2 番目 10000.0 ms で FAIL、直しの後 0.2 ms。
- repro は各段に guest の中の経過 ms を出す（`exchanged N ms` … `closed N ms`）。qemu-close.sh は 4 通り × ROUNDS（既定 3）を流し、
  "done" と close の段の合計 1 s 未満で PASS（SSH の往復は 0.2〜26 s とばらつくので、時間は guest の中で測る）。
