# BUG-285: ログイン画面・ロック画面で、PIN を設定してあっても PIN でログインできない

Reproduction: reproduced（ユーザー、実機 5330、2026-10-10）
Disposition: resolved（2026-10-10 ユーザーの 5330 の UAT「PINを使えました。Closeします。」）
Discovery: 2026-10-10 ユーザーの UAT
Handling: WS172（ws172-p007 の方式の選択）・WS187（ロック画面）・sessiond・/sbin/passkey

## 観測（ユーザー）

「ログイン画面、ロック画面で、ユーザのPINが設定されていても、PINログインができないバグを発見。」

## Q1 の SSH（5330、2026-10-10）

- /var/log/sessiond.log: `SESSIOND ENROLL pin ok user=kei`（1791547886）の後、`UNLOCK`・`LOGIN` の style=pin の行が **1 つも無い**（fido2 の UNLOCK ok・fail はその前にある）。→ PIN の試みが sessiond に届いていない: greeter・lock が PIN の方式を出さない（styles の問い合わせを起動の時だけして cache している等）か、PIN の欄の送信が sessiond へ行かない見込み（未確認）。
- /etc/passkey は 12:11 に更新（PIN の登録）。
- 別件の見つけ: sessiond.log に `net: networkd is unavailable: No such file or directory`（session の開始の直前）。
- QEMU の T1-520 では /sbin/passkey で PIN を登録した後に lock の画面が `styles=3` で PIN の欄を出した（その試験は PIN の欄に password を入れて失敗、試験の側）。

## 2026-10-10 ユーザーの回答（Q1 の問い）

「PIN の選択肢が出ない」→ greeter・lock の方式の選択に PIN の pill が無い（Password・Security Key だけ）。方式の一覧の問い合わせか、PIN の登録の有無の判定が PIN を落としている。

## 2026-10-10 P1: source の確かめと案

- 確かめ（source）: lock も greeter も方式を毎回 sessiond に問う（lock は `kwl_greeter_lock` で毎回 `greeter_styles_reset`、greeter は利用者を選ぶたび。cache ではない）。passkey の `styles` は PIN の登録があれば `pin` を返す（`passkey_styles`）。backend の `STYLES` の解析も正しい。PIN を外すのは sessiond の `sessiond_policy_styles` → `sessiond_policy_pin_allowed` の「sessiond の起動の後に password か鍵で login・unlock したか（`signed_in`）」だけ。autologin は password を通らないので `signed_in` は 0 のまま、Settings の PIN の登録（password で確かめる ENROLL）の成功も `signed_in` を立てない（`auth.c` `auth_granted`: 「a change proves the password, but does not offer the PIN」）。→ 5330 の log（STOP → START → AUTOLOGIN → ENROLL pin ok）どおりなら、**設計（security.md「The PIN is offered for an account only after …」）どおりの挙動**。Security Key の pill が出るのは鍵に `signed_in` の条件が無いため。
- 案（ユーザーの判断）:
  - (A) 設計どおりのまま、説明を足す: lock・greeter の方式の行の下に 1 行「PIN is available after you sign in with your password or security key.」（PIN が登録済みで今は出せない時だけ。sessiond が `STYLES` に理由を足すか、`ENROLLED` の pin=1 と STYLES の差で greeter が決める）、Settings の PIN の登録の欄に「After a restart, sign in once with your password or a security key before the PIN can be used.」
  - (B) **推し**: password で確かめる変更（PIN・鍵の登録と削除）の成功も「password を示した」と数え、PIN をすぐ出す。登録の時に password を入れているので、PIN を出してよい根拠（再起動で PIN の試行を新しく得させない）は崩れない（攻撃者が ENROLL できるなら既に password を知っている）。autologin の直後に Settings で PIN を設定した人がそのまま lock で PIN を使える。再起動の後の greeter で PIN が出ないのは今どおり（電話と同じ）。(A) の説明の 1 行も併せて足せる。
- (B) の実装は済み（agent/p1 の commit、merge は判断の後）: `userland/desktop/sessiond/auth.c` の `auth_granted` で ENROLL・REMOVE の成功を `SESSIOND_STYLE_PASSWORD` の成功として数える、`docs/architecture/security.md` の規則の文に「or proved its password to set or remove its PIN or a key」。host 試験 `plan/ws172/tests/sessiond-auth-host-test.sh` に「autologin 相当の新しい sessiond で STYLES は password だけ → ENROLL pin（password）→ STYLES に pin」を足した（fork した子で新しい counts から。直しを外すと FAIL を確かめた）。PASS。sessiond の build rc 0（新しい warning 無し）、style-check 0。

## 2026-10-10 QEMU（T1）

T1-522 で登録の直後の lock で PIN の解除（PASS）。実機は次の UAT。
