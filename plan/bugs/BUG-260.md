# BUG-260: i915 の buffer・image を先に destroy すると view・descriptor・framebuffer が解放済みの record を指す（疑い）

- 状態: unknown（host の contract 試験で各経路を確かめた。実機で起こしてはいない） / resolved（2026-10-08 Q1 の判定: merge a870f9860、contracts の全 run PASS（plain と ASan/UBSan）。実機は未。本文の「Q1 の判定」）
- 発見: 2026-10-08 P1 の BUG-244 の修正の時の読み（範囲外として報告）。
- 期待: アプリが Vulkan の規則に反して buffer・image を view・descriptor set・framebuffer より先に destroy しても、kernel は解放済みの memory を読まない。
- 観察（読み）: `i915_gfx_destroy_plain` は record を kern_free するだけで、buffer view・image view・descriptor set・framebuffer が持つ buffer・image の pointer が残る（BUG-244 と同じ形）。再現は未。
- 関係: [BUG-244](BUG-244.md)（同じ形の VkDeviceMemory の UAF、2026-10-08 修正）。ユーザーは BUG-244 の優先度を上げた（2026-10-08）。

## 次

- BUG-244 の memory_contract_test と同じ形の host の contract 試験で、修正前の code を ASan で落とす（再現）。
- 直し: destroy の時に、その buffer・image を指す view・descriptor・framebuffer の pointer を NULL にする（drv_i915_object_each）。

## q873（P1、2026-10-08）

### 読んで分かったこと

- pointer で他の object を持つ所（gfx.h）: view → image、buffer view → buffer、descriptor set → view・buffer view・sampler・buffer・**layout**、framebuffer → view、
  command buffer の記録した操作（`struct i915_gfx_op`）→ buffer・image・descriptor set・pipeline・render pass・framebuffer・query pool。pipeline の shader module は作る時に
  compile し、後で読まない（destroy しても安全）。video は view を identity で毎回引いて image の NULL を見る。session の draw の状態は submit の間だけ。
- **規則に従う app でも起きる物が 1 つ**: Vulkan は descriptor set layout を、その layout で確保した set を使う間に destroy してよい（その set への
  vkCmdBindDescriptorSets は layout を読む）。`command.c` の `i915_record_dynamic_offsets` が `dset->layout` を読む → 解放済みの layout を読む UAF。
- 他は規則に反する順の destroy（view・set・framebuffer・command buffer より先に buffer・image など）で、解放済みの record を後で読む。

### 修正

- 新しい `render/forget.c`・`forget.h`（`platform/amd64/vmunix.mk` に登録）: `drv_i915_gfx_forget(session, kind, object)` を object を放す前に呼ぶ。
  buffer → buffer view・set・command buffer、image → view は image を持たなくなり、その view を名指す set・framebuffer も手放す、command buffer、
  view → set・framebuffer、buffer view・sampler → set、set・pipeline・render pass・framebuffer・query pool → command buffer。手放した物があれば 1 行 log。
  `drv_i915_gfx_op_names(op, object)`（記録した操作が名指す object）、`drv_i915_gfx_view_lookup`（image の無い view は不明として引く: descriptor の更新と framebuffer の作成）。
- `command.c`: `drv_i915_gfx_command_forget` — その object を名指す操作を持つ command buffer は操作を空にし `stale`（begin・reset で消える）。`vkQueueSubmit` は stale を
  走らせず log。
- 呼ぶ所: `objects.c` の汎用の destroy（buffer・image・view・buffer view・sampler・framebuffer・render pass ほか）、`pipeline.c` の destroy、`fence.c` の query pool の destroy、
  `descriptor.c` の pool の reset・destroy の set の解放。
- `descriptor.c`・`gfx.h`: set は確保の時に layout を自分の中に写す（`layout_copy`、`layout` はそれを指す）。layout の destroy の後も読める。
- 試験: 新しい `tests/contracts/forget_contract_test.c`（`run.sh forget`）26 checks、`host_render.[ch]`（memory と forget の両方の host の heap・mutex・log、memory の試験から移した）。

### 確認

- host: `forget` 26 checks・`memory` 18 checks、plain と ASan/UBSan（leak 検出）で PASS（scratch の runner で同じ compile の列、rm なし。`run.sh` は trap に rm があるので担当は流さない）。
- build: kernel（i915 込み）warning 0。i915 の試験の組 `I915_TESTS=y` の vke1・vke2・compute・vkx で compile と link が通り warning 0。style-check 新しい指摘 0（descriptor.c は前からの 1 件）。
- 未実施: 実機。layout の UAF（規則に従う app でも起きる物）は修正前の再現の試験を書いていない（descriptor の確保を wire で送る試験が要る）。読みと修正の形で確かめた。
