# BUG-403: ブラウザ: link を押してから遷移まで約 2 秒 app が応答しない（取得の間も event の処理を続ける）

- 状態: fixed（2026-11-02 P8 q1924-i01、agent/p8-uat2。network を待つ間の固まりを無くし、届いた script の実行を細かく分けた。Linux の host build と live の store.google.com で確かめた、本物の Windows は未実施。1 つの重い script・頁の解析そのものの長さは残る（「残り」））。前: open（2026-11-02 08:19 Q1 が起票、P8 の待ち行列）
- 発見: 2026-11-02 08:19 ユーザーの Windows での OmniGrammaton の UAT（BUG-397〜399 の直しの後）。
- 中身: 「ストア」を押すと遷移はできるが、約 2 秒反応が無くなる。socket の通信が非同期か確かめる。原因に依らず、link を押してから遷移するまでの間も、入力・描画などの event の処理が止まらないようにする（ユーザーの要望）。
- 扱い: P8（ブラウザの担当、ユーザーの決定）。BUG-401 の後に順に。

## 原因（2026-11-02 P8）

Windows に固有ではなく libbrowser の view の作り。socket の通信（文書と副資源の取得）は network の thread で非同期だったが、届いた文書を頁にする所（`view_commit_document` → `page_load_bytes`）が main thread で network を同期で待っていた。Linux の host build で google.com から「ストア」を押し、頁の段ごとの時間を測った（一時の計測、commit しない）。

- 文書の解析（inline の script を含む）1.9 秒、その後の `page_wait_sheets` 2.3 秒、deferred script 0.5 秒。`page_wait_sheets` は style sheet が届くまで 10 ms ずつ network を待つ loop で、待つ間に届いた async の script（1.8 秒の物）もその中で走った。store の頁の sheet は script が足す `<link>`（静的に見つからない）。
- parser の script（inline・同期の src）は、その前の「全部の」sheet を待っていた。仕様では script を止めるのは parser が作った link・style の sheet だけで、script が足した sheet・async・defer の script は止めない。
- 頁が出た後も、`browser_view_process` は届いた要求の callback（届いた script の実行）を全部 1 回で処理していた。
- 頁の script の 1 回の実行がとても長い物がある（store の頁で 17 秒の callback が 1 つ、`vm_shape_find` が CPU の 30%・layout が 23%、perf で測った）。これは 1 つの script の中なので分けられない。

## 直し（2026-11-02 P8、agent/p8-uat2）

1. 文書の後半を非同期に（`page/page.c`・`view/view.c`）: `page_load_begin`（解析まで、linked の sheet の読み込みを始める）と `page_load_finish`（後半: deferred・module・load の event・style の集め直し）に分けた（`page_load_bytes`・`page_load_html` は今まで通り続けて呼ぶ）。view は解析した頁を `finishing` に置き、script を止める sheet が届いてから（最大 30 秒）`browser_view_process` の中で後半を走らせて頁を出す。その間は前の頁が出たまま入力・描画が続く。新しい load・stop・destroy は待っている頁を捨てる。
2. script を止める sheet を仕様に合わせた（`dom/dom.h` の `DOM_NODE_PARSER_CREATED`、`html/parser.c`・`html/foreign.c`、`page/sheets.c` の `page_sheets_blocking`、`page/script.c`）: 文書の parser（fragment でない）が作った element に印を付け、その link・style の sheet（とその @import）だけが parser の script と後半を止める。async・defer の外部 script は parser の位置で sheet を待たない（defer は後半で待つ）。
3. linked の style sheet を先に取得（`page/script.c` の `page_scan_scripts`・`page_add_prefetched`、`page/sheets.c` の `sheets_take_ahead`、`view/view.c`）: parser を止める script の先取り（BUG-207）に `<link rel=stylesheet>`（alternate でない）を加え、status と Content-Type も持たせ、sheet は届いた物と同じ検査（2xx、標準 mode では text/css）で読む。
4. callback の処理を区切る（`net/loader.c` の `net_loader_dispatch_until`、`view/view.c`）: `browser_view_process` は届いた要求の callback を 50 ms まで処理し、残りは順を保って次の呼び出しへ（`browser_view_timeout` が 0）。1 つの callback は途中で切れない。
5. 後半の終わりの style の集め直しで layout が古いままになる誤り（`page.c` の `gathered`・`laid_out_gathered`、`script.c` の `page_needs_layout`）: layout の後に style を集め直すと layout を作り直す（1 の後、遅れて届いた sheet が `getComputedStyle` に効かなかった）。

## 確かめ（2026-11-02 P8、Linux の host。QEMU・本物の Windows は未実施）

- 新しい host の試験 `plan/ws074/tests/host-navigation-wait.c`（引数なし、試験の中の 127.0.0.1 の HTTP server、遅い sheet 2 つ（markup の link と script が足す link、各 1.2 秒）と script が足す 150 ms の script 4 つ）: 1 回の `browser_view_process` の最長 150 ms（直す前の object では 2.5 秒前後）、待つ間は前の頁、deferred script が markup の sheet を見る、script が足した sheet が届くと効く、足した script が走る。後は 5 回とも 8 checks PASS、前は「長い呼び出し」で FAIL。
- live（google.com から「ストア」、host build と `build/tmp/p8u/drive.c`）: 押してから頁が出るまでの 1 回の最長の呼び出しが 5.1〜5.3 秒 → 3.0 秒（解析と後半）、続く 21 秒の呼び出しの前に 2.0 秒の呼び出しが分かれた。21 秒は 1 つの script の callback（残り）。
- host build（`host-build.sh plain`、struct が変わったので新しい根で全部）warning 0。host-* の exit は前と同じで新しい試験 1 本が増えた。http 15/15・http-async 19/20（前も同じ async-sheets の FAIL）・loader 11/11・fetch 38/38・js 18/18。
- WS074 の段 1 の前後と cross-build は最後にまとめて。

## 残り

- 1 つの script の実行・頁の解析（inline の script を含む）は main thread で分けられない。store の頁では commit の呼び出しが約 3 秒、頁が出た後に約 17〜21 秒の呼び出しがある（JavaScript の property の探索 `vm_shape_find` が線形で CPU の 30%、layout が 23%）。engine の速さの改善（shape の探索の索引など）は別にするのがよい（WS074 の側か別の Bug、Q1 の判断）。
- 解析を時間で区切って何回にも分ける事はしていない（parser の途中で async の callback が走る順の作りが要る）。
