# BUG-040: journal の UFS の volume で名前の操作が 1 回約 100 ms かかり、続けると guest が応答しなくなる

Bug ID: `BUG-040`
Reproduction: reproduced（QEMU、amd64 guest、KVM、volume は NVMe）
Disposition: scheduled（ws060-p001）
Date: 2026-09-25
Source: ws054-p003（q415-i01）で、journal の volume（`zedimage-host ufs ... --profile=journal-snapshot`）に directory の試験を走らせたとき。
Owner: WS060 p001
Queue: q431-i01。

## 期待と観測・影響

期待: journal の volume でも、名前の作成が journal 無しの volume と同じ桁の時間で終わる。

観測（guest 8 GiB、同じ guest に journal 無しと journal の volume を NVMe でつないで比べた）:

| 操作 | journal 無し | journal |
| --- | --- | --- |
| 新しい directory に 200 の file を作る | 1 秒 | 21 秒（1 回約 100 ms） |
| 2500 の名前がある directory に 200 を作る | 11 秒 | 36 秒 |
| 2500 の名前がある directory で 200 回 stat（mount の直後） | 5 秒 | 4 秒 |

名前の操作ごとに journal の group を commit する費用（flush か）と見ている（未検証）。約 8000 の操作を続けた試験では、SSH と serial の console の command が 60 秒で終わらず、
guest が止まったように見えた（gdbstub の標本では CPU はほぼ idle、busy な標本は `buf_read`・NVMe の I/O）。操作を減らすと最後まで終わった。
ws054-p003 の変更の前の kernel（名前は 1 block まで）では同じ量の試験ができないので、変更の前との比較は未実施。
小さい directory の作成（変更で増えたのは cache にある 1 block の読みだけ）でも 100 ms かかるので、変更の前からの性質と見ている。

影響: journal の volume で多数の file を作る作業（package の展開や build）が遅く、その間 guest 全体の応答が悪くなる。

## 再開の条件

UFS の journal の性能を扱う WS で。受け入れ案: journal の volume で 200 の作成が journal 無しの数倍以内、続けた操作の間も SSH が応答する。
