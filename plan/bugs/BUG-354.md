# BUG-354: `top -b` が全ての process の %CPU を 0.0 と出す（未確認）

- 状態: open・未確認（2026-10-29 Q1 が登録） → fixed（2026-10-31 P2、q1750-i01、QEMU で確かめた。実機は未実施。Q1 の判定待ち）
- 発見: 2026-10-29 P1（q1669-i04、WS235 p006 の実機 10.0.10.3、zedBSD amd64、tcp-perf で CPU を使っている間）。
- 観測: `top -b` の %CPU が全ての process で 0.0。hw.cputimes の CPU ごとの差では CPU は使われていた。
- 期待: 走っている process の %CPU が出る。
- 未確認: 再現の手順、他の board・QEMU で起きるか、`top` の対話の表示でも同じか。

## 原因と修正（2026-10-31 P2、q1750-i01）

- 原因: kernel は process ごとの CPU 時間（`struct process_info` の cpu_ticks、1/100 秒）を返しているが、`userland/base/top/main.c` が %CPU と TIME+ を `0.0`・`0:00.00` の固定の文字で出していた（どの board・QEMU でも、対話の表示でも同じ）。
- 変更（20f8ce41a）: 前の draw の process ごとの cpu_ticks を覚え、%CPU = 前からの増え ÷（経過の秒 × 100）× 100（1 CPU に対する割合、複数の CPU で 100 を超える）。最初の draw の前に 250 ms あけて 1 回 sample する。TIME+ は cpu_ticks から m:ss.hh。%MEM・RES は今まで通り（kernel が resident を返さない）。
- build: warning 0。QEMU（amd64、SSH）で busy loop の sh を走らせ `top -b -n 2 -d 2` が 2 つの frame でその sh を 104.0・100.0、他の process を 50 未満と出し、TIME+ が 0:02.80 → 0:04.80 と進んだ。最初の QEMU の run で、batch mode の delay が SSH の閉じた標準入力の poll ですぐ終わり 2 つ目の frame が間を置かずに来て 0.0 に戻る事が分かったので、batch mode は poll せず delay を nanosleep で待つようにした（e08fa9af6）。実機（10.0.10.3）は未実施。
