# BUG-343: VisionFive 2 の SD からの起動で、root の file system が 60 秒たっても live にならない事がある

- 状態: reproduced（2026-10-20、電源の入れ直し十数回のうち 3 回ほど）/ resolved（2026-10-31 P2: SD の CRC の誤りの原因を直し、直した kernel の 10 回の起動で root は毎回 live、失敗は計 7 回で全部 retry で通った。closed の案。根の直しの IDMAC は提案）
- 発見: WS269 の UAT の電源の入れ直し（SwitchBot）で、3 分たっても SSH に戻らない起動があった。ユーザーのシリアルの log: `powervr: firmware: still in file after 5 s` … `still in file after 55 s` → `powervr: firmware: file failed (42) after 60003 ms`（firmware の file の読みは root が live になるのを 60 秒待つ。`firmware-file.c` の wait_root）。
- 観測: 正常な起動でも `dw-mmc: read of 32 blocks at 153392 failed (5, status a4), try 1`・`dw-mmc: no sample phase reads at 49500000 Hz`・`dw-mmc: data errors at high speed, card clock down to 24750000 Hz` が出る（WS256 p005・p013 の高速の読みの退避）。読みの失敗が root の mount の前に重なると mount が終わらないか、retry が足りない見込み（推測）。
- 環境: VF2 v1.3B、SDXC SA128（manufacturer 02）、image build/uat/vf2-gpu/native.img（main 1512e79cd）、kernel d851a8783。
- 関係: WS256 p013（SD の clock）・p005。GPU とは無関係。
- 再調査の条件: 起動の失敗の時のシリアルの log（ユーザーの手元）で、`vfs:` の行がどこで止まるかを見る。

## 2026-10-21 06:20 の追加の観測（Q1、同じ部品の疑い、同一とは断定しない）

- 電源の入れ直しで戻った（SD は読める）。GPU の試験は影響を受けていない（その直前まで 13/13）。

- 次: WS256 の SD の driver で、retry の後の失敗が block の層に EIO を返し続ける状態（card の state・clock の下げの後の戻り）を見る。
- 2026-10-21 板 100 の電源の入れ直し（P2 の診断の kernel）で 3 分たっても SSH に戻らず、2 回目の入れ直しで戻った（`plan/tools/vf2/run.sh` の「no ssh after 3 min, cycling again」）。シリアルの log は無いので原因は未確認（同じ症状の 4 回目の見込み）。

## 2026-10-21 q1531-i01（P2）: driver の retry と回復を強くした（板は未実施）

- status の解読（DW の RINTSTS）: a4 = bit 2（command done）+ bit 5（RX の要求）+ bit 7（data CRC error）。84 = command done + data CRC error。
  24.75 MHz に下げた後も CRC error は出ていた。card の劣化の可能性は残る。
- driver の穴:
  1. 失敗の後の回復（`recover_card`）は FIFO の reset だけで、controller の state machine と DMA は reset していなかった。
  2. 1 回の回復の失敗で unit を `failed` にしていた。以後の要求は全部すぐに EIO になり、電源の入れ直しまで戻らない（root の書き込み停止、exec の EIO と合う）。
  3. 3 回の try の後の EIO が、そのまま file system に届いていた。
- 修正（`src/drivers/mmc/dw-mmc.c`）:
  - 回復は controller・FIFO・DMA の reset、clock の update、raw status の消去（Linux の dw_mci_reset と同じ）をしてから、CMD12 と状態の待ちをする。
  - 回復は 3 回まで試し、全部失敗した時だけ card を消えたと見る（`the card did not come back`）。
  - run の try は 5 回にした（Linux の MMC_MAX_RETRIES）。それでも動かない複数 block の run は、1 block ずつ、各 5 回の try で読み書きする（Linux の block.c の 1 sector ずつの retry）。
  - log に失敗の累計（`errors N`）と、1 block ずつに落とした run の数（`split runs`）を出す。
- 確認:
  - `plan/tools/vf2-host/dw-mmc/run.sh` は OK、0 failure。
    - CRC error が 3 回なら回復、7 回なら 1 block ずつで回復、毎回なら EIO。
    - 次の要求は通る。
  - VF2 の vmunix は rc 0、warning 0。
- 次: 板で `errors`・`split runs` の数と、root の書き込み停止・exec の EIO が出なくなるかを見る。24.75 MHz でも error が多いなら card の交換を試す。

## 2026-10-31 P2（q1772-i01）: 原因と直し

- main cf41e7630 の kernel の 9 回の起動で、root が live にならない事・firmware の `file failed` は 0 回（本症状は再現せず）。SD の読みの
  失敗は毎起動 5〜17 回あり、retry で通っていた。原因と測り方は [BUG-340](BUG-340.md) の 2026-10-31 の節: PIO の FIFO が満ちて card clock が
  止まった run が data CRC の誤りになる（sample phase・card の劣化ではない）。
- 直し:
  - `src/drivers/mmc/dw-mmc.c`: run の FIFO の serve（`serve_fifo`）を preemption を止めて行う（`move_data`）。割り込みは止めない。
    128 block の run で約 5 ms。
  - `src/drivers/platform/visionfive2/vf2-mmc.c`: card clock を 25 MHz（ciu 49.5 MHz の 1/2 = 24.75 MHz）に抑える。PIO は 49.5 MHz に追い付けない
    （preemption を止めても FIFO がほぼ毎回満ちる）。high speed の switch はそのまま。
  - `plan/tools/vf2-host/dw-mmc/`: 偽の controller の FIFO が preemption を止めずに触られたら FAIL（直す前の dw-mmc.c で FAIL を確かめた）。
    glue の試験の card clock の期待を 24.75 MHz に。
- 確かめ:
  - host: `plan/tools/vf2-host/dw-mmc/run.sh` の 4 つとも `OK: 0 failure(s)`。VF2 の vmunix は rc 0・warning 0。
  - VF2 の実機（`plan/tools/vf2/boot-cycle.sh`、kernel cksum 868265884、3 回の起動）: 3 回とも SSH 35 s、`bus 4-bit, 24750000 Hz, high speed`、
    SD の読みの失敗は 0・2・0 回（直す前は毎起動 5〜17 回、2 回は同じ run の try 1・2 で try 3 で通った）。各起動で p5 の生の 64 MiB の読み
    6.13〜6.14 s（約 10.9 MB/s）、16 MiB の file の書きと読み戻しの cksum が一致。gpu-selftest 13/13・vkcompute PASS。
    証拠 `/tmp/p2-vf2bugs/runE/`（git の外）。
- 残り: 割り込みの handler が長い時の FIFO の満ちは防げない（起動 3 回で 2 回の失敗）。根の直しは IDMAC（Linux の dw_mmc と同じ DMA）で、
  49.5 MHz も使える見込み（未着手、Q1 に提案）。2026-10-22 の file の中身が黙って壊れた件は、この直しの後に未観測（試験の範囲では cksum 一致）。
- 提案（2026-10-31 P2、Q1 の指示で記録だけ、着手しない）: dw-mmc を IDMAC（controller の内蔵の DMA、Linux の dw_mmc と同じ）に切り替える。
  FIFO を CPU が読まないので card clock が止まらず、49.5 MHz の high speed と sample phase の tuning（BUG-340 の hook）が生き、preemption を
  止める時間（128 block で約 5 ms）も無くなる。要る物: descriptor の ring（HCON の address の幅を読む。板の RAM は 4 GiB を越える番地にあるので
  64 bit の descriptor か、32 bit なら 4 GiB 未満の bounce）、data の buffer の cache の保守（JH7110 の DMA は非 coherent の見込み、ccache の
  flush）、host 試験の偽の controller の IDMAC。
- 10 回の起動の確かめ（2026-10-31 05:45〜05:57、kernel cksum 89526334 = 912e43c1f ＋ visionfive2.c の log の一行、`boot-cycle.sh` の LOAD で
  各起動に p5 の生の 64 MiB の読み）: 10 回とも SSH 31〜36 s、`CPUs ready: 4`、root は live（`firmware: file failed`・`refuses writes`・
  `did not come back`・`a block at a time` は 0）。SD の読みの失敗は 0・0・0・1・0・1・1・2・1・1 回（計 7、全部 status a4、全部 try 2 か 3 で通った、
  card clock は 24.75 MHz のまま）。64 MiB の読みは毎回 6.12〜6.13 s（約 10.9 MB/s）。直す前の main の kernel は同じ数え方で毎起動 5〜17 回
  （計 88 回、9 起動）。証拠 `/tmp/p2-vf2bugs/runF/`（git の外）。
