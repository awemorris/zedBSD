# BUG-379: Pi 4 の graphical login の session の中で、compositor の描画が止まる・約 1 fps になる（720p で videoplayer 約 1 fps、1080p で session が 1 frame も描かない）

- 状態: open（2026-10-31 22:51 P7 の直し A・B・C が main に（c3291b1f9）。QEMU の amd64・raspi4b で forkrace PASS、直す前の kernel で再現。Pi 4 の実機の session の確かめは P4）
- 発見: 2026-10-31 P2（WS309 p015 の Pi 4 の試験、10.0.30.6、1280x720 の出力、1080p30 の H.264 High の試験の clip）。
- 症状: login=graphical の session（`/bin/wayland --session`）の中で videoplayer を window でも全画面でも動かすと、15 秒で 17〜18 frame、acquire_us 約 98 万。
- 比べ: session を使わず compositor を自分の socket で動かす（console の login、`--desktop-client=none`）と、zero copy の前（main ea4317337）も後も 360 frame のうち 352〜358。
  session の中では zero copy の前の compositor・libvulkan・libwayland-client・libkeiland でも同じ約 1 fps → WS309 p015 の回帰ではない（前から）。
- 疑い（未確かめ）: session の構成（`--session`・glass などの合成の負荷、session の client）で swapchain の image が返らない、または compositor の frame が約 1 秒ごと。
- 影響: Pi 4 の desktop で動画が実用にならない。

## 1920x1080 では全く描かない（2026-10-31 P4、ws291-p025）

- login=graphical（autologin、/etc/keiland/session、--log-frames）の session の compositor は 1 frame も描かない: session.log に
  `KWL RENDER stalled waited_ms=1001..185056 want=1 number=1 ready=0 ... thread answer=0 busy=0` が繰り返し（render の thread が出力の chain の
  vkAcquireNextImageKHR で TIMEOUT を回る）、`KWL LAT draw` 0 行、flip の perf の行 0。`display lease 1 claimed` の後も core の clock が 137.6 MHz のまま
  （動く run では最初の flip で 500 MHz）。
- 板の元の main の kernel（eff578c、424397698）でも同じ → P4 の driver の変更の前から。
- 同じ /bin/wayland を console の起動から root で `--glass --wallpaper --log-frames` で動かすと普通に描く（静止で 15 s に 12〜13 回、stall 0）。

## 原因（2026-10-31 P4 と bug-analyzer、Pi 4 の実機で測った）

- kernel の fork の livelock: `src/kern/vm/vmspace-fork.c` の vmspace_fork() は PTE の写しの batch ごとに VM の lock を外し、source の generation が変わっていれば
  写しを最初からやり直す（EAGAIN、304 行あたり）。generation は普通の page fault の成功でも進む（vmspace-fault.c 461・659 行あたり、vm/device.c 465 行あたり）。
  fork は親の page を COW の読みだけにするので、親の別の thread が書くたびに fault → generation → fork がやり直し、書く thread が居る限り終わらない。
- aarch64 の posix_spawn は fork を使う（libc posix.c 8814 行あたり、vfork の道は x86_64 だけ）。compositor の io-file の thread が `settings --welcome` を
  spawn すると fork が約 10 秒〜無限に止まる。その間 __pthread_fork_prepare が rtld の loader の lock を持ち、libvulkan の present_worker_get()（wsi-swapchain.c
  4132 行あたり）が global の swapchain_mutex を持ったまま pthread_create → loader の lock を待つ。render の thread の swapchain_acquire は swapchain_mutex を
  時間の上限なしで待つ → frame が出ない（KWL RENDER stalled）。App Home の検索の 0 件も、同じ io-file の thread の後ろに並んだため。
- 証拠: 計測の run で fork の syscall 10.25 s、pthread_create 10.09 s、50 ms の上限の vkAcquireNextImageKHR が 10.147 s で戻る。最小の再現（forktest）:
  64 MB の fork は書く thread 無しで 160〜196 ms、書く thread が 1 つ回ると 15〜30 s で戻らない。資料: `/home/awe/zedBSD-worktrees/p4-ws291pi/build/tmp/bug379/`。

## 直す方針（Q1 の決定）

- A（根、kernel の VM、HAL ではない）: fork が fault だけの generation の進みでやり直さない形にする（fork の写しの間 fault・map が待つ、または map・unmap・protect・
  split だけで進む「配置の generation」を分けて fork はそれを見る）。
- B（libc）: aarch64 でも vfork の posix_spawn（kernel の process_vfork は arch に依らない）。
- C（libvulkan）: present_worker_get で swapchain_mutex を持ったまま pthread_create しない。
- A・B・C を全部入れる（A が正しさ、B・C は露出を減らす）。
- 前の見立て（root でない uid が引き金、render の thread が TIMEOUT を回る）は誤り。引き金は compositor が desktop の client の後に次の program（`settings --welcome`）を spawn すること。
  root でも desktop の client が付けば止まり、user でも `--desktop-client=none` なら描く。
