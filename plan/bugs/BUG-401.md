## 原因（2026-11-02 P8）

クラウドのセッションの commit を git archive の host の build で 1 つずつ試して 2 つに絞った（`build/tmp/p8/bis/` の各 tree の result.txt）。2a8742d542・75b246262f・b25521e077 は 10 本とも基準と同じ、fb96608902 で host-range-* の 4 本、449325eefd で残りの 6 本が落ちる。

1. fb96608902（custom elements の prelude）: 読み込みの時から document を MutationObserver（subtree・attributes）で見ていた。配られる前の record が removedNodes として外した node を持ち、試験が microtask を回さずに collect すると、外した node と（node から届く）子の Document が残った。
2. 449325eefd（iframe の window の proxy と制限した見え方）: `contentWindow` と `event.source` が、親の realm の prelude が作る proxy になった。
   - proxy を element ごとに 1 つにする表が `WeakMap` で、この VM の WeakMap は key を強く持つ（ephemeron が無い。js/builtin_collection.c の注）。親の realm が、一度でも contentWindow を見た iframe の element と、proxy の閉包の `last`（子の window）を永く持った。method を束ねる `bound`（window を key にした WeakMap）も同じ。
   - host-frame-lifetime の segfault（139）: 保存した contentWindow（proxy）の trap は親の realm の閉包で、embedding が親の realm を `vm_realm_destroy` で壊した後に呼ばれ、解放済みの window を読んだ（`prelude_frame_window`）。今までの約束は「子の window はそれ自身の realm の物で、親の realm より長く生きられる」。
   - 調べ方: debug 用の tree（`build/tmp/p8/dbg/`、commit しない）の heap に「どの cell から mark されたか」を記録する道具を足し、host-error-events で子の Document の保持の鎖を出した（root → array → record → removedNodes → iframe の wrapper → element → proxy → 閉包 → 子の realm → Document）。

## 直し（agent/p8-bug401、5b546f3210）

- `plan/ws074/phase230/prelude.js`（と生成した `bind/prelude-source.inc`）:
  - custom elements の observer は最初の `customElements.define` から document と shadow root を見る。それより前に attach された shadow root は `early` に置き、define の時に見始める。
  - frame の proxy の `proxies`・`bound` の WeakMap を外した。束ねた method は proxy の閉包の中の Map（今の window が変わると作り直す）。
- `dom/dom.h`・`dom/node.c`: `dom_element.frame_proxy`（traced）。`bind/frame.c` の `bind_window_view` が proxy をここに置き、2 度目からはそれを返す。`frame_remove_subtree` が element が文書を離れる時に外す（外した element・proxy が子の文書を生かさない）。
- `bind/frame.c` の `bind_window_view`: proxy を使うのは、親が子に届かない frame（別の origin、opaque な origin）だけ。親が届く（同じ origin の）frame は子自身の global を返す（449325eefd の前の形）。

変えた振る舞い: 同じ origin の iframe が別の文書へ移った時、前の `contentWindow` と後の物は別の物になる（449325eefd の前と同じ。host-frame-load の「actual replaced collectible realm and retired initial owner」がこれを確かめる）。別の origin・opaque な frame の proxy は今までどおり文書を移っても同じ物。クラウドの WPT の数（dev188）で同じ origin の proxy に頼った物があったかは未確認。
