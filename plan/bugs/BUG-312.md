# BUG-312: 起動の時に root の UFS が壊れていると read-only で mount され、fsck して rw にしない

- 状態: reproduced（実機、ユーザー）/ closed の案（2026-10-31 q1761 P2、QEMU。実機の T-C は未実施）。元: scheduled（2026-10-14 Q1、P2）
- 発見: 2026-10-14 夜、Pi 4（10.0.30.2）で WS236 の試験の kernel が止まった後、電源を入れ直すと root が RO で mount されていた。ユーザー「Pi4はイメージが壊れてROマウントになっていたので、書き直して起動しました。」「RO mountは動作中に壊れたらRO remountならわかりますが、ブート時にROなのは使いづらいです。fsckしてRWにするべき、というバグフィックスはできそうですか？」
- 期待: 起動の時に root（と他の UFS）が clean でなければ、mount の前に fsck（または journal の replay と修復）をして、直せたら rw で mount する。直せない時だけ RO にして、理由と回復の手順を画面と log に出す。
- 関連: BUG-307・BUG-308（UFS の journal）、WS072（UFS の format の lease）。
- 追加（2026-10-14 ユーザー）: 「しかも、ジャーナリングFSを書き込み途中で電源断したところで、修復できずにROマウントなのは、明らかにバグです。」→ 起動の時の fsck に加えて、電源断の後に journal の replay で直らず RO になった原因そのものを直す。壊れた image はユーザーが書き直したので証拠は無く、QEMU の電源断の繰り返しで再現する。
- 役割の分担（2026-10-14 ユーザー）: 「journal replayはカーネルの役目、それでもROマウントになったら/sbin/fsck (これはstatic link)して、re remountするのがinitの役目、という感じですね。」

## 調べた結果（source の読み、P2 2026-10-14）

壊れた image が無いので、確定ではなく source から見た経路。

### 起動の道（Pi 4）

- Pi の cmdline.txt は `login=...` だけで root を名指ししないので、kernel は **legacy autoroot**（`src/kern/vfs.c` `vfs_mount_legacy_root`）を使う。
- legacy autoroot は、boot partition の隣の partition を 1 つずつ **read-only の private mount** で開いて、`etc/zedbsd-root` の marker を読む（`ufs_root_marker_matches`）。
  - その mount が `EINVAL`・`EROFS`・`EOPNOTSUPP` で失敗すると、何も log に出さずに「root ではない」と扱う。
  - root が見つからないと、ARM の image overlay（FAT の `/rootfs.img`、UFS root の image には無い）を試し、それも無いと **FAT の boot partition を root にする**。
- 見つかった UFS root は rw で mount する（`mount_root_create("auto", 0, ...)`）。kernel が root を RO で mount し直す道は無い。rw の mount が失敗すると起動が止まる。
- amd64 は `rootpart=` の native root で、marker の probe が無い。WS063 の `plan/tools/ufs/root-crash.sh`（電源断と replay の試験）は amd64 の native root だけを試しているので、Pi の道は試されていない。

### 見つけた不具合（確実なもの）

1. **v3 の journal の volume は、read-only の mount で summary が group の数とずれていると EINVAL で失敗する**（`ufs_mount_impl`）。
   - 「journal の無い volume は clean のはず」という検査が `ms->journal_enabled`（v2 の tail journal）しか見ない。
   - v3（batched journal）の volume は `journal_enabled` が 0 で、write cached の rw の mount（root）だけが免除されている。
   - write cached の root は、電源断で summary が group の数より遅れる（同じ関数の注記「a crash can leave the totals behind the groups' own counts」）。
   - よって **電源断の後の Pi では、marker の probe（read-only）が EINVAL で失敗し、UFS root が「無い」ことになる**。
2. **marker の probe の失敗が log に出ない**。UFS の superblock がある partition が mount できなくても黙って飛ばす。
3. **v3 の replay は、最新の commit の descriptor・payload の checksum が合わないと EINVAL で mount 全体を失敗させる**（`j3_replay` → `j3_replay_slot` → `j3_payload_apply`）。
   - 「record は durable、payload は未完」の commit は、完了しなかった commit なので捨てて、前の commit（もう一方の slot）に戻すべき。
   - BUG-307 の bec395969 の注記は、修正の前の kernel にこの窓（record が payload より先に durable）があったと書いている。Pi の kernel はその前の build の可能性がある。
4. ufs の mount の失敗（metadata の領域の free の bit、root inode が無い、summary、replay）の理由が log に出ない。`j3_load` の EINVAL（journal を作り直す）も黙っている。

### 走っている時の RO

`stop_writing`（ufs.c の 43 か所）は、走っている時の失敗で volume の書き込みを止め（`EROFS`）、log に「the volume refuses writes until it is mounted again」と理由を出す。
ユーザーの見た「RO」がこれだった可能性も残る（次の mount では書ける）。

### fsck と remount

- userland に fsck は無い（`userland/base` に無く、`mount` に remount（`MNT_UPDATE`）も無い）。
- kernel にも RO → RW の remount は無い。
- host の検査（`tools/build/check-ufs-image.py`、298 行の python）は到達性・block の所有・bitmap・link の数・summary・directory を検査するが、直さない。

役割の分担はユーザーの 2026-10-14 の指示のとおり。kernel は replay と、直せる不整合の修復。init は RO の root に fsck。

## ユーザーの判断（2026-10-14、Q1 経由、クリック）

1. fsck で直した後は **reboot する**（R1 の remount は作らない。FreeBSD の rc と同じ）。
2. 修復する `/sbin/fsck`（F1、static）を **ベータ 2 に入れる**。

順は K1〜K4 → I1 → F1（host で image を壊す試験つき）→ T（電源断の繰り返し、T1 の手順）。

## K1〜K4（P2、2026-10-14）

- K1（`src/drivers/fs/ufs.c` `ufs_mount_steps`）: summary の合計が cylinder group の数と合わない時は、group の数を使う。
  - 拒む（EINVAL）のは、journal の無い volume を write cached でなく rw で mount する時だけ。
  - v3 の journal（`ms->j3.present`）、write cached、read-only の mount では作り直す（read-only では memory の中だけ）。
  - 前後の値を log に出す。
- K2: `ufs_mount_impl` を wrapper にし、本体（`ufs_mount_steps`）が実行中の段を名指しする。失敗の時に 1 行 log を出す。
  - 書式は `ufs: <disk>: the volume cannot be mounted read-only|read-write: <段> (error N)`。UFS でない disk（EOPNOTSUPP）は出さない。
  - `j3_load` が journal を作り直す時の log も出す。
  - `src/kern/vfs.c` `ufs_root_marker_matches`: UFS の volume が read-only で mount できず root の候補から外す時に log を出す。
- K3（`j3_replay`）: 最新の commit の record が封じた descriptor・payload が合わない（EINVAL）時は、完了しなかった commit として捨てて log に出す。
  - もう一方の slot が未適用ならそれを適用する。I/O の error は今までどおり mount の失敗（log つき）。
  - 検査は新しい `j3_replay_sealed` にまとめた（descriptor の大きさの検査を含む）。
- K4（`src/kern/vfs.c` `vfs_mount_root_volume`）: native root と legacy autoroot の UFS root は、rw で mount できず read-only なら mount できる時、read-only で mount して起動を続ける。
  - console と log に `it is mounted READ-ONLY, and init checks it with fsck` を出す。
  - ENXIO・EOPNOTSUPP・ENOMEM・EBUSY は試し直さない。

- build: `make -j16 ZEDBSD_CONFIG=config/ci/config-amd64.mk BUILD=build/bug312 build/bug312/vmunix` rc=0、warning 0。
- build: `make -j16 ZEDBSD_CONFIG=config/ci/config-rpi4.mk BUILD=build/bug312-rpi4 build/bug312-rpi4/vmunix` rc=0、warning 0、`arm64 vmunix check: PASS`。
- host の試験: 無し。kernel の ufs.c を host で動かす harness が無い（BUG-307 と同じ）。
- QEMU・実機: 未実施。電源断の試験（T）は T1 に依頼する。

## I1・F1（P2、2026-10-14〜15）

- I1（`userland/base/init/root-check.[ch]`、`main.c` から最初に呼ぶ）: 起動の最初に root を調べる。
  - kernel の mount の表（`KERN_SYSTEM_GET_MOUNTS`）で、root が UFS で read-only なら、console に理由を出して `/sbin/fsck -y /dev/<disk>` を流す。
  - fsck の終了の値で分ける。
    - 4（直した）: `sync` して `KERN_SYSTEM_REBOOT`。
    - 0（直す物が無い）、8（直せない）、実行できない: RO のまま。理由と回復の手順（`dmesg | grep -e ufs: -e vfs:`、`fsck -y`、image の書き直し）を console に出す。
- F1（`userland/base/fsck/`、class static、`/sbin/fsck`）: `fsck [-n | -y] device`。終了の値は 0 clean、4 直した、8 残った。`-y` の後に書かない検査をもう一度して clean を確かめる。
  - pass 1: 割り当て済みの inode を調べる。
    - mode の種類、長さ、nanosecond、directory の長さ、属性の領域と pointer、block の範囲と重複（先の inode が持つ）、block の数。
    - kernel の `decode_inode_raw` が拒む物を直すか、clear する。
  - pass 2: root からの walk。record の破損、`.`・`..`、空き inode への entry、directory の 2 つ目の名前、entry の type、参照の数え上げ。
  - pass 3: 届かない物をつなぐ。
    - directory と link の残る file は `/lost+found/#<inode>` へ移す（`/lost+found` が無ければ作る）。
    - link 0 の file（開いたまま消された物）は解放する。
  - pass 4: link の数。
  - pass 5: inode の block を数え直し、各 group の inode・free の map と数、superblock の合計を作り直し、clean の flag を立てる。
  - journal の file と file system の後ろ（v2 の journal、snapshot）には触れない。kernel の replay の後で流す前提（init の流れ）。
- 置き場所: amd64・arm64 の image には必ず入る（top の `Makefile` の essential の後、static の class を link できる platform だけ）。
  pcat・pc98・x68k・sparcv9 には入れない（static の class の build の規則が無い）。
- host の試験 `plan/tools/ufs/fsck-host-test.py`: zedimage-host の 24 MiB の volume を 15 通りに壊し、それぞれ次を確かめる。77 件 PASS。
  - `-n` が 8 を返し、image を変えない。
  - `-y` が 4 を返す。
  - その後の `-n` が 0 を返す。
  - host の validator（`tools/build/check-ufs-image.py`）が通る。
  - 残るべき file の中身が残る。
  - 壊し方: superblock の合計と clean、group の数、使用中の block を free に、free の block を使用中に、link の数、空き inode への entry、
    名前の無い file、名前の無い directory（subtree ごと）、block の重複、data の領域の外の block、directory の record の破損、
    種類の無い割り当て済み inode、link 0 で割り当てたままの file、nanosecond、誤った `..`。
- build: amd64・rpi4 の `bin/fsck`（statically linked）・`bin/init`、vmunix、どれも rc=0・warning 0。
- 規約: `plan/tools/style-check.py` は fsck・root-check の全部の file と、ufs.c・vfs.c の変えた行で違反 0。

## 残り（P2）

- 実機・QEMU は未実施（上の T1 の依頼）。
- fsck の限界:
  - 壊れた cylinder group の header（magic・番号・大きさ・map の位置）と root の inode は直さない（8 を返す）。
  - 壊れた primary の superblock を予備から戻さない。
  - 重複の block は後の inode を clear する（FreeBSD は両方を clear する）。
  - `-y` の後に kernel が未適用の journal の commit を持つ volume（init の流れの外で手で流した時）は、次の mount の replay が直しを上書きしうる。
    init の流れでは kernel の read-only の mount が replay を済ませている。
- 同じ volume で fsck が直しても kernel が rw にできない（fsck は 0 を返す）場合、init は RO のままにして理由を出す。reboot の繰り返しは起きない。
  fsck が毎回直して（4）kernel が毎回拒む組み合わせが残ると reboot が繰り返す。見つけたら BUG にする。
- 道具の登録: `plan/tools/ufs/fsck-host-test.py`、`root-powercut.sh`、`damage-root.py` を master.md の Tools に載せることを Q1 に頼む。

## T-B（T1-639、T3、2026-10-15）FAIL は試験の道具の誤り

- T3: damage-root.py 321 1024 の image で 1 回目の起動から root は rw、fsck・READ-ONLY の行なし（2 回同じ）。T3 の「guest の書き込みが disk に出ない」は guest.py が disk の複写で起動するため（`plan/tools/guest/guest.py` の disk.img）で、異常ではない。
- 原因（Q1、source から）: kernel の orphan の scan（`src/drivers/fs/ufs.c` の orphan_scan_locked）は link count が 0 の inode だけを読む。damage-root.py は link 1 の inode を作っていたので scan に掛からず、rw の mount が成功した。kernel・init の誤りではない。
- 直し: damage-root.py の inode の link count を 0 に（Q1）。T-B を同じ手順で再試験する。
- T-B 再試験（T1-648、T3、2026-10-15、QEMU amd64）: **PASS**。1 回目の起動で `cannot be mounted read-write: recovering orphaned inodes (error 5)`→`mounted READ-ONLY`→ init が `/sbin/fsck -y`→`inode 702 was unlinked but is still allocated; it is freed (repaired)`→ reboot（QEMU の -no-reboot で終了）、2 回目は rw で login。/lost+found が無いのは link 0 の orphan を fsck が解放したためで正しい（Q1）。reboot の行は screendump に撮れず間接の確認。PNG `build/review/bug312-tb-fsck.png`。実機（Pi の SD、T-C）は未実施。

## 2026-10-31 P2（q1761-i01）: 今の main で QEMU の再確認、closed の案

image: main 4fd802a15 の tree、package を含まない amd64 の lean な image（serial の console、BUILD は /tmp、root は 321 MiB から 1024 MiB）。
QEMU は KVM・UEFI・NVMe、disk は写しに直に書く（snapshot なし）、`-no-reboot`。guest の操作は serial の console（serial.py）、判定は volume の host の検査と guest の命令の答え。

- T-B（read-only の root と init の fsck、K4・I1・F1）: **PASS**。
  1. `damage-root.py 321 1024` の後の写しを host で検査: `check-volume.py` が `orphan allocated inodes: [509]` で失敗（壊れていることの確認）。
  2. 1 回目の起動: 何も操作せずに QEMU が自分で終わった（guest の reboot、`-no-reboot`）。
  3. 1 回目の起動の後・2 回目の前の写しを host で検査: `UFS OK`（1 回目の起動の中で fsck が直した間接の証拠。kernel の rw の mount はこの壊し方では通らない）。
