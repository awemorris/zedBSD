# BUG-280: App Home への遷移が Linux の driver より滑らかでない（fps が半分〜75% くらいに見える）

Reproduction: reproduced（ユーザー、実機 5330、2026-10-10 UAT）
Disposition: tracking（2026-10-10 ユーザー、クリック「ベータ2 は既知の問題（推し）」→ release notes の既知の問題に書き、5330 で Linux と zedBSD の frame の時間を測った後に WS139（ベータ3）で直す）
Discovery: 2026-10-10 ユーザーの 5330 の UAT のコメント（image はユーザーの 5330 に入っていた物、版は未確認）
Handling: WS094・WS139（desktop の速度、i915）。原因の調べから

## 観測（ユーザー）

「App Homeへの遷移は、Linuxドライバよりなめらかさがない。たぶんfpsが半分か75%くらいになってる。LinuxではMesaがテクスチャを小さくしたり最適化してる？」

## 調べ（2026-10-10、P1、source だけ。実機の計測は無い）

App Home の開閉（`userland/desktop/wayland/home.c` `kwl_home_draw`、edge.c の奥行き）の 1 frame の仕事: 全画面の stage（`MODE_GLASS`、ぼかしは起動の時に CPU で作った 1/4 の壁紙を引くだけで frame ごとのぼかしは無い）、縮む desktop の層（全部の窓の texture を縮めて描く、mipmap は無い）、Home の content を層として（`layer_on`）、時計と最大 24 の icon。
compositor の code は Linux（keiland-linux、Mesa の ANV と Linux の KMS）と同じなので、差は GPU の driver と表示の経路にある見込み。候補:

1. **frame が vblank に間に合わず 2 vblank かかる**（「半分」に合う）: 1 frame の GPU の時間が 16.7 ms を少しでも越えると 30 fps。zedBSD の i915 の Vulkan の経路が ANV より遅い所（render の圧縮（CCS）や tiling の違い、縮小の sampling の帯域）が効く見込み。
2. **GPU の clock**: zedBSD の i915 の RPS（`src/drivers/gpu/i915/gt-power.h`、ws075-p020）は負荷を見て上げるが、0.3 秒ほどの短い遷移では上がる前に終わり得る（Linux は待ちの boost と短い評価の間隔）。
3. **present の待ち**: compositor が前の frame の fence を待ってから次を描く形なら、render と表示が重ならない。

測り方（実機、Q1 か T1。両方の OS で同じ遷移を 20 回）: compositor の `KWL PERF compose frames=… draw_ms=… frame_ms=…`（`userland/desktop/wayland/main.c`、5 秒ごとの行）を Home の開閉を繰り返す間に取る。zedBSD では i915 の RPS の今の周波数（debug の口があれば）も。frame_ms が 16.7 を越えていれば候補 1、frame_ms は短いのに fps が低ければ候補 3、遷移の初めだけ遅ければ候補 2。

ベータ2 で直せる範囲か: 原因を測る前に直すと外れる。安く試せるのは (a) 遷移の間だけ desktop の層の窓を小さい縮小の copy で描く（帯域を減らす）、(b) 遷移の開始で RPS を boost する（i915 の driver、HAL ではない）。どちらも 5330 での計測の後に決めたい（WS139 ベータ3 の範囲）。推し: ベータ2 は既知の問題に書き、5330 の計測（上の手順）だけを UAT の合間に行う。
