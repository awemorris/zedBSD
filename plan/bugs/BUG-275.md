# BUG-275: Settings の Bluetooth の頁で 5330 に Bluetooth の device が無いと出る

Reproduction: reproduced（ユーザー、実機 5330、2026-10-10 UAT。Q1 が SSH で確かめた）
Disposition: scheduled（2026-10-10 直し 71e4c3c0d、5330 で Bluetooth が ready。ユーザーの Settings の確認で close）
Discovery: 2026-10-10 ユーザーの 5330 の UAT のコメント（image はユーザーの 5330 に入っていた物、版は未確認）
Handling: WS143（release の config に intelbt を入れた後の image か要確認。controller の attach・firmware の load・bluetoothd の起動の順に SSH で見る）

## 観測（ユーザー）

「Settingsで、Bluetoothデバイスがないと言われる」

## 経路の見直しと原因の候補（2026-10-10、P1、source だけ。5330 に SSH が届かないので実機の log は無い）

経路: release（`config/release/config-amd64-beta2.mk`）と UAT（`config/current-uat.mk`）の config は CI の config（`CONFIG_DRIVER_USB_BT := y`、`bluetoothd`・`bt`）に `intelbt-firmware`（`/lib/firmware/intel/ibt-0040-0041.sfi` ほか、Solar の 3 組）を足す。
base の `/etc/passwd`・`/etc/group` に `_bluetooth`、`rc.conf` で `bluetoothd` enabled。kernel の `usb-bt` は interface の class E0/01/01 で付き（vendor の表ではない）、`bt-hci` が `/dev/bluetoothN` を作る。
bluetoothd の子は 2 秒ごとに `/dev/bluetooth0..15` を親に開けさせ（`privsep_open_node`）、開けたら Intel の版を読み、bootloader なら `.sfi` を送り、controller の再起動（USB の付け直し）を 10 秒待つ。
Settings の言葉は `userland/desktop/settings/page-bluetooth.c` の `bluetooth_state_words`: socket に届かない「Bluetooth is not available on this computer.」、STATE none「No Bluetooth adapter was found.」、firmware「The adapter's firmware is missing.」、compositor に Bluetooth が無い「This desktop has no Bluetooth.」。
ユーザーの「デバイスがない」は none の言葉の見込み（言葉の確認はユーザーか PNG で）。

none になる道（可能性の高い順）:

1. **firmware の load の後に controller が戻らない・start が 3 回失敗**: 5330 の実機の load は一度も確かめていない（WS143 p003 i02 と p005 i04 は未着手、T1-378 も未実施）。load の後 controller は USB で付け直る（`BTD_REAPPEAR_MS` 10 秒）。xHCI がこの付け直し（同じ port の disconnect と connect）を拾わなければ node が消えたまま none。start が `BTD_FAILURES_MAX`（3）回 ERROR なら止まる（その間は none と error を行き来）。
2. **usb-bt が付かない**: 5330 の 8087:0033 が zedBSD の xHCI に列挙されているかの証拠が無い（Linux では列挙、plan/ws075/phase011）。CNVi の Bluetooth は AX211 の Wi-Fi の半分と同じ包みで、`intel-ax211` の Wi-Fi の driver の reset が Bluetooth の USB の側を切る可能性も（推測）。
3. **古い image**: ユーザーの 5330 の image が `intelbt-firmware` を足す前（2026-10-09 より前）なら firmware の言葉か none。

確かめ（5330 に SSH が届いた時、Q1 か T1）: `uname -a`（image の版）、`lsusb`（8087:0033 の有無）、`dmesg | grep -i -e usb-bt -e bt-hci -e 8087`、`ls -l /dev/bluetooth*`、`grep bluetoothd /var/log/messages | tail -30`（`state=` の行と `closed` の行、secure send の答え）、`bt show`、`ls /lib/firmware/intel/`、`service status bluetoothd`。
候補 1 なら `bluetoothd: /dev/bluetooth0 state=lost …` の後に node が戻らない行、候補 2 なら dmesg に usb-bt の行が無い。

直し: source だけでは原因を決められないので、この時点では直していない（上の log の後に直す。WS143 の p003 i02 の実機の門と同じ作業）。

## 2026-10-10 Q1 の SSH の確かめ（5330、image `1.0.0-beta2+ga42a544`、2026-10-09 の a42a544、intelbt-firmware 入り）

- `lsusb`: 0bda:8156（RTL8156 の USB LAN）、0c45:6d1d（camera）、0a5c:5842（Broadcom の指紋・smartcard）、30de:6545（USB stick）。**8087:0033 が無い**。
- `/lib/firmware/intel/ibt-0040-*.sfi・.ddc` などはある（firmware は image に入っている）。bluetoothd は走っていない、`/dev` に Bluetooth の device が無い。
- kernel の log（dmesg）:
  - `xhci: port 10 reset complete portsc=00000603`
  - `usb1: port 10 enumeration failed (3)`
  - usb1 は PCH の xHCI（8086:51ed、16 port）。port 10 は Alder Lake の CNVi の Bluetooth の USB2 の port。
  - portsc 0x603 = 接続・有効・**full-speed**（speed 1）。他の device はどれも high-speed（0xe03）か SuperSpeed（0x1203）で、enumerate できている。
- 見込み（未確認）: zedBSD の xHCI の **full-speed の device の enumerate**（EP0 の最大 packet の扱い: full-speed は最初 8 か 64 で読み、bMaxPacketSize0 で Evaluate Context）が失敗している。5330 の他の USB に full-speed の device は無い。P1 の候補 (2) に当たる。

## 原因と直し（2026-10-10、P1、agent/p1）

- **原因**（source と仕様の照合で特定、実機の確かめは未実施）: 「enumeration failed (3)」の 3 は `EINVAL`（`include/uapi/errno.h`）。full-speed の手順（8 byte の device descriptor、Address Device、18 byte の読み直し）は EINVAL を返さず、xHCI の command の失敗の log も無い。EINVAL を返すのは configuration descriptor の読み（`parse_configuration`）で、**endpoint の wMaxPacketSize が 0 なら EINVAL** にしていた。USB の Bluetooth の controller は interface 1（voice、isochronous）の alternate setting 0 の endpoint 0x83・0x03 の packet の大きさを 0 にする（Core 5.4 Vol 4 Part B §2.1.1 表 2.1「No active voice channels (for USB compliance)」、USB 2.0 §5.6.3 の zero-bandwidth の既定の setting）。8087:0033 もこの形の見込み（descriptor の dump は未取得）。full-speed であることは偶然（Intel の CNVi の BT は full-speed）で、Q1 の見込みの EP0 の扱いではない。
- **直し**（`src/drivers/usb/usb.c`）:
  - `parse_configuration`: packet の大きさ 0 は **isochronous の endpoint だけ**受ける（他の型は今どおり EINVAL）。
  - 新 `endpoint_zero_bandwidth`: isochronous で packet の大きさが 0 の endpoint。何も運べないので host controller に context を作らない。
  - `host_interface_enable`・`host_interface_disable`（と各々の rollback）、`configuration_reset_endpoints`・`host_interface_reset_endpoints` は zero-bandwidth の endpoint を飛ばす（xHCI は有効でない endpoint の reset に ENODEV を返すので、飛ばさないと SET_CONFIGURATION の後の reset で quarantine になる）。alternate 1 以上（packet の大きさがある）に SET_INTERFACE した時は今どおり context を作る。
- 確かめ: kernel の build（`ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/p1-uat build/p1-uat/vmunix`）rc 0・warning 0。style-check の数は変更の前と同じ（559、増やしていない）。usb.c の host の試験は無い（kernel の code）。
- 未実施: QEMU（T1）の full-speed の device の enumerate と回帰（QEMU には zero-bandwidth の isochronous を持つ device の model が無いので、この直しの本体は再現できない）、5330 の実機（Q1 が kernel を入れ替えて `lsusb` に 8087:0033、dmesg に `usb1: device … port 10 8087:0033 … configured`、その後 usb-bt・bt-hci、bluetoothd の firmware の load を見る）。

## 2026-10-10 5330 で確かめた（Q1、SSH、ユーザーの許可で kernel だけ入れ替え）

- 原因（P1）: usb.c が packet の大きさ 0 の endpoint を拒み（EINVAL＝3）、USB の BT controller の interface 1 の alternate 0（voice の isochronous、仕様で 0）で configuration 全体が失敗していた。full-speed は無関係。直し 71e4c3c0d。
- current-uat の vmunix（cksum 2331853835）を ESP に書いた（前は vmunix.old、cksum 1520312265）。ESP の書き込みで SSH は止まらなかった（約 28 s、BUG-269 の直しが効いている見込み）。
- 再起動の後: `lsusb` に 8087:0033、dmesg `usb1: device 4 port 10 8087:0033 class e0 configuration=1 configured`、`usb-bt: … interface0`、`/dev/bluetooth0`、`bt show` が `STATE ready`・`firmware=loaded`・`POWER on`、bluetoothd が `READY state=ready`。
- 残り: ユーザーが Settings の Bluetooth の頁と HID の機器の pairing（WS143 の UAT B1〜B14）を確かめる。
- T1-519（QEMU）: boot・usb-kbd・usb-storage・usb-audio・usb-ccid は enumerate、`enumeration failed` は 0。usb-serial（FTDI 0403:6001）だけ出ないのは回帰ではなく試験の QEMU の指定（usb-serial は auto_attach=0、`-chardev null` は open を報告しないので attach されない、P1 の source の読み）。
