# BUG-261: 5330 の touchpad の GPIO の割り込みが起動の後に止まり、4 ms の polling に戻る

- 状態: reproduced（5330 bare metal の log、2026-10-08） / resolved（2026-10-08 夜 ユーザー「下記は実装の変更が多かったので、いったんすべてcloseします。」、Q1 の中継）
- 発見: 2026-10-08 P1 の q874（ベータ2 の Phase の洗い出し）の読み。
- 証拠: [BUG-258 の dmesg](BUG-258/dmesg-5330-20261008.txt):788-789 `intel-gpio: irq 14 fired for no pad; given up` → `i2c-hid: \_SB_.PC00.I2C1.TPD0: the interrupt was given up; watches its line`。BUG-253 の kernel-5330.log:628 にも同じ。
- 期待: touchpad（I2C HID）は GPIO の割り込みで動き続ける（WS159 p006・WS183 p001）。
- 観察: 共有の IRQ 14 が「どの pad も立っていない」発火を受けて割り込みを諦め、4 ms ごとの監視に戻る。タップの遅れや電力に影響しうる。
- 推定の原因（未確認）: firmware が有効にした別の pad が同じ IRQ 14 で発火している（src/drivers/.../intel-gpio.c:575-620 の判定）。
- 関係: WS159 p006、WS183 p001（同じ intel-gpio.c を触る、順を揃える）、BUG-247。

## 解析（2026-10-08 夜、P2 q876、code の読み。実機の log は未取得）

今の handler（`irq_interrupt`）は、driver の pad（GPI_IS と GPI_IE の両方が立つ物）が 1 つも無い firing を **1 回で** 「no pad」とし、IRQ 14 を永久に mask する。原因の候補は 2 つで、今の log からは区別できない。

1. **level の線の再配送（有力）**: handler は pad の GPI_IE を落とし GPI_IS を消すが、どちらも posted な MMIO の write で、読み戻さずに EOI を送る。write が GPIO の controller に届く前に EOI が IOAPIC に届くと、線（active low、level）はまだ立っていて IOAPIC が同じ割り込みをすぐ再配送する。2 回目の handler の read は先の write を追い越さないので GPI_IE は 0 に見え、「no pad」→ 諦める。2 つの log とも、諦めたのは desktop が出た直後（利用者が最初に touchpad に触る頃）で、確率的に最初の数回の touch で起きる形と合う。Linux の pinctrl-intel の handler は何も無い時 IRQ_NONE を返し、kernel は 10 万回中 99,900 回の空振りまで線を止めない。
2. **firmware が有効にした別の pad**: driver は自分の pad の GPI_IE の bit だけを立て、他の bit を触らない。firmware が GPI_IE を残した host-owned の pad の event で線が立てば、driver の pad では説明できない。Linux は probe の時（`intel_gpio_irq_init`）全 community の全 group の GPI_IE を 0 にし GPI_IS を消す。zedBSD はしていなかった。

## 直し（`src/drivers/gpio/intel-gpio.c`、P2 q876）

- 線を取る時（`irq_take`、line の unmask の前）に `\_SB.GPCL`・`\SBRG` から controller の group（GPI_IE が controller の _CRS の memory にあり、32 pad 以下、HOSTSW_OWN が family の register の物。5330 では 15 group、`0x6b0000`・`0x6c0000` の community は範囲の外）を集め、community の page を map し、各 group の GPI_IE を 0 に、GPI_IS を消す（Linux の `intel_gpio_irq_init`）。その前に各 group の HOSTSW_OWN・GPI_IS・GPI_IE を log に出す（確認の材料）。
- handler: 自分の pad を落とした後に GPI_IE を読み戻す（write を controller に届けて線を下げてから EOI）。driver の pad が説明しない firing では、全 group の「GPI_IS と GPI_IE の両方が立つ、driver の pad でない bit」を探して止め・消し、log に pin を出す（これで説明できれば正常）。何も説明しない firing は数え、**200 回続いた時だけ**線を諦める（i2c-hid の Extended Interrupt の経路と同じ数。pad の firing で数は 0 に戻る）。最初の 1 回は log。
- `group_first`（Alder Lake の第 9 要素、Tiger Lake の表の順×32）を pad の検索と group の収集で共有（ws183-p001 の規則は変えない）。

## 5330 で確かめる log（T1・実機。5330 が戻ってから）

- 起動: `intel-gpio: GPI_IS 0x… (pins A-B): HOSTSW_OWN … GPI_IS … GPI_IE …` が 15 行（GPI_IE が 0 でない行があれば、それが原因 2 の pad）、`intel-gpio: 15 groups' interrupts turned off before the line is taken`、`intel-gpio: pin 327 interrupts through irq 14`。
- desktop で touchpad を使った後: `intel-gpio: irq 14 fired for no pad; given up` と `i2c-hid: … the interrupt was given up; watches its line` が**無い**こと。`intel-gpio: irq 14 fired for no pad; the line stays taken` は出てもよい（原因 1 の再配送が起きた印。続けて given up が無いこと）。`intel-gpio: irq 14: pin N (…), not a driver's pad, fired; its interrupt turned off` が出れば原因 2 の pad の番号。
- 合否: 起動から desktop で 1 分ほど touchpad を動かし tap して、given up の行が無く、動きが途切れないこと。

## 残り

- 実機の確認（上）。原因 1 と 2 のどちらだったかは上の log で分かる。
- ws183-p001（同じ file の TGL の group）は main に入っており、矛盾しない（`group_first` に移しただけ）。

## Q1 の確認（2026-10-08）

merge。全ての pad の GPI_IE を止める直しは、zedBSD に GPIO の ACPI の事象（_AEI）の口が無く、蓋・電源は EC・GPE（SCI）の経路であること、GPI_GPE_EN には触れないことを Q1 が確かめた。5330 の実機の確認待ち。
