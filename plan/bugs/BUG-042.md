# BUG-042: 新しい thread が作った thread の signal mask を継承せず、process 宛の signal で process が死ぬ

Bug ID: `BUG-042`
Reproduction: reproduced（QEMU、amd64 guest）
Disposition: resolved（ws056-p001。kernel の mask の継承と libc の worker・reaper・wake signal。process 宛の signal で死ぬ症状は消えた。console の EINTR は BUG-046）
Date: 2026-09-25
Source: ws056-p001（q423-i01）で、BUG-034 を直した `POSIX-R2.ELF` が `realtime-signal-capacity` を通った後、status 144（SIGUSR1 で終了）になったとき。
Owner: WS056 p001
Queue: q423-i01。

## 期待と観測・影響

期待: program の全 thread が SIGUSR1 を block して `sigtimedwait` で待つとき、`sigqueue(getpid(), SIGUSR1, ...)`（`mq_notify` の SIGEV_SIGNAL の通知）は pending になり `sigtimedwait` が受け取る。

観測: `POSIX-R2.ELF` は SIGEV_THREAD の timer を試験した後で mqueue の通知を試験する。timer の試験で libc が作る worker thread（`userland/base/libc/timer.c` の `timer_worker`、detached で残り続ける）は、作った thread の mask を継承するだけで program の signal を block しない。
mqueue の試験で main thread が SIGUSR1 を block して `mq_send` が `sigqueue` で process 宛に送ると、kernel は block していない worker に配り、handler が無いので既定の動作で process が終了する（status 144 = 128 + SIGUSR1 16）。kernel の選び方は POSIX どおりで、libc の worker の mask が誤り。

影響: SIGEV_THREAD の timer を一度でも使った program で、process 宛の signal を `sigwait` 系で受ける設計が壊れる（signal が worker に行って死ぬ）。

## 原因（probe で確定）

`/tmp/vitest/sigprobe`（guest の libc で cross build）: (1) 1 thread で SIGUSR1 を block して `sigqueue` → `sigtimedwait` が受け取る。(2) block しない thread を足す → 144（POSIX どおり）。
(3) 全 signal を block してから thread を作る → **144**。(5) thread が自分で全 block → 受け取る。(6) 作る側の mask `3ffffffffff7feff` に対し新しい thread の mask は **0**。
つまり kernel の `thread_create(2)`（`src/kern/syscall.c` の `sys_thread_create_call`）が新しい thread の `signal_mask` を 0 のままにし、作った thread の mask を継承しない（fork は `signal.c` で継承する）。kernel の配送そのものは各 thread の mask を見ている。

## 修正

1. kernel: `sys_thread_create_call()` で `thread_start()` の前に `thread->signal_mask = curthread->signal_mask`。
2. libc: `timer_service_start_locked()` で `pthread_create` の前後に raw の `sigprocmask` で全 signal を block・復元し、worker が全 block で始まるようにする（1 だけでは、timer を作った thread が SIGUSR1 を block していなければ worker も block しないので、library の thread として要る）。
3. libc: detached thread の reaper（`pthread.c` の `ensure_detached_reaper()`）も同じく全 block で作る。2 だけでは `POSIX-R2.ELF` はまだ 144 で、reaper が残りの受け手だった（直すと mqueue の通知を通る）。
4. libc: 1 の継承で、worker の wake signal（63、SIGRTMAX の上の予約）を worker が unblock するまでの窓に kernel の timer が発火すると、wake が main thread に配られて handler が走り `sem_wait` が EINTR（console で `thread-timer-callback errno=7`）。
   予約の signal を program の thread に見せないため、`__libc_init()` で initial thread が 63 を block（以後の thread は継承、worker だけ unblock）し、worker は callback の thread を 63 を block して作る。

## 結果（q423-i01）

1〜4 の後、`POSIX-R2.ELF` は SSH では mqueue の通知と timer の試験を通り `conformance-identity`（stdout が `/dev/console` であることを要る）まで進む。probe の全変種も通る。この ticket の症状（process 宛の signal で死ぬ）は消えた。
console（serial mirror）で走らせると `thread-timer-callback`・`thread-timer-multiple-callback` が errno 7（EINTR）で落ちる（2/2）。SSH では同じ試験が通るので、console 固有（tty・timing）の別の問題として切り分ける（ws056-p001 の記録を参照）。

## 再開の条件

`POSIX-R2.ELF` が console で status 0 になれば resolved（console の EINTR は別 ticket）。
