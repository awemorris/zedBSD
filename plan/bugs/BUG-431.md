# BUG-431: venus の display の事象を取りこぼす（idle の間の head の抜き差しが topology の番号に出ない）、IRQ の経路が事象を clear しない

- 状態: fixed（2026-11-14 01:15 P2、q2058-i01。QEMU で 2 回 PASS。起票は 2026-11-14 Q1、WS353 p002 の P1 の報告から）
- 発見: 2026-11-13 P1（q2057-i01）、QEMU（Venus、2 head、D-Bus display）。`plan/ws353/tests/qemu-display-fence.sh` の latency の step。
- 観測（P1、2 回とも同じ）: head を挿して 20 s の間、guest の `GPU_DISPLAY_EVENTS` の番号が動かない（12 のまま）。抜き差しが番号に出るのは、guest で venus の queue の割り込みが起きた時だけ。
- code の読み（P1、未確かめ）: MSI-X の時、IRQ の経路（`src/drivers/gpu/venus/transport.c`）は events_read を読むが clear しない（clear は `display.c:1502` の query だけ）。一度立つと以後の全部の割り込みで番号が上がる（余計な signal の元）。config の変化の割り込みそのものが来ていない疑い（QEMU の側か driver の側かは未確認）。
- 影響: WS353 の hotplug の fence（p002）と今の POLLPRI の経路の両方。venus では QEMU で「抜き差しから 1 s 以内」を判定できない。
- 扱い: 考える Phase（code と virtio-gpu の仕様で原因を突き止めて直す）。直したら `qemu-display-fence.sh` の latency の step を流し直し、WS353 p002 の受け入れを判定する。

## 結果（2026-11-14 01:15 P2、q2058-i01、branch `agent/p2-bug431`、基点 main c1a4e756af）

二つの別の事だった。抜き差しが番号に出ない件は試験の harness、driver の欠けは events_clear だけ。

### 抜き差しが番号に出ない件: harness（driver・QEMU ではない）

- P1 の FAIL の step（2 回の latency、1 回の race）は全部、step_start の `serial.py run` が status の印を読めず 120 s 止まった step だった（P1 の `build/ws353-p002-qemu.run.*/latency.start.txt`・`race.start.txt` に `never saw`）。program が GPU node を開くと kernel が console に `venus: context=N opened pid=` を書き、serial の console は文字単位で混ざるので、shell の `ZEDBSD-SERIAL-STATUS=0` が `ZEDBvSeDn-uSERIAL-STATUS=0s` のように崩れる。止まっている間に program の 20 s の窓が終わり、head はその後に挿されていた。
- 確かめ: main c1a4e756af の無変更の kernel で 4 回流し、印が崩れなかった step は全部 1 s 以内に起きた（latency 224・232 ms）。崩れた step だけが P1 と同じ FAIL（wait 1 回）・`passed=0`（race 1 回）になった（`build/p2-base1-qemu.run.GTeMwG`）。
- QEMU 10.0 の source の読み: `dpy_set_ui_info`（ui/console.c）→ timer → `virtio_gpu_ui_info`（hw/display/virtio-gpu-base.c）が `events_read |= VIRTIO_GPU_EVENT_DISPLAY` と `virtio_notify_config`（ISR に 0x3、config の vector へ MSI-X）を毎回送る。抜き差しの通知は来ている。

### driver の欠け: IRQ の経路が events_clear を書かない

- 仕様（Virtio 1.2 5.7.4）: `events_read` は driver が `events_clear` に 1 を書くまで立ったまま。前の IRQ の経路は MSI-X の時 `events_read` を読むだけで clear せず、config と queue は同じ vector なので、一度立つと以後の queue の割り込み（program の open の context 作りなど）のたびに番号が上がっていた（P1 の run で抜き差し 1 回に 2〜3）。display の query の経路は「上げてから clear」の順で、その間の変化を落とせた。
- 直し（176ceef8cd、`src/drivers/gpu/venus/transport.c`・`display.c`・`internal.h`）: `drv_venus_transport_display_event()` が `events_read` の DISPLAY を読み、立っていれば `events_clear` に書いてから番号を上げる（clear の後の変化は再び立って割り込みになり、起こされた読み手は clear の後に問い合わせる）。IRQ は毎回これを呼ぶ。MSI-X では ISR を読まない（4.1.4.5.2）。`display_refresh` も同じ関数を呼び、再問い合わせは `events_read` でなく「前の問い合わせの時の番号と今の番号が違うか」で決める（IRQ が clear しても query が変化を見落とさない）。

### harness の直し（fcab6b1258）

- `plan/tools/guest/serial.py`: status の印に run ごとの番号を付け（遅れて出た前の run の印を取らない）、status は shell の変数に残す。印が崩れて読めず（印の文字が順に、間に他の文字を挟んで出ている）、line が 2 s 黙ったら、変数の status を聞き直す（最大 5 回）。host の試験（偽の guest の socket）: 崩れた印で 2.1 s・status 3 と本文が正しい、崩れない印で即時。
- `plan/ws353/tests/display-fence-test.c`: wait・cancel・race に GATE（open の後 GATE.ready を作り、host の GATE.go を待ってから登録）。open の kernel の行が登録の前に出きるので、marker から変化までの host の時間に serial の聞き直しが入らない。
- `plan/ws353/tests/qemu-display-fence.sh`: 変化のある step を全部 gate し、step の間（program の open と queue の割り込みはあるが head は変えない）で番号が動かない事を `quiet` の 5 組で確かめる。

### 確かめ（実行したコマンドと結果）

- build: `qemu-display-fence.sh` の中の `make -j4 CONFIGMK=plan/ws353/tests/config-amd64-fence.mk disk` が venus の 4 file と vmunix を作り直し、warning 0。venus は amd64 だけの driver（`config/drivers/pci.drivers`）で、arm64・riscv64 の build には入らない（未実施）。
- QEMU（Venus、2 head、D-Bus display）: `sh plan/ws353/tests/qemu-display-fence.sh build/p2-fix1-qemu`、同 `build/p2-fix2-qemu` の 2 回とも `qemu-display-fence: PASS`。latency は 266 ms・255 ms（1 s 以内）。idle は 30 s で番号 3→3。quiet の 5 組は 2 回とも PASS（番号は抜き差しのたびに 1 だけ上がる: 3→4→5→6→7、race は 8 回の変化で 7→15）。直す前（main）は step を跨ぐたびに 2 上がっていた（6→7、9→10、12→13）。
