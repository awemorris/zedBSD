# BUG-339: VF2 の実機で U-Boot の control の DTB を渡すと SoC の block が見つからず VFS で止まる

- 状態: reproduced（2026-10-20 ユーザー、2026-10-31 P2 の実機で再現）/ scheduled（ESP の DTB の道は動く。control の DTB での起動の恒久の直しは判断待ち、下の 2026-10-31 の節）
- 発見: ユーザーの VF2 の UAT（beta2 U27、`bootefi ${kernel_addr_r} ${fdtcontroladdr}`）。BUG-338 の直しの後、SMP は `4 usable of 5` で 4 CPU が online になり、`visionfive2: system control blocks unavailable (13)`（ENODEV）→ SD・Ethernet を上げず → `VFS initialization failed (6)`。ユーザーが貼った serial の log（判定には使わない、手がかり）。
- 原因（見込み）: zedBSD の VF2 の platform は mainline の Linux の DT の compatible（`starfive,jh7110-sys-syscon` など、src/drivers/platform/visionfive2/vf2-syscon.c）で SoC の block を探す。配布の U-Boot 2021.10 の control の DTB はその compatible を持たない（未確認）。設計（WS256 #21「U-Boot が ESP の mainline の DTB を bootefi で渡す形も決定 2 の範囲」）は mainline の DTB を渡す前提。
- 当面の手: Q1 が mainline v6.12（adc218676eef）の `jh7110-starfive-visionfive-2-v1.3b.dts` から dtc で作った DTB（32040 byte、sha256 1826e14d92c1ca33…、cpu@0 は status disabled、sys-syscon の compatible あり）を UAT の image の ESP に `vf2.dtb` として足した `build/uat/vf2/native-dtb.img`。U-Boot で `load mmc 1:1 ${fdt_addr_r} vf2.dtb` と `bootefi ${kernel_addr_r} ${fdt_addr_r}`。
- 恒久の直し（未着手）: image の build で VF2 の DTB を ESP に入れる（source は GPL-2.0 OR MIT の mainline の dts。入手は tarball の検証か zedBSD-firmware の mirror）。あわせて U-Boot の起動の script（自動で mmc rescan と DTB の load）を検討。
- 関係: WS256（p015 の SD の image、#21）、BUG-338。

## 恒久の直し（2026-10-20 P1、q1361-i01、実機の確認は未実施）

- image の build（`ZEDBSD_PLATFORM=visionfive2` の `native-image`）が ESP に入れる物（platform/riscv64/visionfive2/dtb.mk）:
  - `dtb/jh7110-starfive-visionfive-2-v1.2a.dtb`（31655 byte、sha256 e76b80a6ea4e3f16…）と `-v1.3b.dtb`（32040 byte、sha256 1826e14d92c1ca33…、Q1 の当面の `vf2.dtb` と同一）、同じ物を `dtb/starfive/` にも（mainline の U-Boot の fdtfile の形）、`dtb/LICENSE`（MIT と著作権表示）。source は Linux v6.12（adc218676eef…）の file を1つずつ raw.githubusercontent から取り、`platform/riscv64/visionfive2/dts.sources` の size と sha256 で検証して `build/sources/linux-dts/<commit>/` に置く（tree には取り込まない）。GPL-2.0-only の `thermal.h` は取らず、使う値1つ（THERMAL_NO_LIMIT）だけを zedBSD の header に置いた。cpp と dtc は host の物（無ければ build を止める）。sha256 は host の DTC 1.7.2 で観測。
  - `vf2_uEnv.txt` と `uEnv.txt`（同じ内容）、`boot.scr`（legacy の script image、`platform/riscv64/tools/make-uboot-script.py` が作る）。
  - firmware を image に入れない時（`RISCV64_SPL` 無し）は partition 1・2 を空の予約（zedBSD の型）にして ESP を partition 3 に置く。配布の U-Boot は `bootpart=3` しか見ないため。
- 自動の起動の道（配布の U-Boot、starfive-tech/u-boot JH7110_VisionFive2_devel c4c67bb66ae6 の include/configs/starfive-visionfive2.h を gh api で読んだ）: `bootcmd=run sdk_boot_env; run distro_boot_env`。
  1. sdk_boot_env: `mmc dev 1` が通れば `mmc 1:3` の `vf2_uEnv.txt` を env import して `run boot2` → zedBSD の `boot2` が `mmc rescan` → `EFI/BOOT/BOOTRISCV64.EFI` と `dtb/${fdtfile}`（既定 jh7110-starfive-visionfive-2-v1.3b.dtb、無ければ v1.3b）を load → `bootefi`。
  2. 最初の `mmc dev` が voltage select で失敗した時: distro_boot_env が `mmc dev` をもう一度試し、通れば `uEnv.txt` を env import → sysboot（extlinux は無いので失敗）→ 同じ loop の次の `run distro_bootenv_nvme` を uEnv.txt が zedBSD の起動に置き換えている。
  3. 両方の `mmc dev` が失敗すると SD から何も読めず prompt に落ちる（手で `mmc rescan` からの4行）。2回目の init が通るかは未確認。
  - saveenv は使わない。v1.2a の board は `fdtfile` を自動で選べない（配布の U-Boot が revision を env に出さない）。v1.2a で v1.3b の DTB が合わない時は prompt で `setenv fdtfile jh7110-starfive-visionfive-2-v1.2a.dtb; run boot2`。
- host の確認: VF2 の image の build（rc 0、warning 0）、GPT（p1・p2 予約、p3 ESP、p4 root、p5 scratch）、ESP の file の一覧と DTB の sha256、boot.scr の header の CRC と中身、`plan/tools/vf2-host/native-image/run.sh` PASS 40 FAIL 0。U-Boot での実行は未実施。

### 実機の試験（ユーザー、VF2）

新しい VF2 の image を SD に書き、SD を挿して電源を入れるだけ（U-Boot の prompt で何も打たない）で、HDMI の画面に zedBSD の login が出ること。serial に `zedBSD: loading from the SD card or eMMC` が出るのが目印。prompt に落ちたら、serial に出た最後の数行（`Card did not respond…` が2回か）を知らせてほしい。

## 2026-10-31 P2（q1772-i01）: 実機の再現と原因、直しの案

- 再現: 上の BUG-338 の手順（U-Boot から `bootefi ${kernel_addr_r} ${fdtcontroladdr}`）で、serial に
  `visionfive2: system control blocks unavailable (13)`（13 = zedBSD の ENODEV）→ SD・Ethernet を上げず → `VFS initialization failed (6)`。
- 原因（確かめた）: U-Boot の `md.b` で読み出した control の DTB（54304 byte、`/tmp/p2-vf2bugs/ctl/ctl.dts`）は StarFive の vendor の binding。
  root は `compatible = "starfive,jh7110"`・`model = "StarFive VisionFive V2"`（板の revision の compatible が無い）。system control は
  compatible が `"syscon"` だけの 3 node、clock は `starfive,jh7110-clkgen`、pinctrl・SD（`snps,dw-mshc`、node 名 sdio1）・Ethernet
  （`starfive,jh7110-eqos-5.20`）・GPU（`img-gpu`）も mainline と別。cache controller は `sifive,fu740-c000-ccache` で、HAL は `sifive,ccache0`
  だけを見るので `ccache unavailable; no cache maintenance` になる。memory は 4 GiB、OpenSBI の領域は `/reserved-memory` の mmode_resv*。
  visionfive2 の platform の driver は全部 mainline の binding を読むので、この tree では SoC の block が一つも見つからない。
- 良い事: 通常の起動（電源を入れるだけ）は `vf2_uEnv.txt` の `boot2` が ESP の `dtb/jh7110-starfive-visionfive-2-v1.3b.dtb` を
  `${fdt_addr_r}` に読んで `bootefi` に渡し、q1772 の 37 回の電源の入れ直しの起動で全部 SSH まで上がった（上の P1 の恒久の直しの道は実機で動く。HDMI の
  login の画面は見ていない）。U-Boot の serial には毎回 `Card did not respond to voltage select! : -110` が 1 回出て、その後の `mmc rescan` で通る。
- 入れた物（直しではない）: `src/kern/platform/visionfive2.c` が SYS の block の無い tree で、mainline の binding でない事と ESP の DTB を
  `${fdt_addr_r}` に読んで bootefi に渡す事を log に出す（実機の serial で行を確かめた）。
- control の DTB で起動させる直しの案（どれも判断が要るので着手していない）:
  1. loader が ESP の mainline の DTB を「板の tree」として別に kernel に渡し、platform はそれで SoC を探す。HAL は firmware の tree の
     memory・reserved-memory・cpu を使い続ける（8 GiB・2 GiB の板の memory、OpenSBI の領域、U-Boot の MAC を失わない）。loader と kernel の
     handoff の版の変更と、HAL の `hal_get_arch_handoff` の新しい key が要る → HAL の責務の追加として事前承認が要る。
  2. kernel に mainline の DTB を埋め込む。base system に外部の物（Linux の DTB、GPL-2.0 OR MIT）を取り込まない方針（master-design-policy の 2.1）
     に触れ、vmunix の単体の配布に MIT の表示が要る → ユーザーの判断。
  3. loader が firmware の tree を ESP の DTB に差し替える。memory の reg は同じ長さなら書き写せるが、`/reserved-memory`（OpenSBI）と
     MAC の property は足せない（FDT の編集器が要る）。OpenSBI の領域を kernel が使う危険があるので勧めない。
  - 案 1 が筋が良い。案 1 でも板の revision（v1.2a と v1.3b）は control の DTB から分からない（既定は v1.3b、vf2_uEnv.txt と同じ）。
  - 付随: HAL の ccache の compatible に `sifive,fu740-c000-ccache`（Linux の sifive_ccache が受ける名前）を足すのは src/hal の実装の補完で、
    案 1 と一緒に行う。
