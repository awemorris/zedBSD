# BUG-410: libc の atexit が登録した object を覚えず、dlclose した library の関数を exit で呼ぶ

- 状態: fixed（2026-11-02 P3 q1931-i01、agent/p3-bug410 615a0aecf6。QEMU amd64 の guest で rtld-finalize・rtld-nodelete・rtld-many・ws073 p038 の TLS の試験が PASS。実機は未実施）。前: open（2026-11-02 10:41 Q1 が起票、P3 q1931）
- 発見: 2026-11-02 10:41 P3（BUG-409 の残り）。src/libc/stdlib-extra.c の atexit は、どの object が登録したかを覚えない。NODELETE でない library が atexit を呼んで dlclose されると、exit の時に unmap された code を呼ぶ。C++ の静的な object の後始末（__cxa_atexit と DSO の handle）も同じ。
- 直す形: __cxa_atexit（fn、arg、dso の handle）を持ち、atexit は呼んだ object の handle で登録する。dlclose で object を unload する前に、その object の登録を逆順に走らせて外す（__cxa_finalize(dso)）。
- 扱い: P3（q1931）。

## 原因（2026-11-02 P3）

`src/libc/stdlib-extra.c` の `atexit` は登録の owner を NULL にし、`__cxa_atexit` は dso の handle を記録するが、`__cxa_finalize(handle)` を呼ぶ物が無かった（crtbegin が無く、各 object の fini から呼ぶ形も無い）。`src/rtld/rtld.c` の `unload_object_locked` は object の fini_array・DT_FINI を走らせて unmap するだけで、libc に残った登録（atexit の関数、C++ の静的な object の destructor）は exit の時の `__libc_run_exit_handlers` で unmap 済みの code を呼ぶ。また `__cxa_finalize` は C++ の形の登録だけを見て、atexit の関数を走らせなかった。

## 直し（2026-11-02 P3、615a0aecf6）

- `__dso_handle`: toolchain に crtbegin は無いが、lld が未定義の `__dso_handle` を各 object の ELF header の位置に hidden で定義する（build/llvm の clang・lld で確かめた。clang++ は静的な object の destructor を `__cxa_atexit(dtor, obj, &__dso_handle)` で登録する）。toolchain は変えていない。
- `src/libc/stdlib-extra.c`: 登録は (関数、引数、owner) の 1 つの list（上限 64 は今のまま）。`atexit(fn)` は fn の code がある object の ELF header の位置（`dladdr(fn)` の `dli_fbase`）を owner にする。呼んだ側の戻り番地でなく関数の番地で決めるのは、呼ぶ側の `return atexit(f);` が -O2 で tail call（`jmp atexit@plt`）になると戻り番地が呼ぶ側のさらに呼び手を指すため（Q1 の指摘の確かめ。FreeBSD の `__cxa_finalize` も atexit の関数を番地で object に当てる）。`__cxa_atexit` は渡された handle を owner にし、handle が NULL なら destructor の code の object にする。`__cxa_finalize(handle)` は owner が handle の登録（NULL なら全部）を、両方の形とも新しい順に、1 つずつ lock の中で list から外してから lock の外で呼ぶ（handler の中の atexit・dlclose・exit でも二度走らない。複数の thread の atexit は従来の spin lock）。`__libc_run_exit_handlers` は `__cxa_finalize(NULL)`。静的な libc（KERN_DYNAMIC_LIBC で無い）は owner を NULL にする（sysroot の smoke の link が未解決の weak を拒むので dladdr を参照しない。静的な program は object を unload しない）。
- `src/rtld/rtld.c`: `unload_object_locked` が lock を離して destructor を走らせる所で、先に `__cxa_finalize`（`lookup_global_optional` で探す。unload 中の object と ld.so 自身は探さない）を object の ELF header の位置（`object_header_address`: p_offset 0 の PT_LOAD の先頭、無ければ load の base）で呼び、その後に fini_array・DT_FINI。exit の時の順（exit の handler の後に loader の teardown）と同じ。依存を続けて unload する時も各 object で同じ。NODELETE・起動の時の object は unload されないので、その登録は exit の時に走る。
- `__rtld_dladdr` の `dli_fbase` を load の base から ELF header の位置に変えた。共有 object・PIE では同じ値（header は vaddr 0）で、違うのは非 PIE の main だけ（0 から最初の segment の先頭へ。FreeBSD の mapbase と同じ意味）。tree の中の `dladdr`・`dli_fbase` の利用を grep した結果: `dli_fbase` を読む所は rtld の外に無い（`userland/desktop/libvulkan-compat/backend.c` は `dli_fname` だけ）。`build/llvm-source` の libunwind・libcxxabi・libcxx にも無い。外部 package の tarball の中は調べていない。
- HAL・rtld の ABI（`include/libc/rtld-abi.h`）・toolchain は変えていない。

## 残り（2026-11-02 P3 の所見、この Bug の範囲の外）

- `__cxa_thread_atexit_impl`（`userland/base/libc/pthread.c`）は handle を捨てる。dlclose した library の `thread_local` の object の destructor が、その thread の終わりに unmap 済みの code を呼ぶ穴は残る（glibc は object を thread の終わりまで残す）。
- exit の handler の上限は 64 の固定の表のまま（POSIX の下限は 32）。静的な object の多い C++ の program・library では足りなくなりうる（溢れた登録は -1 を返し、その destructor は走らない）。
- unload 中の object の handler が atexit を呼ぶと、dladdr が unload 中の object を見ないので owner が NULL になり exit の時に走る（unmap の後）。普通の使い方では起きない。
