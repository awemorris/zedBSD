# BUG-430: 作り直した build system で、試験の image を別の BUILD に作れない・並列の上限を超える・試験の道具が古い

- 状態: fixed（2026-11-14 Q1。ユーザーが差分（BUG-430-makefile.diff、12 file）を承認、Q1 が main に当てた。make -n の parse は x86_64・rpi4・vf2 で rc 0。QEMU で network が上がるか・x86_64 以外の build は未実施）。前: open（2026-11-13 Q1 が起票。WS353 p002 の P1 の報告から）
- 発見: 2026-11-13 P1（q2057-i01）。worktree で WS353 p002 の QEMU の image を作る時。
- 観測（P1 の報告、Q1 は未確かめ）:
  1. x86_64 の sysroot は `BUILD` に依らず `build/x86_64/sysroot` 固定（`mk/platform-x86_64/sysroot.mk`）。`BUILD=build/<phase>/` で image を作ると package の compile が header を見つけられず失敗する（AGENTS.md の「使い捨ての出力は BUILD=build/<phase>/」と合わない）。
  2. vmunix と userland を同じ make で `-j` に並べると、sysroot の前に package が走る（依存の抜け）。
  3. `sysroot` の target が worktree の `build/NoctLang` を `cmake --parallel 16` で作る（4 thread の上限を超える）。P3 も 2026-11-13 に `make sysroot` の sub-make が `-j16` を強いるのを見た（WS334 p040）。
  4. `plan/tools/guest/test-image.sh` が古い変数（`ZEDBSD_CONFIG`・`ZEDBSD_TEST_EXTRA_FILES`・`disk-image` の target）を使い、今の build に合わない（BUG-418 の古い前提の道具の残り）。
  5. rootfs は `--file` の後に `$(BUILD)/etc` を写すので、試験の file（net.conf）が上書きされる（P1 は test の config で INIT_DATA を override して入れた）。
  6. 最小の image で network の UP が ENOENT で失敗し SSH が使えない（P1 は serial に切り替えた）。`plan/tools/guest/guest.py` の extra-files も古い変数。
  7. package の stamp が config の値（例: `ZEDBSD_TEST_SCREEN_CAPTURE`）の変化を追わず、config を変えても compositor の package が作り直されない（2026-11-14 P1、WS353 p005。P1 は試験の script で shot.c を touch して回避）。
- 扱い: 1〜3 は Makefile・`mk/` なので、Q1 が差分の案を作りユーザーに見せる（makefile-style.md）。4 は道具の直しで、担当に回せる。
- 関係: [BUG-418](BUG-418.md)（作り直しの後始末、fixed）。

## 調べ（2026-11-14 P4、q2070-i01）

各観測を code で確かめ、Makefile・`mk/` の差分の案を [BUG-430-makefile.diff](BUG-430-makefile.diff) に、項目ごとの
原因・差分・確かめ方を [BUG-430-makefile.md](BUG-430-makefile.md) に置いた（当てていない。ユーザーの確認待ち）。

1. 確かめた。`mk/platform-x86_64/sysroot.mk:13` の固定（i386・rpi4・rpi5 も同じ、vf2・pc9821 は `$(BUILD)/sysroot`）と
   `mk/platform-x86_64/vmunix.mk:11` の `-Ibuild/x86_64/sysroot/usr/include`。package と `--sysroot` は `$(BUILD)/sysroot` を見る。
   案: `SYSROOT := $(abspath $(BUILD))/sysroot`。
2. `make -j4 vmunix userland` では再現しなかった（`.WAIT` が効く。P1 の観測は 1 の現れの見込み）。ただし `programs`・
   package の stamp・package の target は sysroot に依らず、新しい BUILD の `make -j4 programs` は header が無く失敗した。
   案: 全 package の stamp と target が sysroot の stamp を order-only で待つ（`mk/tracking.mk`）。
3. 確かめた。`mk/build-jobs.mk:21` の既定が 16 で make の `-j` を見ない（64 thread の host で NoctLang は `--parallel 16`）。
   案: `MAKEFLAGS` の `-jN` を既定にする。
4. 試験の道具を直した（`test-image.sh`・`guest.py extra-files`・`jobs.sh` の既定 4・`aat/build-image.sh` の 1 行）。
   今の Makefile のまま x86_64 の image に harness の file が入る事を確かめた。
5. 確かめた。`mk/rootfs.mk` は一覧の `--file` の後に `$(BUILD)/etc` などを写し、最後の directory の 0755 が一覧の
   `--mode` も消す。案: build の写しを先に、一覧を後に、機種に依らない `ROOTFS_EXTRA_FILES` を足す。
6. 原因は code で特定（guest での再現は未実施）: networkd は `/sbin/ifconfig`・`/sbin/route`・`/sbin/dhcpc` を実行するが、
   `mk/userland.mk:14` が必ず入れる一覧に無く、WS353 の最小の config も ifconfig・route を選ばないので exec が ENOENT。
   案: 必ず入れる一覧に足す（ユーザーの判断が要る）。
7. 確かめた。`mk/userland.mk:55` の stamp は config に依らず、package の link は object の一覧の変化を追わない。
   案: config の file と command line の変数の stamp を package の stamp の依存に、object の一覧の stamp を link の依存に。

案を worktree に当てて x86_64 の最小の config で build（`BUILD=build/p4-x/` の disk・`programs`・rootfs・package の
作り直し）を流して確かめ、元に戻した。QEMU・実機・x86_64 以外の build は未実施。
