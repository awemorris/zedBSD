## 調べ（2026-10-08 P2、q914、読みと T1-341 の撮影）

- 試験の座標は古くない。T1-341 の docked.png では、bar の右端の pill に最小化・元に戻す・閉じるが並び、閉じるの × は x≈1251 にある。dock の行の `buttons=1252,…` と合い、y=17 も bar（0〜43）の中。
- press が bar に届いた時、`bar_press`（shell.c）は時計の pill の後に `docked_window()` を見る。これが NULL なら**何も log に出さずに**捨てる。NULL になる場合は次のとおり:
  - 窓がまだ dock の animation の中（`server->anim == top`）。
  - 一番上の窓が maximized でない。
  - Wiseview の最中。
- T1-341 の log には、dock の animation の frame の行（`KWL GLASS anim … t=0.59`）が 1 行しかない。glxtest の swapchain の作り直し（`resized … after_ms=1416`）の間、frame が止まっていたと見られる。そのため anim が残っていた疑いがある（未確認）。
- 足した診断:
  - compositor: buttons の上の press を docked の窓が取らなかった時に `KWL GLASS bar button=N without a docked window x=X anim=0|1` を出す（`userland/desktop/wayland/shell.c` の `bar_press`）。
  - `plan/tools/x11/x11-p004.sh`: 段 3 の press を bar の中央 y=22 にした（aatlib.close と同じ）。press の後の GLASS・HOME・ARRANGE の行を `close-lines.txt` に残し、close も bar button の行も無ければそう言う。
- 確認: zedBSD の wayland（`build/bug273/bin/wayland`）と Linux の keiland の build は warning 0、style-check の数は前と同じ。
- 次: T1 で x11-p004 を流し直し、T1-481 の `bugs.x11-docked-close` の結果も見る。`bar button … anim=1` なら compositor の直し（anim の終わりを frame に頼らず時刻で決める）、close の行が出て glxtest が残るなら X の窓の close の経路を調べる。
