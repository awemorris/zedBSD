## 期待と観測

期待: commit は物理 + swap で厳密に会計しているので、commit 済みの page の fault はメモリ不足で失敗しない（待つだけ）。RAM を超える分は swap に page out される。

観測（`vmstatprobe` と kernel の log）:

| 操作 | 結果 |
| --- | --- |
| `swaphog 450`（512 MiB の guest） | 53 秒で正常終了。page out 115k・page in 113k（swap は働く）。ただし途中で cron（pid 13）が stack の page の読みで SIGSEGV |
| `swaphog 900` | 触った量が約 460 MiB（= 空き RAM）に達した直後に hog が SIGSEGV（書き込みの fault が ENOMEM）。init（pid 1）・networkd（pid 5）も stack や text の fault で死ぬ。page out は 3.5k だけ |
| 元の kernel（今日の変更の前、swapfile 64 MiB）で 450 MiB | malloc は ENOMEM（commit が正しく効く）。SSH の session が切れる（別の症状、未解析） |

## 原因（解析 2026-09-25。一時的な log を kernel に入れて測った。log は外した）

失敗した fault の site は `vmspace_fault` の「既存の private page を map し直す」経路と「新しい page を map する」経路で、どちらも **`hal_space_map` が `HAL_ERR_NOMEM`** を返す。その時点の `hal_get_memstat`: `physical_free` は 0 か 4096、`physical_allocated` は 509,370,368（管理下の物理の全部）。fault は map の失敗を「page table の圧迫」として `reclaim_page_map_reserve` で 4 page を reclaim してやり直すが（log: `reclaimed 4 last 0`、reclaim 自体は毎回成功）、やり直しの `hal_space_map` の時点でまた free 0。つまり **reclaim が空けた page は、別の CPU で走る他の fault（hog の新しい page の fault）に取られる**。失敗している fault は init・cron の stack の page（`0x7fffffffe000`）の page in で、frame（`vm_reclaim_frame`）は取れても、その後に要る **page table の page**（stack の leaf table は、page が全部 swap out されたときに空になって `hal_space_unmap` の `detach_empty_tables` が解放している）と、**`allocate_table` の管理 record**（`kernel_alloc` は 512 KiB の固定 heap が満杯だと 1 個 32 byte の record に物理 page を 1 つ使う。`kern_malloc` の fallback）が取れない。2 秒（2000 回）待って ENOMEM → SIGSEGV。

要するに 3 つの欠陥の重なり:

1. **空き page の予備が無い**。reclaim は fault が要求した分（frame 1 つ、table のとき 4 つ）をその場で空けるだけで、空きを保つ daemon（Linux の kswapd の low/high watermark）が無い。空きが 0 の状態で複数の CPU が fault すると、1 つの fault が要る 2〜3 page（frame・leaf table・record）を揃えられず、互いに奪い合って餓死する。
2. **fault が ENOMEM で諦める**。commit 済みの page の fault は本来「メモリが空くまで待つ」べきで、失敗は kernel のメモリ会計の穴か真の枯渇（あり得ない）のときだけ。2 秒の polling（q437 で 1 回の再試行から増やしたが根本ではない）ではなく、空きができたら起こされる待ちが要る。init を殺す前に OOM の方針（大きい process を選ぶ、init は殺さない）も要る。
3. **page in に page table が要る**。swap out で leaf table が空になるとすぐ解放するので、page in のたびに table の page と record の確保が要る（Linux は munmap/exit まで table を残す）。加えて固定 heap が小さく、record が page を食う。

副次: q437 で `vm_reclaim_private_one` を clock（第 2 の機会、走査の上限 4096）にする前は、全 page が accessed のとき page ごとに全 queue を 2 回走査していて（O(n²)）、900 MiB では guest が固まっていた。これは直した（450 MiB が通るようになったのはこの分）。

## 修正の設計（案。まだ実装していない）

| # | 変更 | 場所 | 効果 |
| --- | --- | --- | --- |
| A | 空き page の watermark と page-out の worker: 空きが low（例: 物理の 1%、最低 256 page）を切ったら worker が high（2%）まで reclaim する。fault は空きが min を切ったら worker を起こし、`hal_pmem_alloc` が失敗したら **waitq で待つ**（`hal_pmem_free` と reclaim の完了で起こす）。`vm_reclaim_frame`・`reclaim_page_map_reserve` の usleep の polling を置き換える | `src/kern/vm.c`（reclaim）、`vmspace.c` | 餓死をなくす。fault は待つだけで失敗しない |
| B | 1 回の fault が要る page をまとめて確保する（frame + table + record の「fault の予約」）か、page table と record を **緊急の予備**（reclaim の進行に要る分）から取る。swap の I/O が使う memory も io-pool の予備から | `vmspace.c`、`src/hal/amd64/space.c`（実装のみ、hal.h は不変） | 空きが少ないときも 1 fault が完結する |

| D | 固定 heap を現代向けに大きく（512 KiB → 例 16 MiB）し、`kern_malloc` の fallback を「小さい確保 1 つに page 1 つ」ではなく arena の追加に | `src/kern/entry.c`・`heap.c` | record の確保が page を食わない |

## 修正の試み（2026-09-25、commit f7fde78d・e56e5f3f。未解決）

設計の A〜E を実装した: 空き page の予備（管理下の 1/512、最低 256 page）と page-out の worker（予備の 3 倍まで reclaim）、`vm_reclaim_frame` は予備を残して待つ（waitq、10 秒空かなければ E の OOM kill）、page table の予備の reclaim も待つ、object page の確保も待つ、amd64 の `hal_space_unmap` は 2 MiB 未満の unmap では空の table を解放しない、amd64 の固定 heap を 4 MiB に、OOM は init 以外の最大の process に SIGKILL。あわせて、終了して後始末を待つ process（参照数 0 の vmspace）の page を reclaim の候補から外した（これは 1 回目の試験で `pin_backing_mappings` の `vmspace_ref` が trap して panic したため）。

結果（QEMU 512 MiB、swap 1 GiB）:

| 試験 | 結果 |
| --- | --- |
| 1 回目（候補の除外の前） | 450 MiB の途中で init・networkd・cron が text の page の fault で SIGSEGV。その後 kernel が `pin_backing_mappings` で panic |
| 2 回目 | 900 MiB で `kern: out of memory: killed pid 32` が 10 秒ごとに繰り返され、止まったまま（ユーザーが打ち切り）。450 MiB の結果は serial の出力が残らず不明 |

分かったこと: OOM の kill は効かない。SIGKILL は user に戻るときに届くが、殺す相手（hog）自身が kernel の fault の中で frame を待ち続けていて戻れない。そして 10 秒待っても page が空かない、つまり swap に余裕があるのに reclaim が page を空けられない原因が、まだ別にある（未特定。1 回目の text の page の fault の失敗も同じ原因の可能性がある）。

状態: 修正は commit してあるが受け入れに達していない。ユーザーの指示（2026-09-25「さらなる修正案は考えなくてよい」「打ち切ってください」）でここで止めた。再開するときは、fault の待ちの中で「reclaim が何を返しているか」（候補なし EAGAIN か、I/O の失敗か）を取るところから。

## 原因の特定と修正（2026-09-25、2 回目）

一時的な計測（1 秒ごとに空き page 数・reclaim の返り値・候補を捨てた理由の内訳を kernel の log に出す。計測の code は外した）で確定した:

- 空き page は 254〜255 で、予備の 256 をわずかに下回ったまま動かない。
- `vm_reclaim_private_one` は毎回 4096 件を見て、そのほぼ全部が「resident でない（swap に出た）page」で、候補なし（EAGAIN）を返し続けていた（absent の累計 2 億超、EAGAIN 5 万超。swap out 済みは約 4300 page）。
- 原因: **swap out した page が reclaim の待ち行列の古い側（tail）に残り続け、q437 で入れた走査の上限 4096 がそこで尽きて、その先にある resident な page に届かない。** swap out が約 4096 page に達した時点で reclaim が止まる。元の code は上限なしで全部を読み飛ばしていた（O(n) で遅いが止まりはしない）。worker も直接の reclaim も同じ探索なので、どちらも空けられず、10 秒後に OOM の kill になった。
- OOM の kill が効かなかった理由: SIGKILL は user に戻るときに届くが、殺す相手（hog）自身が kernel の fault の中で待ち続けていて戻れない。

修正（commit は下）:

| # | 変更 | 場所 |
| --- | --- | --- |
| 1 | **reclaim の待ち行列には resident な page だけを置く。** swap out で待ち行列から外して swapped の list へ移し、page in で戻す。track は resident なら待ち行列、swapped なら swapped の list へ。swap source を抜くときの走査は swapped の list を読む。list の所属は `queue_kind`（none / reclaim / swapped）で持ち、`queue_remove` はどちらの list からも外す | `include/kern/vmspace.h`、`src/kern/vm.c` |
| 2 | fault が frame を待つ間に SIGKILL が来たら待ちをやめて fault を失敗させる（process は user に戻るときに死ぬ）。`signal_kill_pending()` | `src/kern/signal.c`、`include/kern/signal.h`、`src/kern/vm.c` |
| 3 | page-out の worker は reclaim に失敗したら 5〜10 ms 休む（要求が来続けても空回りしない） | `src/kern/vm.c` |
| 4 | reclaim の候補を選ぶとき、終了して後始末を待つ process（参照数 0 の vmspace）の page は外す（1 回目の試みの panic の修正） | `src/kern/vm.c` |
