## q782-i01（P1、2026-10-06）: 切り分け（原因は取得。libbrowser の engine でも shell でもない）

Status: 判断待ち（User-Agent の方針。Q1 経由でユーザーへ）

- host の headless（`plan/ws074/tests/host-build.sh plain` の `browser --dump=dom --async https://www.amazon.co.jp/`）は `<html><head><body>` だけ。
  libbrowser の User-Agent（`userland/desktop/libbrowser/net/net.h` の `NET_USER_AGENT`）は Chrome 153 の UA
  （`Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/153.0.0.0 Safari/537.36`）。
- curl で同じ UA・同じ header（`Accept: */*`、`Accept-Encoding: identity`）: **HTTP 202、本文 0 byte、`x-amzn-waf-action: challenge`**（AWS WAF の JS の
  challenge。CloudFront）。白い画面はこの空の本文。
- UA ごとの答え（2026-10-06 の curl）: `browser/0.1 (Kei)` → 200・約 900 KB（desktop の版）。`Mozilla/5.0 …` で始まる UA は全部 202・0 byte
  （Chrome の UA、それに `Kei/0.1` を足した物、`Mozilla/5.0 (X11; zedBSD x86_64) Kei/0.1`、Firefox の UA）。
- `NET_USER_AGENT` を一時的に `browser/0.1 (Kei)` にした host の build（commit していない）では、同じ headless の `--render --async` が 3 秒で
  Amazon のトップを描いた（header・検索欄・商品の card・footer。host では日本語の font を渡していないので豆腐。Uncaught は `customElements` の 1 件）。
- 経緯: [amazon-goal.md](../ws074/amazon-goal.md)（2026-09-28）の決定は「目標は私たちの UA の版」。その後の比較の Phase（p096・p097）が固定の
  Chrome の UA を使い、engine の UA も Chrome の物になっている。

直しの案（要る判断: どの UA を送るか。Google など他の site の返す版も UA で変わる）:
1. `NET_USER_AGENT` を `browser/0.1 (Kei)` に戻す（1 行。navigator.userAgent も変わる）。Amazon は desktop の版を返す。
2. Chrome の UA のまま、Amazon は諦める（WAF の challenge の JS を通すのは範囲外）。
3. site ごとに UA を変える（今は仕組みが無い。範囲が広がる）。

## 2026-10-06 ユーザーの決定

「ChromeのUAでデバッグを続けます。」→ UA は Chrome のまま。Amazon（AWS WAF）の challenge の応答（202・x-amzn-waf-action: challenge）を browser が扱えるか（challenge の script の取得と実行、token の cookie、再読み込み）を調べて直す。
## q793 相当（P1、2026-10-06）: Chrome の UA のまま AWS WAF の challenge を通す — 調べ

ユーザーの決定（Q1 経由、原文）:「ChromeのUAでデバッグを続けます。」→ UA は変えない。

1. **本文 0 byte の原因は Accept**: 同じ Chrome の UA でも `Accept: */*` には 202・0 byte、`Accept: text/html,…` には 202・**2012 byte の challenge の
   page**（`window.gokuProps` の key・iv・context、`https://…token.awswaf.com/…/challenge.js` の読み込み、`AwsWafIntegration.getToken()` の後に
   `location.reload(true)`）。→ **直した（84f16c3f）**: `userland/desktop/libbrowser/net/http.c` の `NET_HTTP_HEADERS` を Chrome の navigation と同じ
   `Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8`、`Accept-Language: ja,en-US;q=0.9,en;q=0.8`（`Accept-Encoding: identity`
   は従来どおり）。host の headless で challenge の page と challenge.js（約 687 KB）が読まれ、実行されるところまで来た。example.com は従来どおり。
   引数の要らない host の unit test 60 本は PASS（引数の要る 13 本は base と同じく単体では走らない）。
2. **次の壁は JS の engine と Web API の不足**。challenge.js の最初の Uncaught: `ReferenceError: Uint32Array is not defined`（challenge.js:1:305137）、
   続いて `AwsWafIntegration is not defined`。engine には typed array が全く無い（`Uint8Array` も無い）。challenge.js が使う物（文字列の数、
   obfuscate されていて全部は見えない）: `ArrayBuffer` 19・`Uint8Array` 44・`Uint32Array`・`Int32Array`・`Uint16Array`・`Float32Array`・`DataView` 8、
   `crypto.getRandomValues` 12・`subtle`（`digest` 14・`SHA-256`・`importKey` 3）、`Worker` 8・`Blob` 10・`URL.createObjectURL`・`postMessage`、
   `fetch` 9（POST が要る見込み、今の fetch は GET だけで init を読まない）、canvas の `getContext`・`toDataURL`・`getImageData`（engine に canvas が無い）、
   `localStorage`・`TextEncoder`・`TextDecoder`（有る）、cookie の `aws-waf-token`（`document.cookie` の setter は有る）、`hardwareConcurrency`。
3. 見積もり（大きい、判断が要る）: typed array と ArrayBuffer・DataView（VM の整数添字の exotic object を含む）1〜2 日、`crypto`（getRandomValues、
   subtle の digest と importKey・必要なら decrypt / sign、TLS と同じく libcrypto を使う）0.5〜1 日、fetch の POST（method・body・headers を loader へ）
   0.5〜1 日、Blob・createObjectURL・Worker（Worker 無しの fallback が challenge.js にあるかは未確認）1〜2 日、canvas 2D（fingerprint に使うだけなら
   最小の stub で足りるかは未確認）。1 段ずつ足して、毎回 host の headless で次の Uncaught を見る進め方。WS074 の新しい Phase（または新しい WS）として
   Q1・ユーザーの判断を待つ。
