# BUG-195: 実機 5330 で DSDT が読めず（AML の stack の予算を超える）、ACPI の namespace が無い。native の touchpad・I2C が付かずスクロールできない

Reproduction: reproduced（実機 5330、UAT 2026-10-05 午後、image uat-0505c = main ee2f8c7f）
Disposition: resolved（2026-10-08 夜 ユーザー「下記は実装の変更が多かったので、いったんすべてcloseします。」、Q1 の中継）
Discovery: 2026-10-05 午後 UAT。ユーザー「タッチパッドはスクロールなどができていない。」→ Q1 が 5330（10.0.30.3、ユーザーの許可）の dmesg を読んだ
Handling: WS049（ACPI の AML の解釈器）・WS159（native の touchpad）。担当 P1（最優先）

## 観測（dmesg、`plan/uat/2026-10-05pm/dmesg.txt`）

```
lpss-i2c: attach failed while powering on (3)        ← 2 回（EINVAL）
input: /dev/input/event0: PC/AT PS/2 mouse           ← touchpad は PS/2 の互換の mouse のまま（スクロール無し）
```

`/dev/input` は event0（PS/2 mouse）・event1（PS/2 keyboard）だけ。I2C-HID の touchpad は付いていない。

## 以前の実機

2026-10-04 の UAT（`plan/uat/2026-10-04/dmesg.txt`）でも DSDT は読めていない（`stopped at offset 0x1c89b (error 13)`）。今回は 0x22177 まで進み、別の理由（stack の予算、`src/drivers/acpi/acpi-kern.c` の `STACK_BUDGET` 8 KiB、`aml-eval.c` の `drv_acpi_stack_check`）で止まった。つまり実機では ACPI の namespace が一度も揃っておらず、namespace に頼る物（LPSS の I2C の `_PS0` と I2cSerialBus・GpioInt、I2C-HID の touchpad、蓋・電源ボタン・AC・電池の事象、LPS0、S0 idle）は実機で働いていない見込み。QEMU では DSDT が小さく通る。

## 調べる点

- 5330 の DSDT（取り出し済み、host の試験の入力）を host の AML の harness で読み、0x22177 で stack の予算を超える経路（入れ子の深さ、各 frame の大きさ）を測る。`drv_acpi_stack_deepest()`。
- 予算 8 KiB が小さいのか（kernel の thread の stack の大きさとの関係）、frame が大きいのか（LTO の inline で再帰の frame が膨らむ）、入れ子を再帰でなく明示の stack にすべきか。
- lpss-i2c の `attach failed while powering on (3)` は namespace が無いことの結果か、別の原因か。
- 直した後の確認: host で 5330 の DSDT が全部読める、QEMU の回帰、実機で touchpad の event と I2C-HID の attach（UAT）。

## 影響（2026-10-05 午後 UAT、ユーザー）

「2本指、3本指が使えませんでした。なのでテストできていない機能があります。」→ WS159 の touchpad の層（2 本指のスクロール・右 click、押し込み）、WS142 の gesture（Wiseview・仮想デスクトップ・3 本指の切り替え）は実機で未実施。直した後の UAT で確かめる。
- 電池・AC も実機で読めていない（ユーザー「バーの電源アイコンがないです。バッテリーを認識できていない様子。」）。電池は ACPI の battery の device（`_BIF`/`_BIX`・`_BST`、EC の OperationRegion）の AML で読むので、DSDT が読めないと `KERN_SYSTEM_GET_POWER` が電池無しを返し、bar は電池の無い機械として icon を出さない。直した後の UAT で、bar の電池の表示と AC の抜き差しを確かめる。

## 解析と直し（2026-10-05、P1 generation18）

**原因**: stack の予算の物差しの誤り。`drv_acpi_enter(&storage, __builtin_frame_address(0))` の frame address は、LTO（kernel の build）で
呼び出し側の関数が更に外側へ inline されると、その外側の関数の frame（大きな局所変数を含む）の上端になる。予算 8 KiB にその分が
足されて数え、本当の AML の深さが浅くても E2BIG になった。host の harness でも同じ形が見えた（`drv_acpi_initialize_objects` が `main` に
inline され、`main` の 5 KiB の frame が数えに入った）。加えて LTO の build では再帰の frame が -Os 単体より大きい（`drv_acpi_define`・
`exec_while`・演算子の各 handler が再帰の関数に inline され、全ての段がその局所変数を持つ）。

**再現**（host、5330 の DSDT・SSDT、`plan/ws049/tests/latitude5330/`）: kernel と同じ toolchain の clang -Os -flto で harness を作り、
`--budget 8192` で DSDT だけを読むと 0x2110d で E2BIG（0x22177 の隣の root port の同じ形の `If (WIST () || ...)`）。gcc/clang の非 LTO の
build では通るので、これまでの host の試験は見逃していた。

**直し**（`src/drivers/acpi/`）:
1. `drv_acpi_enter()` は自分の frame から測り、inline しない（`__attribute__((noinline))`、`frame` の引数を削除、20 の呼び出し元）。
2. 冷たい大きな経路を再帰の frame の外へ: `drv_acpi_define`・`drv_acpi_table_operator`・`drv_acpi_sync_operator`・`exec_while`・
   `exec_return`・演算子の handler（`op_*`・`debug_object`）を noinline。kernel の vmunix で `drv_acpi_exec_term_list` の frame 208 → 112 byte、
   `drv_acpi_eval_operator` 192 → 16 byte。
3. Else の中が If（とその Else）だけの時（ElseIf の列、ASL の Switch の Case の列）は同じ frame で次の If を回す（`exec_if` の loop と
   `else_holds_if_alone()`）。Case が何個でも If 1 つ分の stack。
4. 予算を 8 → 10 KiB（16 KiB の kernel の stack、guard page 無し。測った値と余裕を `acpi-kern.c` の comment に）。

**測定**（clang 23 -Os -flto、5330 の全 table）: load 5.1 KiB（直す前は物差しの誤りを除いても 6.4 KiB）、`--methods`（引数の無い全 method）
7.0 KiB。

**host の確認**: `plan/ws049/tests/check-latitude5330.sh` に 5（LTO の build で kernel の予算の中に全 table と全 method が入る）と、3 に
power-off（`--poweroff`、BUG-197）を足した。全 PASS。`run-asl.py` 21/21、`compare-corpus.sh` 63 same、kernel の build（warning 0）。

**lpss-i2c の EINVAL（3）は namespace の無いことの結果ではない**: `drv_pci_pcat_init()` の中の PCI の attach（`src/kern/platform/pcat.c`）は
`drv_acpi_attach()` より前で、`lpss_power_on()` は ACPI を使わない（PCI の command・PM の D0・BAR0 の確認と map だけ）。zedBSD の
EINVAL(3) を返し得るのは BAR の取得（index）か map（`pcat_map_bar`: bus_address 0 か size 0 の BAR を断る）。どれかを実機で
確かめるため、`lpss-i2c.c` に BAR0 の型・address・大きさを出す log を足した（次の UAT の dmesg に `lpss-i2c: 0000:00:15.x ...`）。
Linux では 00:15.0/00:15.1 の BAR0 は 64-bit の 0x4017001000 など（`plan/ws159/tests/latitude5330-linux/lspci-lpss-i2c.txt`）。

## 直し（2026-10-05 P1 1eff1521）

原因は stack の予算の測り方: `drv_acpi_enter` が呼び手の frame の address を基にしていて、LTO で呼び手が大きな関数に inline されると外の関数の局所変数まで予算に数えていた。また LTO で define・While・Return・各 operator の処理が再帰の関数に畳み込まれ各段の frame が膨らんでいた。直し: `drv_acpi_enter` を noinline にして自分の frame から測る、重く冷たい道を noinline に、ElseIf・Switch の鎖を 1 frame で回す、予算を 10 KiB に。BUG-196 は DSDT が失敗しても固定の hardware の ACPI の有効化（SMI_CMD に ACPI_ENABLE、SCI、電源ボタンの事象）を行う。BUG-197 は host で `\_S5_ = {7,0,0,0}`、poweroff で SLP_TYP 7 と SLP_EN。lpss-i2c の EINVAL は ACPI と無関係（PCI の BAR の扱い）で、失敗の時に BAR0 の型・address・大きさを log に出すようにした。次の UAT の dmesg で原因を見る（touchpad はまだ付かない恐れ）。
