# BUG-369: QEMU の guest への SSH の往復が、数回の後から 3〜32 秒に伸びる

- 状態: open（2026-10-30 Q1 が登録）
- 発見: 2026-10-30 P3（BUG-367 の確かめの途中）。main b776fd468（BUG-367 の直しの前）の image で `guest run true` を 15 回: 0.3 0.3 0.3 0.2 0.2 5.3 6.4 8.8 31.9 20.2 14.4 11.2 11.6 3.6 6.2 s。5 回目の後から伸びる。BUG-367 の直しとは無関係（直しの前から有る）。
- 影響: SSH で guest を操作する試験（AAT・回帰）が遅くなり、timeout で落ちうる。実機でも同じなら、SSH の使い勝手が悪い。
- 疑い（未確かめ）: 接続を閉じた後の資源（TCP の endpoint・TIME_WAIT を持たない解放・port の再利用）、sshd の側、QEMU の user の network（slirp）の側のどれか。BUG-367 の P3 の所見（TIME_WAIT を持たない）と関係するかを先に見る。
- 直す方針: QEMU で再現の script を作り、遅い回の packet を tcpdump（host 側）と guest の net.tcpstats で見る。
- 2026-10-30 P3 の手がかり: 遅れは close ではない（guest の中で各回 2 ms 以下）、SSH の接続か終わりの側。BUG-367 の直しの後も同じ形（0.3 0.3 0.3 0.2 3.6 12.0 8.0 23.2 7.4 3.4 0.3 0.2 0.2 0.3 0.3 s、終わりの方で戻る）。sshd の session は server を先に閉じる順で、直しの前は host の FIN を listener が捨て、後は RST。それでも形が変わらないので主な原因はこの経路ではない見込み（未確かめ）。

## 解析（2026-10-30 P3 q1707-i01）

- 再現の script: `plan/tools/ssh-rtt/qemu-ssh-rtt.sh IMAGE [OUT]`（`guest run true` を ROUNDS 回、QEMU の `filter-dump` で guest の側の
  pcap を取り、各回の SYN・banner・FIN・guest の答えの最長の待ち（と何に答えたか）・boot disk の読み書きの数と時間（QMP の
  query-blockstats）・前後の net.tcpstats を `rtt-summary.py` で要約。`LOAD=N`（host の busy loop）・`CPUS`・`WRITE_IOPS=N`（QMP の
  block_set_io_throttle で disk の書きを N/s に絞る））。
- 負荷の無い host では 15・30・30 回とも 0.21〜0.28 s（`build/bug369/rtt1`〜`rtt3`）。host の CPU の負荷（busy loop 64 本、nice 10）でも
  4 CPU・1 CPU とも全回 0.3 s 未満（`load-smp4`・`load-smp1`）。
- 同じ host で image の build（disk-image まで）と並べると再現: 30 回のうち 3〜11 回目が 3.2〜19.0 s、その後 0.25 s に戻る（`rtt4`）。
  disk の書きを 1 IOPS に絞っても同じ形（`thr1`: 1〜5 回目 0.24 s、6〜8 回目 13.9・15.9・3.9 s、遅い回に disk の書き 14・16・4 回、
  emulator の書きの時間 15.9・16.0・4.0 s）。
- pcap: 遅い回は TCP は速い（SYN-ACK・ACK は即時、再送なし）。待つのは guest の sshd の答え: USERAUTH_SUCCESS の後、client の
  session の channel open（112 bytes）への答えが 13.7・15.7・3.6 s 遅れる。接続の終わり（guest の FIN）も 10〜18 s 遅れる。
  net.tcpstats の socket の数は前後で同じ（listener と自分の接続、TIME_WAIT の溜まりも無い）。→ TCP・TIME_WAIT は原因ではない。
- ログインで書き換わる file は `/var/log/messages` だけ（guest の `find / -xdev -newer`）。1 IOPS に絞った guest で syslogd を止めると
  12 回とも 0.24〜0.28 s（止める前は 6〜20 s）（`build/bug369/man1`）。
- 原因: syslogd（`userland/base/syslogd/main.c`）は 1 本の loop で、2 秒ごとに `/var/log/messages` と `/var/log/kernel.log` を fsync する。
  fsync は file の block と journal の commit を書いて待つので、遅い disk（host が書きで忙しい QEMU、ここでは絞った disk）では何秒も
  かかり、その間 `/run/log` を recv しない。unix の datagram の受けの queue は 8 通（`SOCKET_RECEIVE_MESSAGES_MAX`）で、満ちると
  libc の `syslog()`（`src/libc/syslog.c`）の blocking の `send()` が空くまで待つ。sshd は認証の後（"Accepted publickey"）と切断
  （"Disconnected"）で syslog するので、そこで止まる。最初の数回が速いのは、最初の fsync（2 秒後）までは queue が空くため。

## 直し（2026-10-30 P3 q1707-i01）

Q1 の条件（2026-10-30）: syslogd の memory の積みに上限、溢れたら新しい物を数えて捨て、数を次に書ける時に 1 行で記録。libc の待ちと捨ても
捨てた事が後で分かる形に。確かめは絞った disk で 15 回以上が全部 1 s 未満、syslogd を止めない状態でログの行が失われない試験も。

- `userland/base/syslogd/main.c`: 受け（main の thread）と書き（writer の thread）に分けた。受けは `/run/log` から recv して memory の
  queue に積むだけで disk に触れない。writer は queue をまとめて取り、`/var/log/messages` に書き、2 秒ごとに kernel log の写しと
  両 file の fsync をする（遅い fsync は writer だけを止める）。queue は 1 MiB（`LOG_QUEUE_LIMIT`）まで。超えた・memory の取れない
  message は捨てて数え、writer が次の書きで「syslogd: N messages were dropped while the log was behind」の 1 行を書く。SIGHUP の
  開き直し・SIGTERM の停止は writer に渡し、停止では残りを書いて flush してから終わる。signal は main の thread が受ける
  （writer は block して作る）。
- `src/libc/syslog.c`: `send` を `MSG_DONTWAIT` にし、queue が満ちていれば `poll(POLLOUT)` で最長 100 ms（`LOG_ROOM_WAIT_MS`）
  待って 1 度だけ送り直す。それでも入らなければ捨てて数え（LOG_CONS なら console へ）、次に送れた message の後に
  「ident[pid]: syslog: N messages were dropped because the log daemon was behind」を送る。制限: 数は process ごとの memory に
  あるので、捨てた後に何も送らずに終わる process の数は残らない（daemon が止まっている間に終わる短い process の分）。
  FreeBSD の libc も root の送り（sshd・su）は満ちていれば待たずに捨て、NetBSD は少し待って捨てる。
- kernel・HAL・TCP は変えていない。TIME_WAIT は原因ではないので F-BUG367-time-wait は Future Work のまま。
