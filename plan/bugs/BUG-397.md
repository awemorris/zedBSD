# BUG-397: Windows 版ブラウザ: Google の頁の「サイト」の link を click すると app が固まって応答しなくなる

- 状態: fixed（2026-11-02 P4 q1915-i01、agent/p4-bug397 32e6e318f9（2 件の修正と試験を 1 つの commit に）。Linux の host build で再現と修正を確かめた。本物の Windows は未実施）
- 発見: 2026-11-02 06:16 ユーザーの Windows での OmniGrammaton（WS334 の Windows 版ブラウザ）の UAT。
- 中身: 起動すると Google の top が出る（ユーザーの評価はよい）。その頁の「サイト」の link を click すると、その場で app が固まり応答しなくなる。link の遷移で固まるので、libbrowser の navigation か Windows の shell の message loop が疑わしい。
- 扱い: P4（q1915）。このセッションで直す（ユーザーの指示）。描画と JavaScript の全般の改善はクラウドのセッションの libbrowser を待つが、この Bug はこのセッションで直す。
- 補足（2026-11-02 Q1 がユーザーに確かめた）: 押した link は左上の「ストア」（store.google.com）。Google の top に「サイト」という link は無い。

## 原因（2026-11-02 P4）

Windows に固有ではなく、libbrowser の layout の速さの問題。Linux の host build（`plan/ws074/tests/host-build.sh plain`）で、shell と同じ形（wake と背景の fetch）で view を回す道具から live の google.com を開き「ストア」を押すと、同じく戻らなくなった。固まった間の全 thread の stack（gdb）: main thread は `browser_view_process` → 頁の commit → HTML の parser → inline script → `getComputedStyle` → `page_computed_style` → `page_layout` の中、他の 2 本（loader の resolver と network の thread）は待ちで、deadlock ではなく main thread が計算を続けていた。

- store.google.com の inline script（`initAft`）は img 135 枚ごとに `getComputedStyle(img).height/.width` を読み、その間に `img.setAttribute("data-atf", …)` する。libbrowser は属性の変更ごとに document の generation を進め、次の読みで頁の全体を layout し直す。
- その 1 回の layout が約 7 秒かかった。入れ子の shrink-to-fit（inline-block・flex の項目・grid の項目）が、祖先が min-content を測るたびに自分の content を 0 の幅で測り直し、その中でまた子が測り直すので、深さに対して指数的に増える（max-content の幅は box に覚えていたが min-content は覚えていなかった）。
- 135 回 × 約 7 秒で十数分、main thread が戻らない。Windows の shell は main thread で message loop を回すので「応答なし」になる。

## 修正（2026-11-02 P4、platform に依らない libbrowser の変更）

1. min-content の幅を box に覚える（`layout/position.c` の新しい `layout_narrowest`。`layout_min_content` と flex の `flex_min_content` が使う）。覚えた幅は、測った時と同じ条件（その box の min/max-width・height・min/max-height・box-sizing・aspect-ratio、containing block の高さとその definite、height の indefinite）の時だけ使い、使った時も box model は 0 の幅で測った時と同じに置く。box は layout のたびに arena に作り直すので、覚えは 1 回の layout の中だけで、DOM・style・font・viewport の変化を跨がない。writing mode の論理の座標に替える所（`logical.c`）では max-content と同じく捨てる。store の頁の 1 回の layout が約 7 秒 → 約 0.7 秒。
2. どの style sheet も名指さない data-* 属性の変更で style と layout を古くしない。
   - `css/parser.c`: sheet を解く時、`data-` で始まる identifier の token（attribute selector の名、`attr()` の名。:is・:where・:not・:has・@media・入れ子の中も token として全部）を sheet に覚える。
   - `css/cascade.c`: `css_engine_names_attribute` が engine の全 sheet（UA・author・`<style>`・`<link>`・@import・shadow の sheet）の覚えた名と、属性の名を ASCII の大小を区別せずに比べる。
   - `dom/node.c`・`dom/dom.h`: 属性の追加・変更・削除で、名前空間なしの `data-*` 属性で、頁（`attribute_styled`）が「名指す sheet が無い」と答えた時、`generation` に加えて `quiet_generation` も進める。頁を持たない document（DOMParser・template など）は今まで通り。
   - `page/page.c`・`page/script.c`: style と layout の古さは `page_generation`（`generation - quiet_generation`）で見る。後から sheet が足されれば sheet の世代か DOM の挿入で style を作り直すので、その時の属性の値が効く。
   - store の頁の layout が 135 回 → 2 回。
