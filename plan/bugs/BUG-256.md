# BUG-256: 5330 の USB-C（TC1）に DP の monitor を挿すと DP-alt には入るが AUX が全部 timeout し、表示されない

- 状態: reproduced（実機 5330、2026-10-08 ユーザー「USB-C DPを接続しましたが、ディスプレイは表示されませんでした。」） / scheduled
- 証拠: [kernel-5330.log](BUG-256/kernel-5330.log)（kernel は P2 の ws113-p011 の build、cksum 1836440229、main の WS051 p004a・p004b・p005a を含む）

## 観察（Q1、SSH）

- 挿すと `hpd: long hpd on DDI D: detecting`、`hpd TC1 connected=1 (DDI D)`、`TC1: mode none -> dp-alt`（FIA lanes 4）→ Type-C の port は DP-alt に入る。
- その後 `i915: vbt: i915: edp [err] i915: vbt: %s: not done (status 0x%08x)` が 32 行（AUX の転送が DONE にならない。log の書式の文字列がそのまま出ている（%s・%08x が展開されない）のも別の不具合）→ `DP-ext TC1: disconnected (step receiver capabilities, rc -16)`、`probe N held the port in dp-alt mode (FIA lanes 4), none after it`。6 回の retry で同じ、`HPD-EVENT DP-1 ... disconnected -> disconnected`。
- 2026-10-07 の M-3（Linux）の正解値は **TC2（DDI E、DP-2）** で採った。今回ユーザーが挿したのは **TC1（DDI D、DP-1）**。
- 疑い（未確認）: TC1 の AUX の channel の対応（VBT の aux_ch）・AUX_USBC1 の power well・TC1 の AUX の register の番地、または TC の AUX の timeout の扱い。log の書式の展開の不具合も直す。

## 次

- i915（WS051）の担当が TC1 の AUX の経路を読んで直す。ユーザーにもう一方の USB-C の口（TC2）でも試してもらうと切り分けになる。

## TC2 でも同じ（2026-10-08 ユーザー「TC2でつなぎましたが変わりませんでした。」）

- 起動時: `TC2: declared (DDI E, legacy 0, AUX channel 4)`、`TC2: PHY mode tbt (ready 1, owned 0, live none)`、`DP-ext TC2: bound (DDI E, AUX channel 4, VBT max rate 810000 lanes 4)`。
- 挿すと `hpd: long hpd on DDI E: detecting`、`hpd TC2 connected=1`、`TC2: mode none -> dp-alt` → AUX の `not done` が続き `DP-ext TC2: disconnected (step receiver capabilities, rc -16)`（TC1 と同じ）。
- → port に依らない TC の AUX の経路の問題（Linux（M-3）では同じ TC2 で DPCD・EDID が読めた）。AUX の失敗の log の行に `edp` の接頭が付く → TC の AUX の転送が eDP の AUX の hook（channel・power domain・register）を使っている疑い（p004b の D7 の「DPCD の routing を object ごとの aux_emit に」と p004a の aux.c の Type-C の分岐の食い違いも）。
- 証拠: [kernel-5330-tc2.log](BUG-256/kernel-5330-tc2.log)。

## 解析（2026-10-08 P2、code を読んだ範囲）

- 確かめて合っていた物: TC1・TC2 の AUX channel は VBT の値を Linux と同じ ADL-P の表（adlp_aux_ch_map）で引いて USBC1（3）・USBC2（4）、AUX の control は 0x64310・0x64410（M-3 の Linux で TC2 が使った 0x64410 と同じ）。AUX の power domain は AUX_USBC1・2（`drv_i915_aux_legacy_power_domain`）、power well の index は 3・4（M-3 の driver の request 0x45444=0x303 は well 0 と 4）。外部 DP の AUX の環境は eDP device の backend（同じ display の power domains・MMIO・lock）を使うだけで、eDP の register・channel は使っていない。
- log の `i915: vbt: i915: edp [err] … %s … %08x` は DP の Linux の text の共通の出し方（書式の文字列だけを `i915: edp` の接頭で出す、dp-internal.h の I915_DP_LOG）で、TC の AUX が eDP の経路を通っている証拠ではなかった。
- 「not done」は SEND_BUSY が落ちたのに DONE も TIME_OUT も立っていない状態（10 ms の待ちの timeout の行は出ていない）。status が 0 なら AUX の register に電源・clock が無い（AUX_USBC の well が実際は落ちている、TC cold の中など）を疑う。値が無いので切り分けられない。
- 直し（commit は下）: AUX の失敗（not done・receive error・10 ms で終わらない）を 1 行の `i915: aux AUX USBCn/DDI TCn: <何> (status …; control 0x64x10 reads …; AUX wells bios 0x45440 … driver 0x45444 …; report N)` で値ごと出す（最初の 8 回、その後は 64 回に 1 回）。外部 DP の probe が AUX で失敗した時、port を握ったまま `TCn AUX failed: mode=… cold=… live=… TCSS_DDI_STATUS … DFLEXDPSP … DDI_BUF_CTL …` を出す。
- 次: 5330 でこの kernel を起動し、TC1 か TC2 に DP の monitor を挿した log を取る（Q1）。status と well の bit で原因を決める。

- 同じ症状: `TC2: mode none -> dp-alt` → `aux AUX USBC2/DDI TC2: not done (status 0x00000000; control 0x64410 reads 0x00000000; AUX wells bios 0x00000101 driver 0x00000303 ...)` → `TC2 AUX failed: mode=dp-alt links=1 legacy=0 cold=1 live=0x1 | TCSS_DDI_STATUS=0x00000025 ...` → `DP-ext TC2: disconnected (step receiver capabilities, rc -16)`。retry 0〜5 で繰り返し。
- Q1 の見立て（未確認）: 起動時は `cold=0`、挿した後の AUX の時に `cold=1`。AUX_CH_CTL（0x64410）が書いた後も 0 を読む → TCSS が TC-cold のまま AUX の register に届いていない疑い。Linux の Tiger Lake は TC の AUX を使う前に pcode の mailbox で TC-cold を止める（`tgl_tc_cold_request`、TGL_PCODE_TCCOLD）。これが無い・効いていないかを最初に調べる。
- 2026-10-08 午後 Q1: P2 に割当（USB-C はユーザーの優先順の 2 番、WS191 より上）。

## 原因の推定と直し（2026-10-08 午後 P2、q898、code と Linux の参照で。実機は未）

- **原因（推定、強い）**: XE_LPD（display 13、ADL-P）の電源の map（`display/power.c` の `i915_power_map_init`）で、PW_2 と DC_off の domain の一覧に Linux の `XELPD_DC_OFF_PORT_POWER_DOMAINS` の半分しか無かった（DDI の lanes だけ。VGA・audio playback・AUX_IO_C〜E・AUX_C〜E・**AUX_USBC1〜4**・AUX_TBT1〜4 が欠けていた。参照は `plan/ws031/linux-parity/linux-reference/i915-src/display/intel_display_power_map.c` の 1247〜1308 行）。そのため Type-C の port の AUX_USBC の domain（TC cold の block と AUX の転送が取る物）は AUX_USBC の well だけを点け、PW_2・DC_off を点けない。connect は DDI の lanes の domain（PW_2）の下で DDI_BUF_CTL の PHY ownership（bit 6）を立てるが、connect の終わりにその domain を返すと PW_2 が落ちて（eDP だけの時は他に PW_2 の利用者がいない）、ownership と AUX の channel の register が消える。
  - log と合う: AUX の失敗の時 `DDI_BUF_CTL=0x00000080`（ownership の bit 6 が無い。Linux の M-3 は点灯中 0x80001146）、`TCSS_DDI_STATUS=0x25`（M-3 の Linux は 0x2d、bit 3 が無い）、AUX_CH_CTL（0x64410）は書いた後も 0 を読む（PW_2 が落ちた register）、AUX の well（0x45444 の 0x303 = AUX_A と AUX_USBC2）は点いている。
  - `cold=1` は TC cold の中ではなく「TC cold を block している」（tc.c の `cold_held`）。ADL-P の DP-alt の TC cold の block は Linux でも pcode（TGL の `tgl_tc_cold_request`）でなく AUX_USBC の domain（`adlp_tc_phy_cold_off_domain`、xelpd に TC_cold_off の well は無い）で、zedBSD もその形。TBT の well の扱い・FIA の lane の順（adlp_tc_phy_connect）も Linux と同じだった。
- **直し**:
  - `display/power.c`: XE_LPD の pw_2 と dc_off に DC-off の port の domain の全部を足した（Linux と同じ）。
  - `display/aux.c`: AUX の失敗の報告の行に `main wells driver`（0x45404、PW_1・PW_2 の要求と状態）と `DC_STATE_EN`（0x45504）を足した（直らなかった時の切り分け）。
  - log の書式の未展開: DP（`dp-internal.h` の `I915_DP_LOG`、`dp-sink.c` の `drv_i915_dp_notef`）と VBT の parser（`vbt.h` の `I915_VBT_LOG`、`vbt.c` の `drv_i915_vbt_notef`）の message を、出す level の時だけ引数を評価して kernel の printf の subset（`kern_vsnprintf`、subset の外の変換は書いたまま出し引数は消費する）で整形する。DP の接頭は `i915: edp` から `i915: dp` に（外部の DP の message にも出るため）。
- **試験**: 新 `plan/ws051/tests/host-power-map.sh`（power.c を host で単独に link、XE_LPD の map で AUX_USBC1〜4 が PW_2・DC_off を点ける、AUX_TBT・AUX_C〜E・AUX_IO・VGA・audio playback、DDI lanes TC2、eDP の AUX_A は PW_2 無しで DC_off、plain・ASan/UBSan）→ PASS、直しの前の power.c では 15 個 FAIL。回帰: `plan/ws051/tests/host-tc.sh`（host-tc 112・tables 34、0 failures）。build: `make -j16 BUILD=build/p2-k ZEDBSD_CONFIG=config/ci/config-amd64.mk build/p2-k/vmunix` と、試験の kernel（`ZEDBSD_CONFIG=plan/ws075/tests/config-test-hw.mk I915_TESTS=y`、I915_TEST_SET = display_ktest・execution・display）の vmunix、warning 0。
- **未実施**: 実機（5330）。PW_2 を AUX_USBC が握るので、DP-alt の monitor を挿している間は DC5・DC6 に入らない（Linux と同じ）。

### 実機の確認の手順（Q1 からユーザーか T1 へ）

1. この kernel（main に統合後の tree）の image で 5330 を起動する。
2. USB-C の DP の monitor を **TC2**（M-3 で Linux が DP-2 として点けた口）に挿す。次に TC1 でも同じ。
3. 合格: dmesg（SSH）に `i915: TC2: mode none -> dp-alt` の後、`i915: aux AUX USBC2/DDI TC2: not done` が**出ず**、`DP-ext TC2:` の行が `disconnected (step receiver capabilities …)` でなく接続・mode の設定に進み、monitor が点灯し、Settings の Display に外部の display が出る（PNG かユーザーの目視）。
4. 不合格の時に返す物: `i915: aux …` の行（新しく `main wells driver 0x…` と `DC_STATE_EN 0x…` が付く: PW_2 の要求 bit 3・状態 bit 2 が立っているか、DC_STATE_EN の下位 bit（DC5・DC6）が 0 か）、`TC2 AUX failed: …` の行（`DDI_BUF_CTL` の bit 6（0x40）が立っているか）、`i915: dp [err] …` の行（今度は値が展開されて出る）。
