# BUG-244: i915 の render で buffer・image が bind した VkDeviceMemory を生の pointer で持ち、vkFreeMemory の後に use-after-free

- 状態: reproduced（2026-10-08 P1: host の contract 試験の ASan で heap-use-after-free） / resolved（2026-10-08 Q1 の判定: merge dc5bc7597、contracts の memory 18 checks PASS（plain と ASan/UBSan）。実機の確認は未実施。本文の「Q1 の判定」）
- 発見: ws083-p001 の design-reviewer（P1 の報告、2026-10-07）

## 内容

- src/drivers/gpu/i915/render/memory.c の 588・617 行で、buffer・image が bind した VkDeviceMemory の record を生の pointer で持つ。vkFreeMemory（397〜411 行）の後も残る。
- その後の drv_i915_gfx_memory_va（command.c 2582 ほか）が解放済みの record を読む use-after-free（app が規格違反の順で memory を先に free した時）。kernel の中の実行器なので、悪い app が kernel の memory を壊せる恐れ。

## 次

- 参照の数を持つか、free の時に bind している buffer・image を切り離す（WS031 の範囲、準正常・異常系として WS177 の backlog か、security の観点で優先を決める）。

## 2026-10-08 P2 の確認（q869）

- **未実装**: src/drivers/gpu/i915/render/memory.c に「buffers and images bound to it keep a dangling pointer」の XXX が残る。`drv_i915_gfx_free_memory` は remove と release だけ。
- 証拠: code を読んだだけ（再現の試験・QEMU 無し）。
- 残り: 参照の数か、free の時の切り離しの実装（WS031）。どの backlog に入れ、security としてどれほど急ぐかは判断が要る（Q1・ユーザー）。

## q871（P1、2026-10-08、ユーザーの決定「BUG-244: はい、優先度を上げてください。」）

### 確かめたこと（読んで、host で再現）

- `drv_i915_gfx_free_memory` は表から外して record を `kern_free` するだけで、bind した buffer・image（`struct i915_gfx_buffer`・`struct i915_gfx_image` の `memory`）は
  解放済みの record を指したまま。その後の draw・copy・dispatch・video（`drv_i915_gfx_memory_va`・`_cpu` の 20 か所ほど、command.c・state.c・image.c・draw.c・video.c）が
  `memory->object` を読む → kernel の heap の use-after-free。悪い（規格に反する）app が kernel の memory を読ませられる。
- record の pointer を持つのは buffer と image だけ（video.c は identity で毎回引く。device の list `vk->memories` は free の時に lock の下で外れる）。
- session の終わり（`drv_i915_gfx_objects_release`）は memory を先に放し、buffer・image は record を読まずに `kern_free` するので安全。
- host の再現: 新しい `src/drivers/gpu/i915/tests/contracts/memory_contract_test.c`（memory.c・object.c・codec.c・reply.c を host で動かし、wire の bind と free を送る）を
  修正前の memory.c で ASan にかけると `heap-use-after-free`。

### 修正

- `render/object.c`・`object.h`: `drv_i915_object_each(session, kind, visit, argument)` — session の kind の object を表の lock の下で訪ねる（visit は object だけを変え、
  表と lock に触れない）。
- `render/memory.c`: `drv_i915_gfx_free_memory` は record を表から外した後、session の buffer と image のうちその memory に bind した物の `memory` を NULL・`offset` を 0 に
  してから record を放す（以後その buffer・image は storage 無し: GPU address 0・CPU view NULL。読む側は前から NULL を受ける）。bind されたままの free は 1 行 log
  （`i915: vk: vkFreeMemory of an allocation still bound to N buffers and M images; they have no storage now`）。XXX の comment を消した。
- 参照の数（refcount）にしなかった理由: Vulkan の規則では free の後のその buffer・image の使用は app の誤りで、storage を残す必要が無い。切り離しは
  解放済みの kernel の memory を名指す pointer を残さないことだけを保証し、record の寿命は今のまま（表・list と同じ）。

### 確認

- host: `memory_contract_test`（新しい、`run.sh memory`）18 checks PASS、plain と ASan/UBSan（leak 検出あり）。修正前の memory.c では ASan の heap-use-after-free で落ちる。
  `run.sh` は既定の組に `memory` を足した（この test は host_unreached を link しない）。`run.sh` 自体は trap の rm を含むので担当は走らせていない（同じ compile の列を
  build/tmp で手で流した）。
- build: kernel（`make BUILD=build/p1-wl ZEDBSD_CONFIG=plan/ws113/tests/config-amd64-p005.mk vmunix`、i915 を含む）warning 0。style-check 新しい指摘 0。
- 未実施: 実機（5330）。QEMU では i915 の executor は動かない（i915 は passthrough だけ、Venus の経路は使わない）。

### 確認の方法の案（Q1 へ）

1. 主の証拠は host の contract 試験（上、ASan で旧の再現と新の PASS）。T1 は QEMU を使わず `src/drivers/gpu/i915/tests/contracts/run.sh memory` を流せる（rm は script の trap）。
2. 実機（5330、T1 の i915 の lock の下）: libvulkan で memory を確保し buffer を bind、memory を先に free して、その buffer への `vkCmdCopyBuffer` を submit する小さな
   program（または `I915_TEST_SET` の新しい場面）。期待: kernel の log に上の 1 行、panic・GPU hang 無し、copy は storage 無しで何もしない（GPU の address 0 への書き込み
   は ppgtt の外で fault、session だけの失敗）。作るかは Q1 の判断。

### 残り（同じ種類の疑い、範囲外）

- buffer・image を先に destroy した時の buffer view（`view->buffer`）・image view・descriptor set・framebuffer の pointer（`i915_gfx_destroy_plain` は kern_free するだけ）。
  同じ「規格に反する順の解放」で同じ use-after-free の形になりうる。読みだけで未確認。別の Bug にするかは Q1 の判断。
