# BUG-338: VF2 の実機で SMP が S7 の監視用の hart 0 を起こそうとして止まる

- 状態: closed（2026-10-31 Q1 の判定、main f52088f45）← reproduced（2026-10-20 ユーザーの VF2 の実機）/ resolved（2026-10-31 P2 の VF2 の実機で U-Boot の control の DTB を渡して 4 CPU が online。closed の案）
- 発見: ユーザーの VF2 の UAT（beta2 U27、U-Boot の prompt から `load mmc 1:1 ${kernel_addr_r} EFI/BOOT/BOOTRISCV64.EFI; bootefi ${kernel_addr_r} ${fdtcontroladdr}`）。ユーザーが貼った serial の log（判定には使わない、手がかり）: `RISCV64 SMP 5 CPUs (device tree 5 usable of 5, limit 8)` の後、`sbi_trap_error: hart0: … mcause=0x5 mtval=0x4003d068`、`RISCV64 SMP cpu 1 (hart 0) did not come up`、`fatal: src/hal/riscv64/smp.c:621`。
- 原因（見込み）: JH7110 の hart 0 は SiFive S7（rv64imac_zba_zbb、S-mode・F・D が無い監視用の core）。U-Boot の control の DTB（`${fdtcontroladdr}`）では hart 0 も mmu-type 付きで usable と数えられ（`src/hal/riscv64/fdt.c` の usable の判定は mmu-type と status だけ）、SBI の HSM で起こして OpenSBI が trap した。vendor の Linux の DT は cpu@0 が `sifive,s7`、`rv64imac_zba_zbb`。
- 同じ log で分かった良い事: 配布の U-Boot 2021.10 は bootefi で GOP（1920x1080、format 1、base 0xfe000000）を出し、zedBSD の loader が受け取った（`RV64 GOP handed over`、`RISCV64 FRAMEBUFFER 1920x1080 phys=fe000000`）。WS277 の D1（U-Boot の mode の引き継ぎ）の前提が成り立つ見込み。
- 関係: WS256（p004 の SMP・FDT）。

## 修正（2026-10-20）

- 原因: `src/hal/riscv64/fdt.c` の `keep_cpu()` は、hart を `mmu-type` があり `status` が okay なら usable と数え、ISA を見ていなかった。U-Boot の control の DTB で S7 が okay・mmu-type 付きなら（実物の DTB は未確認、症状の `5 usable of 5` と合う）、smp.c が SBI の HSM で S7 を起こす。S7 は S-mode・F・D が無く、OpenSBI が trap した。
- 直し（`e8b65b6e9`）:
  - `fdt.c`: `cpu_runs_system()` を足し、usable の条件に「system が build された base の拡張 i・m・a・f・d・c（kernel は rv64imac、userland は rv64gc）を持つ」を加えた。`riscv,isa-extensions` があればその list で各文字を探し（`cpu_extensions()` と同じ優先）、無ければ `riscv,isa` の文字列を `rv64` で始まる事を確かめてから、width の後の 1 文字の拡張（版の数字は飛ばし、`_` か h・s・x・z で終わる。`g` は imafd）を見る。どちらも無い hart は持つと言えないので usable にしない。S7（rv64imac）は F・D が無いので usable にならず、これまでどおり数えるだけ。
  - `smp.c`: boot の hart は tree の記述によらず usable と数える（logical 0 のまま。ISA の判定で boot の hart を外さない）。
  - `fdt.h`: `usable` の説明を直した。
- 確かめ（host、QEMU・実機は未実施）:
  - `plan/tools/vf2-host/fdt/run.sh build/bug338/fdt`: 37 項目すべて PASS（`PASS 0 failed`）。足した `jh7110-uboot-like.dts`（S7 の hart 0 が status okay・mmu-type 付き・`riscv,isa = "rv64imac_zba_zbb"`、hart 1〜4 は list・文字列・`rv64gc`・list だけの各形）で「five harts, four usable」「S7 hart 0 not usable」「U74 harts 1 to 4 usable」。既存の `jh7110-like.dts` の hart 2〜4 に ISA の文字列（`rv64imafdc_zba_zbb`・`rv64gc`・版付きの `rv64i2p1m2p0a2p1f2p2d2p2c2p0_zicsr2p0`）を足した（新しい条件では ISA の無い hart は usable でないため）。
  - 直す前の `fdt.c`（`de5e5094c`）を同じ試験で build すると、新しい case が `FAIL jh7110-uboot: five harts, four usable`・`FAIL jh7110-uboot: S7 hart 0 not usable` になる事を確かめた。
  - build: `config/ci/config-visionfive2.mk` と `config/ci/config-riscv64-virt.mk` の `vmunix`（`BUILD=build/bug338/vf2`・`build/bug338/virt`）が rc 0、warning 0。
- 残り: VF2 の実機で U-Boot の control の DTB を渡した起動（`RISCV64 SMP 4 CPUs (device tree 4 usable of 5 …)` 相当で S7 を起こさず先へ進む事）の確認は未実施（T1 へ）。QEMU の virt で SMP が従来どおり全 hart を使う事も未実施。

## 実機の確認（2026-10-31 P2、q1772-i01）

- kernel: main cf41e7630 ＋ q1772 の SD の直し（cksum 868265884 と、log の一行を足した 89526334）。U-Boot の prompt で
  `mmc rescan`・`load mmc 1:3 ${kernel_addr_r} /EFI/BOOT/BOOTRISCV64.EFI`・`bootefi ${kernel_addr_r} ${fdtcontroladdr}` を serial から打った
  （`plan/tools/vf2/uboot-serial.py`、電源の入れ直しから autoboot を止めて打つ）。2 回とも同じ結果。
- 生きた serial の行（板は BUG-339 で VFS で止まり SSH が無いので、判定は serial の行による。QEMU ではない）:
  `RISCV64 SMP 4 CPUs (device tree 4 usable of 5, limit 8)`、`cpu 1 online (hart 2)`・`cpu 2 online (hart 3)`・`cpu 3 online (hart 4)`、
  `RISCV64 SMP 4 ONLINE`。OpenSBI の trap（`sbi_trap_error`）と `did not come up` は無い。
- 渡った tree（U-Boot の `md.b` で読み出した control の DTB、54304 byte）は cpu@0 が `sifive,s7`・status okay（直す前の 5 usable の条件）。
- ESP の mainline の DTB の道（通常の起動）でも `CPUs ready: 4`（dmesg、boot-cycle.sh が数えた 28 回の起動の全部）。
