# BUG-394: 起動が長い。network の有効化が desktop・login の prompt の前に待っている見込み。init が desktop の表示を優先して順番を組めるように

- 状態: fixed（init の順と sessiond の印。2026-11-02 P7、QEMU と Pi 5 の実機で確かめた。Pi 5 の desktop の表示までの時間は画面が検出されず未計測）。kernel の GPU・display の self-test の待ちは BUG-393 の側
- 発見: 2026-11-02 ユーザーの Pi 5 の UAT。起動時間が長い。以前、init が network を有効にする部分は desktop の起動の後か login の prompt の表示の後に遅らせたはずだが、また起動時に待つようになっているかもしれない。全般に、desktop の表示を優先して init を schedule できるようにしてほしい。
- 背景（2026-11-02 ユーザー）: 電力を常に確保できない地域があり、sleep でなく電源を切って運用する事も想定する。そのため電源を入れてから使えるまでの時間（desktop か login の prompt が出るまで）を短くする事が、製品の要件として重い。
- 扱い: P7（q1892）。(1) 起動の各段の時間を測り（Pi 5 の CI の image と QEMU）、network の待ちが desktop・login の前に戻っていないか、戻ったならいつの commit かを調べて直す。(2) init（と service の定義）が「desktop・login の prompt を先に、その他の service を後に」と優先して順番を組める仕組みを入れる。

## 原因（P7、2026-11-02）

- init の 2 段の起動（WS253、b2f0919a7・d9dbec60d、2026-10-16）は、service の `late=yes`（network・sound・sshd・cron など）を desktop の後に回す。ただし 2 段にするのは起動の parameter が `login=graphical` かつ `kmsg=quiet` の時だけで、他は「debug の起動」として依存の順の 1 段（greeter・getty_console は `after=syslogd,networking` なので networkd の READY（最大 10 s）と `net startup` を待つ）。
- Pi 4・Pi 5 の CI の image は `ZEDBSD_BOOT_KERNEL_MESSAGES := y` で、cmdline.txt は `login=graphical rpi5gpu.start=boot` だけ（kmsg= が無い）。init は kmsg=quiet でないので debug の起動と見なし、greeter が network の後になる。回帰の commit ではなく、Pi 5 が graphical login になった bbc602814d（2026-11-01）の時から 2 段の起動の条件の外にあった。text の login（getty_console）の起動も、どの image でも常に network の後だった。
- Pi 5 の実機（ユーザーの UAT の image 1.0.0-beta2+g8f91a0d、2026-11-02 01:46 に Q1 が電源を入れ直した起動、SSH で読むだけ）の内訳（kernel の時計、秒）: kernel の devices attached 0.39 → boot storage discovered 6.32 → VFS 6.80 → init 6.82 → greeter の start 7.23 → compositor の start 7.52 → desktop shown 8.25 → files の desktop drawn 9.73。init の order は `dependencies`（debug の順）。この起動では networkd の READY が 41 ms・networking が 0.1 s で、network の待ちは約 0.15 s だけだった（Wi-Fi の radio を下ろす所が遅い時は最大 10 s）。root の UFS は rw。
- Pi 5 の最大の待ちは kernel の 0.39 → 6.32 s（5.9 s、`kern_platform_refresh_devices`）。この間に hvs6 の display の self-test（R1 64 vblanks 1.07 s、rpi4gpu P1 の 1 s の vblank の観察、P2・P3 の 100 ms の pause、R2 の overlay 30 steps）と v3d の V5〜V9 の self-test（V9 は hang を timeout で検出）を同期で流す。/boot/boot0/log の過去 6 回の起動も 6.2〜6.6 s で同じ形。行に時刻が無いので内訳は推定。firmware と loader の時間は未計測（板に RTC が無く電源の時刻と結べない）。この driver は BUG-394 の範囲（init）の外なので直さない（BUG-393 の扱い）。

## 設計（P7 の案、2026-11-02 Q1 に送った）

- init の約束を変える: 2 段の起動（login を先に、late を後に）を既定にし、1 段の依存の順（debug の起動）は `kmsg=console` が明示された時だけにする（amd64 の loader で Ctrl を押した時。Pi は cmdline.txt に書く）。kmsg= の無い起動（Pi）と kmsg=quiet は login を先に。
- login=console（Shift）だけの起動も login を先に（getty_console が networking を待たない）。WS253 の時は login=console も debug の起動だったが、今回の「login の prompt の後に network」の趣旨に合わせて変えた。console の login の起動では、prompt の後に init・late の service の行が console に出る（kmsg を出す起動では kernel の行も元々出る）。
- Q1 の判断（2026-11-02）: (a)〜(c) を案のとおり進める。(b) は、2026-11-02 のユーザーの指摘（network の有効化は desktop の起動の後か login の prompt の表示の後、全般に desktop の表示を優先）が WS253 の「debug の起動は今のまま」のうち login=console の部分より新しい決定として優先する。console の login で prompt の後に init・late の行が出る事は `docs/reference/init-services.md` の Boot order に書いた。
- Q1 の判断（2026-11-02、P7 の問いに）: console の login の起動で prompt の後に init・late の行が出る事は、別の件にしない。text の login の image は debug 用なので行を残し、quiet の image では出ない。
- 仕組みは既存の service の定義の `late=yes`・`desktop=yes` のまま（新しい key は足さない）。既存の定義は変えない。timeline の語は `order login-first`・`round login-started`（前は desktop-first・desktop-started）。
- 変えた file: `userland/base/init/main.c`（判定の関数 `boot_puts_login_first`、名前と comment）、`docs/reference/init-services.md`、`docs/reference/kernel-boot-parameters.md`、`userland/desktop/sessiond/greeter.service`（comment）、`userland/desktop/sessiond/main.c`（最初の起動の失敗でも印を置く、Pi 5 の計測の後に足した）。計測の道具 `plan/tools/boot-time/`（`config-amd64-boottime.mk`・`boot-time.py`）。

- login を先にした事で、init が login（greeter・getty_console）を始めるまでが 0.26〜0.29 s → 0.02〜0.04 s になった。network が速く答える QEMU の user-net ではこの差だけで、host の時計の screen は粗さの中に入る。同じ image の先の 1 組（host の load が高かった時）では、1 段の順の greeter が homes・networkd（READY に 4.2 s）・networking（4.1 s）の後で init の開始から 11.3 s・3.8 s・0.26 s 待った（`build/bug394/out/console/`）。2 段の順はどの run も 0.03 s 前後。network の待ちは環境で大きく揺れる（networkd の READY は最大 10 s）ので、login を先にする事がその揺れを desktop・login から外す。
- network は後で上がる: 2 段の順では SSH の最初の応答が desktop の画の後（host で約 2〜3 s 後）、1 段の順では desktop の画より前だった。text の login の起動の init.log は `start greeter` → `round login-started` → `start getty_console`（0.598）→ `desktop not-running` → `start networkd`（0.801）→ `done networking`（0.912）→ `start sshd` の順。
- text の login の起動では prompt の後に init・late の service・dhcpc の行が console に出る（画面: worktree の `build/bug394/out3/text-console.png`）。docs の Boot order に書いた。
- build: `plan/tools/guest/test-image.sh plan/tools/boot-time/config-amd64-boottime.mk build/bug394/img`（-Werror。init の warning 0）。計測の出力は worktree の `build/bug394/out3/`（console・none・quiet・text）。

## Pi 5 の実機の変更の後（P7、2026-11-02 02:26〜02:39）

- 板はユーザーの UAT の image（1.0.0-beta2+g8f91a0d）。main 86d360426 の kernel（cksum 2887926735、BUG-393 の後）と init（2218740128）を置いた。init は /sbin/init を変えずに /sbin/init.bug394 に置き、cmdline.txt に `init=/sbin/init.bug394` を足した。電源は SwitchBot のプラグミニ 2 で、sync の後に off（8 s）→ on。
- 計測は電源 on から SSH の応答まで（host の時計）と、guest の記録（dmesg の boot: at・init.log・sessiond.log）。script と出力は worktree の `build/tmp/bug394/pi5-boot.sh`・`pi5-sessiond.sh`、`build/tmp/bug394/pi5-after/`・`pi5-sessiond/`（各 summary.txt）。
- **画面が検出されなかった**: この時間の 7 回の起動は、どれも firmware が HDMI を見つけなかった（`rpi5-screen: no firmware framebuffer`、hotplug 0、EDID unreadable、640x480）。元の kernel と init に戻した起動も同じだった。01:46 に Q1 が入れ直した起動は 1920x1080 だったので、画面（monitor）の側の状態の見込み。compositor は `KWL VULKAN_ERROR operation=display` で起動できず、sessiond は 6 回の失敗の後に console へ落ちた。そのため desktop の表示までの時間は測れていない。
- kernel: boot storage discovered 0.40〜0.64 s、init の開始 0.48〜0.71 s（変更の前の image は 6.3 s・6.8 s。BUG-393 の kernel の効果）。
- init: order login-first、greeter の start は init の開始から約 2 ms（変更の前は 0.41 s）。
- **画面が無い時の新しい問題とその修正**: login を先にすると、late の service（network・sshd）は desktop の印を待つ。desktop が出ないと init はその上限の 30 s まで待ち、電源 on から SSH まで 56.8・56.9・57.8 s（既定の cmdline の 3 回）、56.4 s（kmsg=quiet）だった。元の init（1 段の順）に戻した起動は 34.1 s・40.0 s だった。直し方: sessiond が、login か自動の login の session の最初の起動に失敗した時にも同じ印 `/run/desktop-shown` を置く（`SESSIOND DESKTOP failed at_ms=`）。desktop は何度も試すか来ないかなので、network を待たせない（`userland/desktop/sessiond/main.c` の `main_desktop_mark`、docs の Boot order にも書いた）。この sessiond を置いた 1 回の起動では、自動の login が 9.79 s に失敗して印を置き、init は 9.84 s に late を始め、電源 on から SSH まで 39.2 s になった。画面が無い時は元の init（34〜40 s）とほぼ同じになった。
- firmware と loader: 電源 on から SSH の応答までの host の時間から、その時の guest の時計（RTC が無いので kernel の開始からの秒、1 s 単位）を引くと、どの起動も約 24〜25 s だった（例: 戻した起動の 34.1 s − 9 s）。電源 on から使えるまでの最大の部分は firmware と loader。画面が無く firmware が EDID を何度も読み直した（`BSC_B no ACK`）分を含むかもしれない。画面がある時の値は未計測。
- 戻し: vmunix 2112791070・cmdline.txt 3178356281・/sbin/init 1564009957・/sbin/sessiond 1920417911 がすべて元と一致した。bug394 の file は残っていない。root は ufs (rw)。
