# BUG-381: libvulkan が native の OOM の返事で job を CANCEL するが、nvrtx では前の command buffer がもう GPU に送られている事がある

- 状態: open（2026-10-31 22:32 Q1 が起票、P3 の job-submit の設計のレビュー（BL1）で見つかった）
- 中身: libvulkan の `sync.c`（749 行あたり）は、native の reply が確かな拒否（OOM）の時に GPU_JOB_CANCEL（fault でない取り消し）をする。nvrtx の queue_submit は
  失敗した command buffer の前で止まるが、それより前の command buffer と早めの push は GPU で走っている。取り消しは「何も走っていない」証明にならず、
  fence・timeline の完了の順が崩れうる。
- 直す方針（案）: driver が GPU に送った数を数え、何も送っていない時だけ CANCEL、何か送った後の失敗は CANCEL_FAULT（または完了を待つ）。
  WS291 の job-submit（GPU_JOB_SUBMIT）では P3 が同じ規則で作る。今の 3 本の ioctl の道も合わせて直す。
- 影響: nvrtx で GPU の memory が足りない時（まれ）。他の driver は未確かめ。

## 2026-10-31 P3（q1785）: 直した所と driver ごとの調べ

- 規則: libvulkan は native の OOM の答えを確かな拒否（CANCEL）と扱うまま。仕事の一部を GPU に出した後に失敗しうる driver は、その失敗を OOM で
  なく失った submit（EIO → VK_ERROR_DEVICE_LOST）として答える（答えを返す driver が知っている、libvulkan に driver の名を書かない）。libvulkan は
  OOM 以外の失敗を今どおり CANCEL_FAULT にする。送る前の transport の OOM は CANCEL のまま。（一度 libvulkan で全 driver を保守的に fault に
  する形を入れたが、一時の OOM が全 driver で device lost になるので取りやめた。）
- nvrtx: 直した（`vk/vk-queue.c` の queue_submit: この submit の間に `gpu_sends` が増えていたら失敗を EIO に）。GPU_JOB_SUBMIT の道は kernel が
  GPU に出した run の数で outcome を決める（WS291 p024）。
- 調べ（読みだけ、2026-10-31、file:line は worktree p3-ws291wsi の物）:
  - amdrdna: command buffer の間で部分がありうる。`amdrdna/vk/vk-queue.c` 145〜157 の loop が 1 つずつ実行し ring に待たずに出す（`vk-execute.c`
    860）、次の command buffer の `state` の確保（`vk-execute.c` 357〜359）の ENOMEM が OUT_OF_DEVICE_MEMORY になる。1 つの command buffer の中は
    早い ring の submit の後に ENOMEM は出ない。直し方: loop の index が 0 より大きい時の失敗を EIO に（未実施、P2 の driver、実機が無い）。
  - i915: 部分がありうる。全 command buffer を 1 つの batch に記録するが、満ちた時（`vk-draw.c` 352）や window が尽きた時（287）に早く走らせ、
    失敗の後も `submit_end` が記録した分を走らせる（`vk-command.c` 3857〜3862）。転送の kernel の遅い compile（`vk-blit.c` 113〜137）の ENOMEM が
    その後に来うる。直し方: 何か走らせた（または失敗の後に走らせる）時の失敗を EIO に（未実施）。
  - powervr: 部分がありうる。render pass の job と転送はすぐ走る（`powervr/vk/vk-queue.c` 1527・867、前の stream は 1490 で kick）、後の
    dispatch の `jobs` の確保（827）や compiler の buffer（949・955・963）の ENOMEM が OUT_OF_DEVICE_MEMORY（`vk-object.c` 338〜339）。
    直し方: この submit で job を走らせた後の失敗を EIO に（未実施）。
  - bcm2711（V3D）: all-or-nothing。失敗しうる準備（decode・`prepare_submission`・admit・`create_execution`）は全部 `vulkan-queue.c` 199 の
    submit の前、その後の答えはいつも VK_SUCCESS（失敗は fence の状態で）。直し不要。
  - venus: guest の側は all-or-nothing（stream を丸ごと transport に渡し、OOM は packet の確保 `transport.c` 962〜963 の、送る前だけ）。host の
    renderer の部分の失敗は host の driver の規則（調べていない）。
- 残り: amdrdna・i915・powervr の上の直し（各 driver の担当へ）。
