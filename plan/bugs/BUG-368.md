# BUG-368: amd64 の QEMU で「invalid amd64 APIC acknowledgement」の fatal（EOI の記録が CPU の積みと合わない）

- 状態: fixed（2026-10-31 P4 q1753-i01、f045ddf59。原因は source の読みと objdump で道を確かめた候補、QEMU での再現と観測は未実施。main に未 merge）
- 発見: 2026-10-30 P2（WS327 p016、QEMU の AAT の回帰の 1 回目）。Video Player の再生の途中（直前の klog は `venus: context=9 opened pid=448`）で guest が止まった。QMP で 4 CPU とも HLT・IF=0、CPU#1 が amd64_lapic_panic_all。gdbstub で klog_buffer の末尾: `fatal: src/hal/amd64/irq.c:290: invalid amd64 APIC acknowledgement`、caller は `hal_irq_send_eoi`+0x77（irq_handler から）。
- 条件: QEMU に音の device（`-audiodev none -device intel-hda -device hda-duplex`）を足した run。image は P2 の build/ws327-p016-aat（tree 5bfe04792）。再現は P2 が確かめ中。
- 意味: `hal_irq_send_eoi` に渡された acknowledgement が、その CPU の acknowledgement の積みの一番上でない（入れ子の割り込みの順の崩れ、別の CPU の記録での EOI、二重の EOI のどれか）。
- 直す方針: 再現を取り、どの割り込み（HDA・virtio-gpu・timer）の EOI が順を外れたかを gdbstub で確かめる。HAL の実装（src/hal/）の直しは承認不要、HAL の API は変えない。
- 再現（2026-10-30 P2）: 同じ image・同じ条件（音の device あり）の 2 回目では出ず、Video Player・Photos・Settings を通った。1 回だけの観察。QEMU の command line は WS327 の guest-apps.sh（WS の完了で削除、git の履歴に残る。zdesktop-guest の Venus の command line ＋ `-audiodev none,id=snd0 -device intel-hda -device hda-duplex,audiodev=snd0`、boot の disk は cache=unsafe）、image は P2 の worktree の build/ws327-p016-aat、vmunix は build/ws327-p016-aat/vmunix。

## 解析と直し（2026-10-31 P4 q1753-i01、bug-analyzer の解析、f045ddf59）

- 道（objdump で実際の binary にあると確かめた）: irq_handler の realtime の handler → `pci_irq_dispatch` → `xhci_irq` → `xhci_completion_drain` → `drv_usb_hcd_complete` → `urb_publish_terminal`（`src/drivers/usb/usb.c`）。ここで URB の submit の記録を別の CPU の submitter が先に取り、まだ `submit_commit_pending` を 0 にしていない時、割り込みの中で `sched_yield()` を回していた。割り込まれた thread は ack の record（CPU の積みの上、active）を持ったまま run queue に戻り、別の CPU に盗まれて戻ると、`xhci_irq` から戻った `pci_irq_dispatch` の tail call の `hal_irq_send_eoi` が別の CPU の積みを見て `invalid amd64 APIC acknowledgement`。`pci_irq_dispatch` は `jmp hal_irq_send_eoi` の tail call なので、caller は irq_handler に見える（klog の `hal_irq_send_eoi+0x77` と合う）。窓は submitter の atomic の数個分で、KVM の vCPU が host に止められると広がる（1 回だけで再現しない事と合う）。
- 他に調べて道が無かった物: venus・HDA・NVMe・ACPI の SCI・PS/2 の割り込み（spin と wake だけ）、二重の EOI、無条件の sti、supervisor の page fault、task mode の IRQ（呼び元なし）。
- 直し（`src/drivers/usb/usb.c`、HAL は変えない）: submit の記録を取る側は全て、取ってから `submit_commit_pending` を 0 にするまで local の割り込みを止める（submitter は前から、terminal の publisher も止めるようにした）。そのうえで、取れなかった側の待ちは短いので `sched_yield()` でなく `atomic_spin_hint()` で回る。publisher の側（割り込みの中）と submitter の側（callback が割り込みの中から再提出する時）の両方。
- 確かめ: amd64 の vmunix の build（warning 0）。この直しを含む image（tree f045ddf59）で QEMU の起動・SSH・USB の stick と usb-net の通信が動く事（BUG-351・BUG-359 の試験の間）。USB の通信の負荷試験は host の /tmp が満杯になって QEMU が止まった時期と重なり、判定できなかった（未実施扱い）。
- 未実施: 元の条件（Venus＋intel-hda で Video Player の再生）での再現と、直す前の kernel で `urb_publish_terminal` の `call sched_yield` に条件つきの breakpoint（ack の深さ > 0）を置いて道を直に見る事。
- 案（入れていない）: HAL の `hal_task_context_switch` の実装で、ack の積みが空でない時の切り替えを検出する。今は同じ CPU に戻れば無害な場合もあるので、fatal にすると挙動が変わる。入れるなら klog の警告から。
