# BUG-422: CPU の affinity が無く、cpuperf の測りの thread が他の CPU に移る

- 状態: fixed（2026-11-13 Q1。P2 の 97528b4670 を main に merge。host 試験 46 checks・cpuperf-host PASS、x86_64・rpi5 の kernel warning 0、QEMU amd64 -smp 4 で login prompt。5330 で `cpu N not measured` が出ない事は WS333 の次の 5330 の測定で確かめる）
- 発見: 2026-11-12 P1（WS333 p025）。5330 の起動の log に `cpuperf: cpu 4 not measured (24)`（EAGAIN）。cpuperf の測りの thread は `sched_set_cpu` で CPU に置くが、1 tick 以上 run queue に居ると idle の CPU の `steal_runnable`（`src/kern/sched.c` の `take_stealable_locked`）が取って移す。E-core の `highest_mhz` が 0 になった原因。
- 正しい振る舞い（2026-11-13 ユーザーの決定の要点）: affinity を設定していない thread は自由に CPU を移る（work stealing は正しい）。CPU に留まるのは affinity を設定した thread だけ。
- 食い違い: `src/kern/sched.c` の file の comment は「thread は CPU に固定され、`sched_set_cpu()` でだけ移る」と古い。kernel に affinity の仕組みが無く、`sched_set_cpu` は一度置くだけ。
- 影響: CPU を名指して置く kernel の thread（今の呼び手は `src/kern/cpuperf.c` だけ）が、その CPU で走る事を当てにできない。CPU ごとの MSR・計測の値が別の CPU の物になりうる。
- 当座: P1 が p025 で cpuperf の側に「busy の後に CPU を確かめ、外れたら 3 回まで測り直す」を入れた（agent/p1-ws333h dc89af4412）。
- 直し方: kernel の thread に affinity（留まる CPU の指定）を足し、affinity のある thread だけを `take_stealable_locked` が飛ばす。affinity の無い thread は今どおり移る。cpuperf の測りの thread は affinity を付けて置く。sched.c の file の comment を「thread は自由に移り、affinity のある thread だけが留まる」に直す。HAL の API は変えない。user の process の affinity（syscall）は範囲の外。cpuperf の測り直しは守りとして残すか外すかを直す担当が決める。
- 確かめ: host の sched の試験に「置いた thread が盗まれない」場面を足す、QEMU の SMP（-smp 4）で起動、5330 で `cpu not measured` が出ない事。

## 経過

- 2026-11-13 P2（q2024-i01、worktree `p2-bug422`、基点 main 641f1ad69b）が直した。
  - 口: `include/kern/sched.h` に `enum sched_cpu_affinity`（`SCHED_CPU_FREE` = 0、`SCHED_CPU_BOUND`）と `struct sched` の `affinity`（calloc の 0 で全 thread が FREE）。`sched_set_cpu(thread, cpu, affinity)` に引数を足した（呼び手は cpuperf だけ）。移す時は新しい CPU の lock の下で affinity を置き、同じ CPU なら `set_affinity_in_place` がその CPU の lock の下で置く（移動中は EBUSY）。失敗では affinity を変えない。知らない値は EINVAL。
  - 盗み: `take_stealable_locked` は各段で `first_free_thread` が woken・run の列を頭から見て BOUND を飛ばす。BOUND が頭に居ても後ろの FREE は今どおり盗まれる。BOUND の無い列では前と同じ thread を選ぶ（頭だけを見ていた形と同じ）。
  - cpuperf: 測りの thread を `SCHED_CPU_BOUND` で置く。busy の前後の CPU の確かめと `CPUPERF_MEASURE_TRIES` の測り直しは守りとして残した（別の CPU の値を決して記録しない。affinity の後に外れたら scheduler の誤りで、3 回とも外れれば `not measured` に出て見える）。comment を「bound なので盗まれないが、それでも確かめる」に直した。
  - `src/kern/sched.c` の file の comment を「thread は自由に移り、`sched_set_cpu()` で bound にした thread だけが CPU に留まる」に直した。`sched_set_cpu` の呼び手は `src/kern/cpuperf.c` だけ（grep、src・include）。
  - 他に thread を CPU から動かす所: `sched_prepare_thread`（作る時の置き場所、bound の前）と盗みだけ。tick の `backlog` は BOUND だけが待つ CPU でも idle の CPU を 1 つ起こす（起きた CPU は何も取らずに止まる。tick ごとに高々 1 回の無駄な通知で、正しさには触らない。直していない）。
- CPU が止まる時（Q1 の確かめの依頼）: 実行時に CPU を外す道は無い（`scheduler_cpus[].online` は 1 を書くだけ、`sched.c` の 386・1648・1946 行。`hal_cpu_park`・`hal_cpu_panic_all` の呼び手は panic と停止の `src/kern/entry.c:505`・`src/kern/platform/pcat.c:516` だけ）。system の sleep は S0 idle（`src/kern/sleep.c`。S3 の kernel の道は無い）で、各 CPU は自分の idle の loop（`sched_idle`）の中で、run queue が空の時だけ `kern_sleep_idle` から suspend-to-idle に入り、同じ loop に戻る。queue・`sched.cpu`・`affinity` は触られないので、BOUND の thread は戻った後も同じ CPU で続く。sleep の間に BOUND の thread を起こすと `notify_cpu` が その CPU に通知し、通知は `hal_irq_suspend()` の間も届く（`include/hal/hal.h` 161〜163 行の契約）ので、その CPU が起きて走らせる。BOUND の thread が queue に居る CPU はそもそも idle にならず suspend に入らない（FREE の kernel の thread が居る時と同じ）。直す物は無い。
- 確かめ（host）:
  - 新しい `plan/bugs/BUG-422/sched-affinity-host.sh`（`src/kern/sched.c` を freestanding で取り込み、HAL と kernel の他は stub）: 5 場面 46 checks、0 failures。場面は FREE が盗まれる・BOUND は 100 tick 待っても盗まれない・BOUND の後ろの FREE は盗まれる・`sched_set_cpu` の BOUND の移動／同じ CPU の FREE・BOUND／移動中の EBUSY／知らない値の EINVAL・NEW の thread を BOUND で置いて `sched_add` の後も盗まれない。`first_free_thread` の飛ばしを外した sched.c では 18 failures（試験が直しを見分ける事の確かめ）。
