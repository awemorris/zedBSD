## 解放を compositor の暇な時に回す（2026-10-08 夜、P2 q878）

T1-392 の残り（drain の約 20 s の間 frame_ms 510〜604 ms）の直し。1 回の解放（import の vkDestroyImageView・vkDestroyImage・vkFreeMemory と、buffer の fd の close）は分けられない（それぞれ同期の往復）ので、「枠を越えたら次の frame へ」ではなく、**1 回を走らせる時を選ぶ**形にした。

- `objects.c` の `kwl_retire_ready(server, now)`（新）: 解放してよいのは、list が空でない、**frame が飛んでいない**（`compose->in_flight == 0`。飛んでいる間の解放は frame の完了を遅らせ、Venus では host の ring でその frame の後ろに並ぶ）、前の解放にかかった時間だけ後（C ms かかったら次の C ms は frame と input に譲る）、かつ「input が 200 ms 無く（`lock_input_ms`）描く物も無い（`server->dirty == 0`）」か「list が最後の解放から 1 s 待った」（ずっと描き続ける画面でも進む）。
- `kwl_retire_tick` は解放の始めと終わりを測り `retire_last_ms`・`retire_next_ms`（`kwl.h` の server に追加）を置く。
- `main.c`: poll の timeout を 0 にするのは解放してよい時だけ（今までは list が空でない間ずっと 0 で、work 99% の空回りになっていた）。`kwl_schedule` の後の解放も `kwl_retire_ready` の時だけ。
- 見込み: frame の途中に解放が入らないので frame_ms は解放に引き延ばされない。input の後 200 ms は解放しないので、操作中の画面は止まらない。止まるのは、暇な時に始めた 1 回の解放の途中に来た input だけ（最大で 1 回の解放の時間）。drain の合計の時間は、暇な時が続けば今と同じ程度、操作が続けば 1 s に 1 個まで遅くなる。
- AAT `desktop.session.release-clients`: kill の後の `KWL PERF compose … frame_ms=` の最大を記録し、100 ms 以下を合否に足した（tests/scenarios/desktop/session/release-clients.md も）。
- build: zedBSD の compositor（`build/p2-k/bin/wayland`）と keiland-linux は warning 0、style-check 0（objects.c・main.c）、check-scenarios PASS。host の試験は無い（objects.c・main.c を compile する host の試験は無い）。QEMU は T1 に依頼。

## 1 回の解放が遅い理由（調べた範囲、2026-10-08 夜 P2）

- libvulkan: 全ての command は返事を待つ同期の transaction（`wire.c` `vulkan_command_execute` → `vulkan_context_execute`、context の mutex の下）。destroy・free にも返事を待つ。vkFreeMemory は blob の破棄（ioctl `GPU_RESOURCE_DESTROY`）と renderer の memory の破棄（`GPU_OP_FREE_MEMORY`）の 2 回。import 1 つで vkDestroyImageView・vkDestroyImage・vkFreeMemory の往復が 4 回。
- kernel（`src/drivers/gpu/venus/venus.c` の resource の解放）: blob の UNMAP_BLOB（0x0209）・context からの DETACH（0x0203）・UNREF（0x0102）を、それぞれ virtio の control queue で応答を待って順に送る。QEMU では UNMAP_BLOB は memory region の削除（KVM の memslot の更新と RCU の同期）で、数百 ms かかりうる（未計測、推定）。buffer の fd の close（backend_us）も最後の参照なら同じ解放の列を通る。
- 案（別の Phase、大きいので今回はしない）:
  1. kernel: resource の host 側の解放（UNMAP・DETACH・UNREF）を venus の driver の worker の thread に回し、ioctl・close は session からの切り離しだけで返す。compositor から時間が消える一番大きな直し。GPU の driver（venus）の Phase。
  2. libvulkan: 返事の要らない destroy（vkDestroy*・vkFreeMemory の renderer 側）を返事を待たずに送る（Venus の本来の形）。kernel の command の protocol に「返事なし」の command が要る（gpu-op.h の UAPI。HAL ではないが UAPI の変更）。
  3. 計測: `KWL RETIRE slow` を view・image・memory・backend に分けて出すと 1・2 のどちらが効くかが分かる（今回は入れていない）。
