# BUG-258: 5330 の素の起動で USB メモリが disk にならない（USB-A でも USB-C TC2 でも）

- 状態: reproduced（5330 bare metal、2026-10-08 ユーザーの UAT） / tracking（解析中）
- 発見: 2026-10-08 ユーザーの UAT「USBメモリは認識しないですね。通知はないですしFilesでも見えないです。」「USB-AもUSB-C TC2も試しましたがだめでした。」
- 環境: Latitude 5330、zedBSD 1.0.0-beta2+g2fe4a50（2026-10-07）を USB から単独起動。
- 証拠: [dmesg-5330-20261008.txt](BUG-258/dmesg-5330-20261008.txt)（i915 の perf・vk・resident shim の行を除いた dmesg）。時刻の無い dmesg なので、どの行がどの挿し込みかは推定。
  - USB-C TC2（usb0 port 3、普段は Realtek LAN 0bda:8156 の port）: `05e3:0748` が `usb-storage: only LUN 0 of 4 is supported` → `LUN 0 has no medium; reader attached without a disk`。media が LUN 0 に無い（LUN 1〜3 にある）か、LUN 0 が最初の TEST UNIT READY で NOT READY を返すだけ（時間を置くと ready）か、のどちらか（未確認）。
  - USB-A（推定 usb1 port 2）: `usb1: port 2 enumeration failed (13)`（ENODEV）を挿す度に。
  - 以前は Kioxia `30de:6544` が usb1 port 16 で `sdb` として publish された（その後抜けた）ので、usb-storage 自体は動く。
- 未確認: ユーザーの USB メモリの型番（05e3:0748 が当の物か）、USB-A の port 2 に何が挿さったか。

## 解析（2026-10-08、bug-analyzer のやり直し。Q1 が要点を確認）

前回の仮説の訂正: `usb1: port 1/2 enumeration failed (13)` は USB-A ではなく Type-C TC1/TC2 の USB2 側の companion port（SS で link が張れると USB2 の終端が外れて ENODEV）で、無害の雑音。`LUN 0 has no medium` は LUN 0 が本当に MEDIUM NOT PRESENT（02/3A）を返した時だけ出る。USB-A に挿した物は Kioxia 30de:6544（usb1 port 16、`sdb` を publish → その後 disconnected）。

- **候補 A（USB-A、最有力）**: usb-storage（BOT）の hot-plug では partition table を一度も読まない。`partitions_pending=1` が立つのは再 probe の経路（usb-storage.c:1796）だけで、attach（`storage_attach` :1904〜、publish :1977 付近）では 0 のまま。UAS は attach で立てる（usb-uas-disk.c:440）。kernel に disk の ADD で scan する物は無く、volumed は BLKREREADPART を呼ばず、MBR の whole disk は FS の type が無いので volume にならない → 通知も Files も出ない。dmesg でも boot 時の sda には `vfs: scan`・partition の行があるが sdb には無い。QEMU の受け入れ（ws132 p004）は partition 無しの superfloppy だったので見逃した。Q1 が `grep partitions_pending` で 1796 だけを確認。
- **候補 B（USB-C TC2）**: 05e3:0748（Genesys の多 slot の card reader、GET_MAX_LUN=3）。driver は LUN 0 しか probe しないので、media が LUN 1〜3 にあると見えない。
- 候補 C（低い）: sdb の disconnect が抜去でなく電気的な落ち。候補 A なら「認識しないので抜いた」で説明がつく。

確かめ方（実機、code の変更なし）: Kioxia を USB-A に挿して抜かずに 30 秒 → `ls /dev/sd*`（sdb だけで sdb1 が無い）→ root で `diskpart reload /dev/sdb` → sdb1 と通知・Files が出れば A 確定。

修正の方針: A は attach の publish の成功の後に `partitions_pending = 1`（UAS と同じ。superfloppy は partition_reload の EINVAL を成功扱いなので壊れない）。B は (a) 最小: LUN 0..max を順に probe し media のある最初の LUN を使う、(b) 本来: LUN ごとに disk を持つ。

## 修正（2026-10-08、P3、agent/p3 の 1859f13f2、base main cc283689c）

- **候補 A**: `storage_attach` で `storage_publish_disk` が成功した後に `partitions_pending = 1`。読み込みは control worker（`storage_refresh_partitions`、command の lock の外）。
  - 解析の見落とし（P3 が code から、Q1 承認）: 5330 の起動 disk `sda` 自体が usb-storage（BOT）で、publish → `vfs_scan_physical_disks` の順。無条件の pending だと worker（別 thread）が boot の scan と競って `partition_reload` する（scan が後なら `partition_create_disk` が EEXIST で loader の partition を見失い、scan の途中なら child disk が置き換わる。scan が先で root が mount 済みなら EBUSY で毎秒の再試行が止まらない）。
  - 対策（usb-storage の中だけ、kernel の API は不変）: root が未 mount（`mount_root_get_ref()` が NULL、root の mount は boot の scan の後）の間は pending のまま待つ。root の mount 後、その disk の partition が pool（`partition_at`）に既にある（boot の scan が読んだ）なら reload せず pending を消す。無ければ reload（superfloppy の EINVAL・EOPNOTSUPP は従来どおり成功扱い）。判断は `include/drivers/usb/usb-storage-media.h` の `storage_partition_decide`。
  - UAS（`usb-uas-disk.c:440`）も同じ潜在の問題（UAS の boot disk で boot の scan と競う）を持つ。記録だけ（範囲外）。
- **候補 B (a)**: GET MAX LUN の答え（失敗・1 byte でない・15 を超える時は 0）を `storage->maximum_lun` に保ち、attach と control worker の再 probe（ABSENT・REVALIDATE）で LUN 0..max を順に `scsi_probe` し、media のある最初の LUN を `storage->lun` に使う（`storage_probe_luns`、判断は同じ header の `storage_lun_scan_*`）。media 無し（02/3A）の slot が 1 つでもあれば今と同じく reader として attach（ABSENT、worker が全 LUN を再検出）。全 LUN が他の理由で失敗なら最初の error で attach 失敗。単 LUN の device は従来と同じ動作・同じ log。新しい log: `usb-storage: N LUNs; probing each for a medium`・`usb-storage: LUN k of N has a medium`・`usb-storage: LUNs 0-M have no medium; reader attached without a disk`。LUN ごとの disk（(b)）は範囲外。
- 範囲外（記録だけ）: Type-C の companion port の `enumeration failed (13)` は変えていない。
- **reload の event**（P3 が見つけ、Q1 の指示で BUG-258 の範囲に追加）: `disk_reload_replace`（`src/kern/disk.c`）は reload で現れた partition の ADD・消えた partition の REMOVE の system event を出していなかった。volumed は disk・USB の event の 300 ms 後に全 block device を見直すだけなので、hot-plug の whole disk の ADD から worker の reload が 300 ms 以内に終わらないと sdX1 が volume にならず通知も出ない（timing 依存）。修正: `disk_reload_replace` が commit の前に古い partition を記録し（commit は各 child の参照が 1 つであることを要るので、まだ pin しない）、commit の後に registry の lock の下で古い・新しい partition を pin し、lock の外で古い物の REMOVE・新しい物の ADD を出して pin を外す（各 32 まで、`DISK_RELOAD_POST_MAX`。どれか 1 つの event で listener は全 disk を見直す）。pin は reload がまだ disk を持つ間（関数を返す前）に外すので、`partition_reload_owned` の古い child の `disk_destroy` は従来どおり。UAS・`diskpart reload`（BLKREREADPART）も同じ経路で event が出る。
  - volumed の重複への耐性（読みで確認）: `volumed_events` は DISK・USB の event ごとに 300 ms 後の再走査を予約するだけで、`volumed_merge` は id で照合する状態の比較なので、REMOVE sdb1 → ADD sdb1 の続き（同じ table の reload）や重複した ADD は既知の volume を保ち、新しい id だけ `VOLUMED ADD` を出す。
