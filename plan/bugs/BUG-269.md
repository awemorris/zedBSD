# BUG-269: 5330 で ESP（FAT）に vmunix（約 3 MB）を cp・sync・umount すると、sshd が応答しなくなり電源を切るまで戻らない

- 状態: reproduced（実機 5330、2026-10-08 に 2 回） / resolved（2026-10-08 夜 ユーザー「下記は実装の変更が多かったので、いったんすべてcloseします。」、Q1 の中継）
- 観察（Q1、SSH）: `mount -t msdos /dev/sda1 /tmp/esp; cp /tmp/vmunix.q1 /tmp/esp/vmunix; sync; umount /tmp/esp` を sudo で流すと、ping は返るが SSH の port 22 が timeout（banner の交換で止まる）。1 回目（2026-10-08 午後）はユーザーの電源の再投入の後、file は全部書けていた（cksum 一致）。2 回目（夕、BUG-267 の kernel）も同じく応答なし。最初の 1 回（06:23）は cp の後しばらく遅れたが戻った。
- 疑い（未確認）: FAT の書き込み（cluster の割り当て・FAT の table の更新）か sync・umount が長く lock を持ち、他の process（sshd の fork・file の open）が待つ。
- 影響: Q1 の 5330 の更新の手順が毎回止まる。利用者が ESP を書く場面（更新）でも起きうる。
- 担当: 未割当（ベータ2 の残りの後か、kernel の fs の担当に）。

## 調べ（2026-10-08 夜 P2、code の読み。QEMU・実機は未実施）

- 5330 の単独起動は USB stick（usb-storage、BOT）から。ESP は 64 MiB の FAT32 で、mformat の既定で **cluster が 1 sector（512 B）**（同じ引数で作った image を `minfo` で確かめた）。root の UFS も同じ stick。
- FAT の file の書き込み（`src/drivers/fs/fat.c` の `fat_raw_write_bytes`）は **1 sector ずつ**一つの sector の cache を通して書き、毎回 flush する。buffer cache の line は 4 KiB なので、1 sector の書き込みごとに 4 KiB の line を丸ごと書き戻す（WRITE(10) が 1 つ）。新しい cluster は書く前に 0 で埋める（`fat_raw_zero_cluster`、これも 1 sector ずつ）。cluster の割り当ては FAT の 1 sector の中の 31 個までを 1 つの transaction にし、その中で `disk_sync`（SYNCHRONIZE CACHE を含む）を 2 回以上。
- 見積り: 3 MB の vmunix で、0 埋め 6144 回と data 6144 回の 4 KiB の WRITE(10)（約 48 MiB を書く）、約 200 の transaction と約 400〜600 の SYNCHRONIZE CACHE。USB stick は小さい書き込みの繰り返しと flush が遅いので、数分から数十分かかりうる。その間 usb-storage の `storage->lock`（mutex、手放した直後に cp の thread がまた取る）を cp が取り続け、同じ stick の root の UFS を読む sshd の exec・login が待つ。ping は kernel の中で返る。症状と合う（1 回目の cksum 一致も、書き込みは完了していたことと合う）。
- 未確認: 実機の stick の 1 回の書き込み・flush の時間、lock の取り合いで sshd が待つこと（gdb で thread を見る道具が無い）。

## 直し（2026-10-08 夜 P2、dedf4a0a4）

- `fat_raw_write_bytes`: sector の頭から始まる sector 単位の部分は、続いた cluster をまたいで最大 128 sector（64 KiB）を 1 回の要求で書く（`fat_raw_write_sectors`・`fat_engine_write_run`）。一つの sector の cache と clean slot の、その範囲の写しは書く前に flush して捨てる（`fat_engine_forget_range`）。chain の伸ばし方は前と同じ（`fat_raw_write_next_cluster` に括り出した）。端の半端な sector は前の 1 sector の道。
- 0 埋め: `fat_raw_zero_cluster` は cluster を 8 sector の 0 の block で書く。`fat_raw_allocate_run` は予約した cluster の内、番号の続く物をまとめて 0 で埋める（`fat_raw_zero_clusters`）。順番（0 埋め → disk_sync → FAT の公開）は変えない。
- 見積り（3 MB、512 B cluster）: 0 埋め約 200 回（各 31 cluster）、data 約 50〜100 回、transaction の数と SYNCHRONIZE CACHE の数は変わらない（約 200 と 400〜600）。transaction の大きさ（FAT_BATCH_ENTRIES 32）を 128 に上げれば SYNCHRONIZE CACHE も 1/4 になるが、stack の配列が大きくなるので今回は入れない（試験の数で要否を決める）。
- 確認: `make -j16 ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/amd64 build/amd64/vmunix` exit 0・warning 0、style-check で新しい指摘なし（既存の指摘は残る）。QEMU は T1 に依頼（USB の WRITE(10)・SYNCHRONIZE CACHE の数を `sysctl vfs.io.stats` で前後比較、cksum、cp の間の SSH の応答）。実機 5330 は Q1。
