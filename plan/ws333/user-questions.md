# WS333 ユーザーへの問い（用語と概念から）

2026-10-31 P5（q1734-i01）。設計の本文は [design.md](design.md)。

## 前置き

- **どの WS か**: WS333「/dev/thermal で統一する電力・熱の枠組み」。
- **どんな WS か**: CPU の休み方（idle）と速さ（P-state）、P-core と E-core の速さの比、温度の読み、fan、熱と速さの方針（strategy）、危ない温度での電源断を、1 つの device `/dev/thermal` と道具 `/sbin/thermal` にまとめて作る。WS301（CPU の速さ）と WS303（熱と fan）を 2026-10-31 に統合した WS。最初の対象は 5330（Dell のノート）。
- **今の状態**: 設計の段（p001、P5）。並べて p002（amd64 の CPU の休み方を HLT から MWAIT に、P1）が進行中。実装はまだ。
- **決まっていない事**: 下の 7 つ。Q333-1〜5 は WS303 で聞いていて答えが無かった物（統合で前提が変わった Q333-1 は聞き直し）、Q333-6・7 は新しい物。どれも推しで進めても後で直せる。Q333-7 は今は「いつ決めるか」だけを決める。

## 用語

- **strategy**: 「速さ優先か、省電力か」の全体の方針。performance（速さ）・balanced（釣り合い）・powersave（省電力）・manual（手で 3 つの軸を決める）の 4 つ（WS303 Q303-11 の答え）。
- **受け手**: strategy を受け取り、自分の hardware に当てはめる部分（driver）。CPU の速さの driver は CPU の周波数の範囲に、Dell の driver は BIOS の熱の mode に、Pi 5 の fan の driver は fan を回し始める温度に写す。
- **3 つの軸**（manual の時だけ、各 0〜100）: 実行速度（speed）、騒音（noise）、細粒度パワーゲート（gating: 使っていない部分の電源をこまめに切る事）。
- **C-state**: CPU が仕事の無い時に入る休みの深さ。C1 は浅く（すぐ起きるが電力が多い）、C6・C8・C10 は深い（電圧を下げ、起きるのに数百 µs かかる見込み）。core ごとの休みと、全部の core が同時に休んだ時の package（CPU の部品全体）の休みがある。
- **P-state と HWP**: CPU が動いている時の周波数。HWP は Intel の CPU が自分で周波数を決める仕組みで、OS は範囲と「性能寄りか省電力寄りか」を伝える。
- **tick**: OS が時間を数えるための周期の割り込み。zedBSD の amd64 は 1 秒に 1000 回、全部の CPU（5330 は 12）で来る。来るたびに休んでいる CPU が起きる。
- **HAL**: zedBSD の kernel と CPU・board の間の層。宣言（`include/hal/hal.h`）を変えるにはユーザーの承認が要る。
- **RAPL**: Intel の CPU が持つ電力の積算の計数。package・core・GPU の使った電力量（J）を読める。
- **firmware**: 機械に最初から入っている制御の program（BIOS、Dell の EC など）。5330 の fan は firmware が回す。
- **rc**: 起動の時に init が走らせる設定の手順。

## Q333-1 起動した時の strategy（WS303 の Q303-15 を聞き直す）

- 背景: WS303 では「起動では何も書かない（firmware のまま）」を推しにしていた。その後、2026-10-31 に「CPU の省電力を先に直す」指示があった。起動で何も書かないと、HWP（CPU が自分で周波数を省電力寄りに決める仕組み）は使われないままで、利用者が毎回 `/sbin/thermal` で選ぶまで省電力が効かない。
- 決まると変わる事: A なら起動は今と同じで、省電力は利用者が選んだ時から。B・C なら起動の後すぐ CPU が balanced で動く（`CONFIG_CPU_PERF=y` の kernel の時。今の既定は「試験が通るまで無効」、WS301 Q301-4）。
- (A) firmware のまま（何も書かない。表示は FIRMWARE と firmware の今の mode の名前）。
- **(B, 推し)** 最後に選んだ strategy を `/etc` に保存し、起動の時に rc が `/sbin/thermal` で渡す。保存が無ければ balanced。Dell の BIOS の mode は、今の mode と同じなら書かない（書くと BIOS の設定の書きと SMI という firmware の呼び出しが起動のたびに走るため）。
- (C) kernel が起動の時に自分で balanced にする（保存しない）。
- 推しの理由: 省電力が既定で効き、利用者の選びも再起動で残る。kernel に方針の起動の parameter を持たせない（WS301 Q301-7 の答え「持たせない」）形のまま、user の側の設定でできる。

## Q333-2 細粒度パワーゲート（gating）の軸が何に効くか（WS303 の Q303-16）

- 背景: gating を効かせる先は、CPU の休みの深さ、PCIe の link の省電力（ASPM）、NVMe の自動の省電力（APST）、GPU の部分の電源断など、別々の driver。CPU の休みの深さは今は HAL が決め、OS から変える口が無い（Q333-7）。ASPM・APST は WS300、GPU は各 GPU の WS。
- 決まると変わる事: A はこの WS の仕事が大きく増え、HAL の変更も要る。C は軸の値を記録して見せ、各 WS が自分の時に使う。
- (A) この WS で全部の受け手を作る。
- (B) CPU の休みの深さだけ（HAL の口が要る、Q333-7 と同じ判断になる）。
- **(C, 推し)** 軸は保存して示すだけ。受け手は WS300 などがそれぞれ足す。CPU の休みの深さは Q333-7 の口が出来た時に受け手にする。
- 推しの理由: 受け手の hardware を扱う WS が別にあり、そこで作る方が正しく試せる。CPU の分は測りで要ると分かってから。

## Q333-3 root の直の設定と strategy の関係（WS303 の Q303-17）

- 背景: root は CPU の周波数の範囲を数で直に書ける（診断用、WS301 Q301-7 の答え）。書いた後の strategy の表示と、次に strategy を選んだ時をどうするか。
- **(A, 推し)** 直の設定が strategy より優先し、表示に「custom（直の設定あり）」の印。次に strategy を選ぶと直の設定は消える。
- (B) 直の設定は manual の時だけ許す。
- 推しの理由: 直の値は root の診断用という答えに合い、診断の後は strategy を選び直すだけで元に戻る。

## Q333-4 3 つの軸の向き（WS303 の Q303-18）

- 背景: 0〜100 のどちらの端が何かを決めないと、driver ごとに逆に作られる恐れがある。特に「騒音」は「騒音の多さ」とも「静かさの度合い」とも読める。
- **(A, 推し)** どれも「100 = その物が多い」: speed 100 = 一番速い、noise 100 = 一番うるさくてよい、gating 100 = 一番こまめに電源を切る。
- (B) どれも「100 = 好ましい方」: speed 100 = 一番速い、noise 100 = 一番静か、gating 100 = 一番こまめに切る。
- 推しの理由: 軸の名前（実行速度・騒音・パワーゲート）をそのまま量として読める。

## Q333-5 firmware が fan を遅くする mode（Dell の Quiet）を選んでよいか（WS303 の Q303-19）

- 背景: 5330 の BIOS の熱の mode は 4 つ（UltraPerformance・Optimized・Cool・Quiet）。Quiet は firmware が fan を遅くし、代わりに CPU の電力を下げる。ユーザーの決定は「必要な回転数を下回らせることはできない」「コントロールできないときはストラテジだけファームウェアに伝える」。OS は firmware の fan の曲線を変えられない。
- 決まると変わる事: A なら manual で騒音を低くした時に Quiet を選ぶ。B なら Quiet は使わず、静かさは CPU の上限を下げる事だけで得る。
- **(A, 推し)** よい。manual で noise ≤ 33 の時だけ Quiet（powersave は Cool）。
- (B) 選ばない。
- 推しの理由: OS が fan を下げるのではなく、firmware に方針を伝え、firmware が自分の温度の判断で回す形で、「ストラテジだけファームウェアに伝える」に当たる。

## Q333-6 電力の読み（RAPL）と CPU の休みの統計を /dev/thermal に入れるか（新しい問い）

- 背景: 5330 の zedBSD は何もしていない時に 12.99 W を使い、Linux は 3.2〜3.5 W（WS291 p022）。今 zedBSD で電力を読む方法は、GPU の driver に一時的に当てる診断の patch だけで、source に入っていない。改善を確かめるにも、strategy の写し方を調整するにも、電力と「CPU がどの深さでどれだけ休んだか」の数が要る。どちらも読みだけで、CPU の model ごとの register（許可の表に載った CPU だけ）から読む。
- 決まると変わる事: A なら `/sbin/thermal` で電力（W）と休みの深さの割合が見え、受け入れの試験もこれで測る。B なら試験の時だけ診断の patch を当てる。
- **(A, 推し)** 入れる（読みだけ。電力の上限を書く制御はしない）。
- (B) 入れない。
- 推しの理由: この WS の受け入れ（省電力が効いたか）を source の中の口で測れ、後の調整にも使える。書かないので firmware の電力の制御と衝突しない。

## Q333-7 CPU の休みを OS がもっと制御する口（HAL の変更が要る）をどう扱うか（新しい問い）

- 背景: p002 で CPU の休みを HLT（浅い C1）から MWAIT（深い C-state）にする。これは HAL の実装の補完で、HAL の宣言は変えない。ただ、さらに 2 つの事は、今の HAL の口では足りない。
  1. **休んでいる CPU の tick を止める**: 12 個の CPU に 1 秒 1000 回ずつ tick が来て休みを起こすため、全部の core が同時に深く休む（package の深い休み）間が短い見込み（推定）。tick は HAL の中の各 board の部分が周期で動かし、kernel から止める口が無い。系の S0 idle 用の口（`hal_cpu_idle_suspend`）は tick を止めるが、用途が系の sleep に決まっている。kernel の側だけでは、各 CPU の時間つきの待ちをその CPU の tick で起こす作りのため止められない。
  2. **休みの深さの上限を OS が選ぶ**: 深い休みから起きる時間（数百 µs の見込み、未確認）が、入力・音・ゲームの応答を遅らせる時に浅くする口。gating の軸の受け手にもなる。`hal_cpu_idle()` は引数を持たず、HAL は kernel の値を読めないので、宣言の追加が要る。
  どちらも、要るかは p002 と p009（5330 の測り）の数で決まる。tick の件は WS332（tick の周期を API で扱う WS、周期を変える実装は将来）とも重なる。
- 決まると変わる事: A なら今は HAL の案を作らず、5330 の測りの後に、数と、既存の口で代えられない理由と HAL の差分の案を示して決めてもらう。B なら今から HAL の案を作る（要らないかもしれない案になる）。C ならこの WS では扱わず、WS332 の将来の拡張に移す。
- **(A, 推し)** p009 の測りの後に、数と HAL の差分の案と理由を示して決める。
- (B) 今から HAL の案を作る。
- (C) この WS では扱わない（WS332 の将来へ）。
- 推しの理由: HAL を変える必要を数で示せる時だけ案にする（これまでの方針）。p002 の MWAIT だけで十分に下がる可能性もある。
