# GPU drivers and node kinds

Status: experimental reference for GPU ABI version 1.

Eight kernel drivers publish `/dev/gpuN` nodes: amdrdna (AMD RDNA), bcm2711 (Raspberry Pi VideoCore, V3D and HVS), ghci (a PCIe GPU with the GPU Host Controller Interface), i915 (Intel), mali (Arm Mali), nvrtx (NVIDIA RTX), powervr (Imagination PowerVR) and venus (the virtual GPU of QEMU). Five of them publish one node per physical GPU, and that node does both rendering and display. Three of them (bcm2711, mali, powervr) publish two nodes per GPU: a display node that only shows images and a render node that only renders. The table below has one row for each kind of node. The capability bits that `GPU_GET_INFO` returns decide at run time what a node offers; the table explains where those bits come from and what each display does. See [the device interface](gpu.md) for the rules every node shares and [capabilities](gpu-capabilities.md) for the meaning of each bit.

## Node kinds

Capability bits are written without the `GPU_CAP_` prefix, so `DISPLAY` is `GPU_CAP_DISPLAY`. Output flags are written in full. The architectures are those whose kernels can contain the driver; a driver that a build option turns off is marked.

Every driver fills in the capability bits of its operation table before it calls `drv_gpu_register`, and `GPU_GET_INFO` returns the bits of the registered table at the time of the call. No driver in the tree changes the table after registration. The "Bits added later" column therefore says which conditions at attach time select the bits, and a program that has read the bits of a node does not need to read them again.

In the Display behaviour column, "Present" says when `GPU_DISPLAY_PRESENT` returns for a frame and "Wait" says how the driver answers `GPU_DISPLAY_WAIT`. Every display in the tree sets `GPU_DISPLAY_FIFO`. The kernel core does not read that flag; it is the driver's statement that the output takes whole frames in order, and libvulkan uses it to offer the FIFO present mode. Only venus sets `GPU_DISPLAY_ATOMIC_MODE_PRESENT` and `GPU_DISPLAY_VIRTUAL_CLOCK`. `GPU_DISPLAY_ACTIVE` and `GPU_DISPLAY_CONNECTED` follow the state of the output, and the table names them only when the driver sets them on every query.

## Render and display pairs

bcm2711, mali and powervr split the work over two nodes. The display node has `GPU_CAP_DISPLAY` and none of the rendering bits, and its `GPU_DEVICE_QUERY` reports only `GPU_DEVICE_DISPLAY`. The render node reports only `GPU_DEVICE_RENDER`. Each driver registers its display node first, so it normally gets the lower node number, but node numbers follow probe order and are not stable (see [the device interface](gpu.md)). The other drivers (amdrdna, ghci, i915, nvrtx, venus) publish one node whose `GPU_DEVICE_QUERY` roles are the ones it implements.

Every driver in the tree sets `companion_id` to zero, which means no preference, so a program cannot find the render node of a display node through `companion_id` today. It reads the roles and `device_id` of every node (see [memory](gpu-memory.md) for `GPU_DEVICE_QUERY`), and it asks the display node for `GPU_DISPLAY_CONSTRAINTS` to learn which routes its frames can take (see [display](gpu-display.md) and [sharing](gpu-sharing.md)).

The three display nodes answer `GPU_SCANOUT_COPY`, `GPU_SCANOUT_SHARED` and `GPU_SCANOUT_FOREIGN`, with the formats `GPU_DISPLAY_FORMAT_BGRA8888` and `GPU_DISPLAY_FORMAT_RGBA8888` and a stride and offset alignment of 4 bytes.

- bcm2711 also requires `GPU_PLACEMENT_CONTIGUOUS` and a DMA address at or below 0x3fffffff for an imported allocation.
- powervr and mali ask for no placement. Their import is a trial: the display node imports an image that its render node exported, as a linear packed 4-byte format in one contiguous run of RAM. Any other image is refused with `ENOTSUP`, and the swapchain then copies its frames through ordinary storage. On mali an imported image below 4 GiB is scanned directly and one above it is copied.

A node that does both jobs answers only `GPU_SCANOUT_SHARED` and `GPU_SCANOUT_COPY`: it shows its own blobs, or copies ordinary storage.

## Known differences between capability bits and behaviour

A set bit says that a node implements a group of requests. In these cases a request that a set bit guards does not work in every state of the node.

- venus with `GPU_CAP_JOB` and `GPU_CAP_JOB_CAPACITY`: the node always reports both bits in `GPU_GET_INFO`. At attach the driver reads the host's vendor capset and grants strict queue completion only to a host that answers with the paired profile (the vendor magic and one of the three flag values the driver knows). On any other host, such as stock QEMU, `GPU_JOB_RESERVE` and `GPU_JOB_CAPACITY` answer `ENOTSUP`, and the other job requests then have nothing to act on because no reservation can be made. The `STRICT_QUEUE` flag of the vendor capset (see [capabilities](gpu-capabilities.md)) tells a program which kind of host it has. The driver's own information operation clears the two bits for such a host, but the core replaces the bits with those of the registered table, so a caller never sees that.
- nvrtx and i915 with `GPU_CAP_DISPLAY_CONTROL`: `GPU_DISPLAY_REFRESH` works, but an output without `GPU_DISPLAY_POWER_CONTROL` answers `GPU_DISPLAY_POWER` with `EOPNOTSUPP`. nvrtx never sets that flag and answers after its display and lease checks. i915 sets it only on an eDP panel.
- Cursor and overlay requests depend on output flags, not on a capability bit. A node with `GPU_CAP_DISPLAY` whose display has no cursor operations answers `GPU_DISPLAY_CURSOR_SET`, `GPU_DISPLAY_CURSOR_MOVE` and `GPU_DISPLAY_CURSOR_HIDE` with `EOPNOTSUPP`: mali, venus, all three i915 displays, and ghci on a controller without a cursor plane. nvrtx and powervr have the operations but set `GPU_DISPLAY_HAS_CURSOR` only when the cursor channel or the frame counter was set up, so a program reads that flag on the output. `GPU_DISPLAY_COMMIT` and `GPU_DISPLAY_OVERLAY_INFO` answer `EOPNOTSUPP` on every node except the bcm2711 display node, the only one with `GPU_DISPLAY_HAS_OVERLAYS`.
